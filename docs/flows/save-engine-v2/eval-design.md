# 평가 설계 — 진술 엔진 (save-engine-v2)

> 진술 엔진의 세 동작 — 쪼개기·분류·검색 — 이 잘 도는지 **숫자로** 재는 방식과 평가셋 씨앗, 실행 계획. [`ingestion-design`](ingestion-design.md)의 절단 원칙과 [`retrieval-design`](retrieval-design.md)의 검색 계약을 재는 짝 문서다. 두 설계가 "하니스에서 보정"으로 미룬 값들(절단 기준 세부·limit·threshold)을 보정할 측정 도구가 이것이다.
>
> 테스트 하니스 화면(NEM-125)이 돌릴 *내용물*을 정한다 — 화면 자체는 범위 밖.

---

## 0. 이 문서가 정하는 것 / 정하지 않는 것

- **정한다**: 3대상 각각의 지표·채점 방법, 평가셋 씨앗의 구성 원칙과 위치, eval 디렉터리에 잇는 실행 계획.
- **정하지 않는다**: 테스트 페이지 화면(E 본작업), 관계·충돌·되돌리기 평가(관계 엔진 후속), 지표의 합격선(첫 측정에서 기준선을 잡은 뒤 정함), 러너의 구현 코드.

---

## 1. 무엇을 재나 — 3대상

| 대상 | 묻는 질문 | 재는 계약의 출처 |
|---|---|---|
| **쪼개기** | 글이 기대대로 진술로 끊기나 + 같은 글이 매번 비슷하게 끊기나 | ingestion-design 3장 절단 원칙 1~4 |
| **분류** | 종류(claim/question/todo)와 확신도(claim의 certain/guess)가 맞나 | schema-design 4.2 |
| **검색** | 뜻으로 물으면 관련 진술이 나오나 (같은 단어를 안 써도) | retrieval-design 1~3장, 09 완료 기준 |

## 2. 박힌 결정

1. **검색 코퍼스 = 골든 진술 직접 임베딩.** 추출 결과가 아니라 사람이 확정한 기대 진술을 코퍼스로 쓴다 — 검색 성능만 격리 측정되고(점수가 나쁘면 원인이 무조건 검색 쪽), 추출 엔진 빌드 전에도 돌릴 수 있다. 엔진 추출 결과를 코퍼스로 쓰는 엔드투엔드 점검은 쪼개기·검색이 각각 안정된 뒤의 후속(8장).
2. **의미 매칭 = LLM 심판 이진 판정으로 통일.** "두 진술이 같은 의미인가"가 골든 대조와 일관성 측정 양쪽에 필요한데, 임베딩 유사도 임계값(또 하나의 보정 문제, 경계 오판)을 피하고 심판 이진 판정 하나로 통일한다. 우리 규모(진술 수십 × 반복 5회)에서 비용은 무시할 수준.
3. **심판 모델 = 추출과 다른 계열(Claude).** 추출이 gpt-5인데 같은 계열이 채점하면 자기선호 편향이 정확히 우리가 보정하려는 지점(절단 습관)에서 눈을 가릴 수 있다. 평가셋은 측정 도구라 신뢰를 처음부터 확보한다. `LlmProvider` 인터페이스 뒤에 평가 전용 provider 하나 추가 — 제품 경로는 안 건드린다.
4. **점수 척도 = 이진 pass/fail.** 모든 심판 판정은 이진. 다단 척도(5점 등)는 모델별 반응이 달라 불안정하다는 게 실무 통설.
5. **심판 판정의 사람 표본 검사.** 심판 매칭·품질 판정 중 20~30개를 사람이 표본 검사해 심판-사람 정렬을 확인한다. 작은 평가셋에서는 이 검사가 어차피 필수라, 심판이 미덥지 않으면 데이터로 드러난다.
6. **절단 기준의 주인은 사람.** 골든 진술은 고정 정답이 아니라 *씨앗*이다 — 시스템(이 문서 작성 포함)은 후보로 끊어 제안하고, 경계가 애매한 항목은 `needsHumanReview`로 표시해 사람이 확정·보정하며 자란다. 04가 절단 기준을 "실제 데이터를 끊어보며 정한다"로 열어둔 것과 같은 태도.
7. **숫자보다 실패 사례.** 질의 수십 개 규모에서 지표의 소수점 증감은 잡음이다. 결과 보고의 1급 산출물은 실패 사례 목록("대명사 해소 4건 중 3건 실패")이고, 집계 숫자는 추세 참고용.

## 3. 쪼개기 평가 — 세 측정

### 3.1 골든 대조 — 진술 단위 precision / recall / F1

기대 분할과 실제 분할은 1:1이 아니라 n:m이라, 위치 기반 세그멘테이션 지표(Pk·WindowDiff)는 부적합하다. 의미 매칭 후 진술 단위로 센다 (claim extraction 평가의 표준 패턴).

```
입력 글 → 추출 → 진술 N개
                    │  심판 매칭: (추출 진술, 골든 진술) 쌍마다
                    │  "같은 의미인가" 이진 판정, greedy 1:1
                    ▼
precision = 매칭된 추출 수 / 전체 추출 수      (과잉 추출이 깎는다)
recall    = 매칭된 골든 수 / 전체 골든 수      (누락이 깎는다)
F1        = 둘의 조화 평균
```

- 매칭은 greedy 1:1 — 골든 하나에 추출 둘이 닿으면(과잉 분리) 하나만 매칭되고 나머지는 precision을 깎는다. 추출 하나가 골든 둘을 덮으면(과소 분리) 골든 하나가 미매칭으로 남아 recall을 깎는다. 절단 오류가 지표에 그대로 비친다.
- 골든 진술에는 시험하는 축 태그(`axes`)가 붙어 있어, 실패를 축별로 집계한다 — "복합문 분리 실패 N건" 같은 그림.

### 3.2 차원별 품질 — 절단 원칙을 루브릭으로

매칭과 독립적으로, 추출된 진술 각각에 원문을 동봉하고 이진 심판 3개(차원당 프롬프트 분리):

| 차원 | 판정 질문 | 절단 원칙 |
|---|---|---|
| 원자성 | 하나의 '왜'만 담는가 | 원칙 1 |
| 자기완결 | 원문 없이 단독으로 읽히는가 (대명사·생략 해소) | 원칙 2 |
| 충실성 | 원문에 없는 내용을 보태거나 확신 수준을 과장하지 않았는가 | 원칙 3 |

- 차원별 pass율로 집계. 포괄성(누락 없음)은 별도 차원이 아니라 3.1의 recall이 담당.
- 골든 없이도 돌릴 수 있는 측정이라, 나중에 골든이 없는 실데이터에 그대로 확장된다.

### 3.3 일관성 — 같은 입력 반복의 쌍대 일치율

절단 원칙 4("같은 글은 같은 모양으로")의 직접 측정.

```
같은 입력 5회 실행 → 실행 쌍 10개 각각:
  두 결과를 3.1과 같은 심판 매칭으로 대응 → 쌍대 F1
일관성 점수 = 10쌍 F1의 평균   (+ 진술 개수의 분포 병기)
```

5회 중 1회는 3.1·3.2의 채점 대상을 겸한다 (별도 실행 없음).

## 4. 분류 평가 — 심판 없이 정답 대조

3.1에서 매칭에 성공한 (추출, 골든) 쌍에 한해 라벨을 직접 대조한다. 라벨 맞히기에 LLM 심판은 불필요 — 정답 대조로 충분하다는 게 통설.

- **type**: 일치율 + 3×3 혼동 행렬(claim/question/todo). 케이스가 적어 macro-F1 같은 집계보다 혼동 행렬을 눈으로 보는 게 유익하다 — 어느 경계(claim↔todo 등)가 흔들리는지가 바로 보인다.
- **confidence**: 양쪽 type이 claim인 쌍에 한해 certain/guess 일치율.
- LLM 호출 0회.

## 5. 검색 평가 — recall@5 + MRR

```
골든 진술 전체 임베딩 → Qdrant 평가용 컬렉션
골든 질의 각각 → retrieval-design의 검색 경로(전처리 없이 임베딩 → 검색)
  → recall@5 : 기대 진술 중 상위 5에 들어온 비율 (질의별 → 평균)
  → MRR     : 첫 정답의 역순위 평균 (1등이면 1, 3등이면 1/3)
```

- 코퍼스가 작고 정답이 질의당 1~3개라 recall@k + MRR 조합이 가장 직관적(이진 관련도에선 nDCG의 이점이 없다).
- **질의에 실패 유형을 의도적으로 심는다**: 패러프레이즈(같은 단어 안 쓰고 묻기 — 09 완료 기준의 직접 검증이라 과반), 부정, 시간 표현, 고유명사 표기 변형 각 2개, 정답 없는 질의 2개.
- 정답 없는 질의는 recall/MRR 집계에서 제외하고 top-1 점수만 기록 — "엉뚱한 게 얼마나 높은 점수로 나오나"가 threshold 보정의 반대쪽 재료다.
- **전 질의의 점수 분포를 결과에 기록한다.** retrieval-design이 미뤄둔 limit·threshold 값은 이 분포(정답의 점수대 vs 무정답 질의의 top-1 점수대)로 보정한다.

## 6. 평가셋 씨앗 — 구성 원칙

씨앗은 `apps/server/src/eval/statement-engine/seed-data.ts`. 구성 원칙:

- **글은 겸용으로 적게.** 실제 입력은 한 가지 난점만 담고 오지 않는다 — 축당 글을 따로 빚으면 실제 분포와 괴리된다(합성 데이터의 함정). 글 하나가 여러 축을 겸하고, 채점이 진술 단위라 실패 분석은 골든 진술의 축 태그로 가른다.
- **겸용 글 4 + 독립 글 2.** 겸용: 회의 메모(04의 토스 예시 그대로 — 제품 문서가 이미 보증한 유일한 골든) · 구어 전사 · 다주제 위클리 · 할일/질문 위주 머리비우기. 독립: 짧은 단문(과잉 추출 검출 — 입력이 작아야 성립), 잡담 글(추출 0개가 정답 — "진술이 안 나오는 텍스트는 추출되지 않는다"의 검증).
- **축 태그.** 골든 진술마다 시험하는 축(복합문 분리, 결정-근거 분리, 대명사 해소, 확신도 판별, todo 경계, …)을 태그로 단다.
- **`needsHumanReview` 표시.** 절단·라벨 경계가 애매한 항목은 후보로 제안하되 사람 검토 필요로 표시한다. 결정 #6.
- 규모: 글 6개, 골든 진술 ~30개, 질의 ~17개. 1회 실행이 몇 분·푼돈 안쪽이라 프롬프트를 고칠 때마다 부담 없이 돌리는 게 목적.

## 7. eval 디렉터리에 잇기 — 실행 계획

기존 `eval/` 패턴(시드 → 러너 → `results-*.json`)을 계승한다.

```
apps/server/src/eval/statement-engine/
  seed-data.ts        # 씨앗: 글·골든 진술·질의  ← 이 작업의 산출물
  judge.ts            # 심판 부품: 매칭·품질 차원 (Claude, 이진)
  run-extraction.ts   # 쪼개기(3장) + 분류(4장) 러너 — 5회 반복 포함
  run-retrieval.ts    # 검색(5장) 러너
  results-*.json      # 실행 결과 (gitignore 여부는 기존 eval 관례 따름)
```

| 러너 | 전제 | 돌릴 수 있는 시점 |
|---|---|---|
| `run-extraction` | 추출 프롬프트(ingestion-design의 LLM 1콜) + 심판 provider | **엔진 빌드 전, 추출 프롬프트가 생기는 즉시** — worker·DB 불필요 |
| `run-retrieval` | Voyage 임베딩 + Qdrant 평가용 컬렉션 | 엔진 빌드 전 가능 — 코퍼스가 골든 진술이라(결정 #1) 추출과 무관 |

- 심판용 Claude provider는 eval 전용으로 추가한다(`LlmProvider` 구현 하나). 제품 코드 경로엔 영향 없음.
- 결과 JSON에는 집계 숫자와 함께 **실패 사례 전수**(미매칭 골든, 품질 fail 진술과 사유, 검색 miss 질의와 실제 상위 결과)를 싣는다 — 결정 #7.
- E(NEM-125, 테스트 페이지)는 이 시드·러너를 받아 화면에 얹는 작업이다. 러너가 페이지보다 먼저 CLI로 돌 수 있게 설계해, 페이지 없이도 보정 루프가 시작된다.

## 8. 후속 / 미결

- **골든 확정** — 씨앗의 `needsHumanReview` 항목을 사람이 검토·확정. 이후로도 골든은 실데이터로 보정하며 자란다(절단 기준 확정과 같은 루프).
- **합격선** — 첫 실행에서 기준선을 잡은 뒤 정한다. 지금 임의 숫자를 박지 않는다.
- **심판 정렬 표본 검사** — 첫 실행 결과에서 매칭·품질 판정 20~30개 사람 검사(결정 #5). 체계적 어긋남이 보이면 심판 프롬프트 보정.
- **엔드투엔드 점검** — 추출 결과를 코퍼스로 쓰는 통합 모드. 쪼개기·검색이 각각 안정된 뒤, `run-retrieval`에 코퍼스 소스 옵션 하나 추가로 충분하다.
- **threshold·limit 값 제안** — 검색 평가의 점수 분포가 쌓이면 retrieval-design의 자리에 값을 채운다.
- **관계·충돌·되돌리기 평가** — 관계 엔진 설계 이후.

## 부록 — 조사 근거 (방식 선택의 출처)

- 이진 pass/fail·차원당 프롬프트 분리·정렬 표본 검사: [Hamel Husain — LLM-as-judge](https://hamel.dev/blog/posts/llm-judge/), [Eugene Yan — LLM evaluators](https://eugeneyan.com/writing/llm-evaluators/)
- 심판 편향(자기선호·위치·길이)과 reference 기반 채점: [MT-Bench](https://arxiv.org/html/2306.05685v3)
- 추출 평가의 차원(충실성·포괄성·원자성·자기완결)과 진술 단위 F1: [Claimify](https://arxiv.org/abs/2502.10855), [VeriScore](https://arxiv.org/html/2406.19276)
- 위치 기반 세그멘테이션 지표의 부적합: Pevzner & Hearst (2002), WindowDiff
- 반복 실행 일관성(의미 동치 클러스터): [Semantic Entropy](https://arxiv.org/abs/2302.09664)
- 소규모 검색 평가(recall@k·MRR, 질의 다양성 > 양, 실패 사례 중심): [Weaviate — Retrieval metrics](https://weaviate.io/blog/retrieval-evaluation-metrics), [Vespa — LLM-as-a-judge 검색 평가](https://blog.vespa.ai/improving-retrieval-with-llm-as-a-judge/)
- 임베딩 검색 실패 유형(부정·시간·고유명사·패러프레이즈): [BEIR](https://arxiv.org/abs/2104.08663)
