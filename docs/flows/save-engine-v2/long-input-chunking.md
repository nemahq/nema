# 초장문 분할 설계 — 진술 엔진 (save-engine-v2)

> 임계선을 넘는 장문 입력(긴 회의록·문서 붙여넣기)을 청크로 갈라 추출하는 방식의 설계. [`ingestion-design`](ingestion-design.md) 3장("추출 — LLM 1콜")의 장문 확장이다 — 짧은 글은 그 문서 그대로 1콜, 이 문서는 임계선 초과분만 다룬다. 검증은 [`eval-design`](eval-design.md)의 하니스 위에서.

---

## 0. 이 문서가 정하는 것 / 정하지 않는 것

- **정한다**: 분할 발동 임계선과 단위, 청크 경계를 고르는 규칙, 청크에 동봉하는 문맥, 청크 간 실행·실패 처리, 여러 콜의 결과를 기존 changeset 계약에 잇는 방식, 검증 계획.
- **정하지 않는다**: 입력 길이의 상한(거대 입력 거부 정책 — 운영 데이터 보고), 청크 결과 캐싱(후속, 7장), 확인/수정 화면에서 장문 결과(진술 100개+)를 보여주는 방식(화면 작업).

---

## 1. 관문 측정 — 분할은 가설이 아니라 실측으로 확정

기존 보정(추출 F1 0.958, 타임아웃 0건 — measurement-log #3·#4)은 전부 ~300자(≈200토큰) 이하에서 잰 숫자였다. 분할 설계 전에 장문 시드 4급간을 **분할 없는 현행 1콜**(gpt-5 + reasoning low, 제품과 동일)에 넣어 곡선을 그렸다. 약 1시간 간격의 두 스냅샷이다 (measurement-log #5, `run-length-curve.ts`):

| 입력 토큰 | 지연 — 빠른 시간대 | 지연 — 느린 시간대 | 진술 수 (두 스냅샷) |
|---|---|---|---|
| 676 | 31~37초 | 47~60초 | 35~39 |
| 1,278 | 33~38초 | **74~89초** | 42~55 |
| 2,712 | 50~**63**초 | 74~89초 | 67~99 |
| 5,340 | 54~**69**초 | 79~88초 | 97~139 |

- **지연의 정체는 출력량**: 지연이 입력 길이가 아니라 진술 수와 같이 움직인다(같은 스냅샷 안에서 139개=69초, 71개=50초). 분할의 본질은 "한 콜의 출력량을 묶는 것"이다.
- **일관성은 길이가 길수록 무너진다**: 진술 수 분산이 ~1,278토큰에서 ±3~13%, 2,712토큰부터 ±16~18%. 절단 원칙 4("같은 글은 같은 모양으로")가 긴 맥락에서 실제로 흔들린다.
- **제공자 속도는 통제 변수가 아니다**: 같은 입력·같은 설정이 시간대에 따라 1.5~2.3배 출렁인다(1,278토큰이 38초 ↔ 89초). 출력량은 분할이 묶을 수 있지만, 이 출렁임은 분할로 못 막는다 — 최소 급간(676토큰)조차 느린 시간대엔 60초를 스쳤다. **출렁임을 받는 자리는 타임아웃이다** (2장).
- 현실 최대 입력은 ~25,000토큰(2시간 회의 전사)으로 추정 — gpt-5 입력 한도(272k)의 1/10이라 입력 컨텍스트는 제약이 아니다.

## 2. 임계선 1,500토큰 + 추출 타임아웃 120초 — 역할 분담

```
토큰 수(body) ≤ 1,500  →  현행 1콜 그대로 (이 문서의 어떤 것도 발동 안 함)
토큰 수(body) > 1,500  →  분할 경로 (3장~5장)
```

곡선이 가르쳐준 역할 분담: **분할(임계선)은 출력량 — 평균 지연과 절단 일관성 — 을 묶고, 타임아웃은 제공자 출렁임을 흡수한다.** 어느 한쪽으로 둘 다를 풀 수 없다.

- **단위는 토큰** (js-tiktoken, `o200k_base` 고정). nema는 글로벌 서비스라 글자 수는 언어별 토큰 비율 차이(한국어 자당 ~0.7 vs 영어 ~0.25)를 못 받는다 — 토큰이면 임계선·곡선이 언어 무관. 인코딩 고정이라 결정적이고, 측정은 로컬 동기 연산(수천 자에 밀리초)이라 워커 경로에 부담 없다.
- **임계선 1,500의 근거는 출력량과 일관성**: 호출당 진술을 ~45개 안쪽으로 묶는 값(1,278토큰 실측 42~55개에서 외삽 — 실제 1,500토큰 청크는 다소 클 수 있다). 일관성 안정 영역(676토큰은 두 스냅샷 모두 분산 ±5% 이내)과 붕괴 영역(2,712토큰부터 ±16%+) 사이이며, 6장 A/B가 이 값에서 일관성이 실제로 회복되는지 검증한다 — 미달이면 하향 조정.
- **추출 타임아웃은 60→120초** (`EXTRACTION_TIMEOUT_MS`, lease도 90→150초 동반 — `extraction_lease_covers_slow_provider` 마이그레이션). 60초는 느린 시간대의 *정상* 호출(1,278토큰 74~89초)을 죽은 호출로 오판해 끊는다 — 재시도해도 같은 느린 시간대라 또 느리고, 버리는 것만 는다. 타임아웃의 일은 행 걸린 호출 회수 하나뿐이고, 비동기 파이프에서 높게 잡는 오차(복구 몇 분 지연)는 낮게 잡는 오차(정상 작업 폐기)보다 싸다.
- **임계선 = 청크 목표 크기.** 분할 시 모든 청크가 임계선 이하가 되게 가른다. 보정 완료된 짧은 글 경로를 한 글자도 안 건드리는 게 이 설계의 제1 원칙.

## 3. 분할 — 경계 강등식 균등 패킹 (결정적, LLM 0콜)

절단("하나의 '왜'")은 LLM의 일이고, 분할기의 책임은 그보다 약하다 — **'왜' 하나가 걸쳐 있을 확률이 낮은 경계를 고르는 것**. 문단·문장 경계가 그 역할을 한다.

1. 청크 수 = ⌈전체 토큰 ÷ 1,500⌉, 목표 크기 = 전체 ÷ 청크 수 (균등 분배 — 꼬투리 청크 방지, 청크 간 모양 일관성).
2. 각 목표 지점 근처에서 경계를 고른다. 우선순위: **빈 줄(문단) → 줄바꿈 → 문장 종결 부호** — 좋은 경계가 목표 지점 근처에 없으면 한 단계씩 강등. 최후 수단(경계 전무)만 토큰 위치 하드 컷.
3. 같은 입력 → 항상 같은 분할 (무작위성 없음). 절단 원칙 4의 분할기 버전이고, 청크 결과 캐싱(7장)의 키 안정성도 이 결정성이 보장한다.

의미 경계 분할(임베딩 변화점·분할 LLM 선행 콜)은 채택하지 않는다 — 비용·지연·보정 대상이 늘고 결정성이 죽는데, 얻는 건 잔여 경계 사례 약간의 감소다(그 잔여는 4장이 받는다). 단, **분할기는 "텍스트 → 경계 목록"의 순수 함수로 격리한다** — 검증(6장)에서 경계 품질 미달이 드러나면 이 함수만 교체하는 퇴로.

## 4. 경계 처리 — 양방향 읽기 전용 문맥 동봉 (겹침 없음)

청크 경계의 두 위험 — 경계에 걸친 '왜', 청크 밖을 가리키는 대명사·생략 — 은 **원문 이웃 구간을 읽기 전용 문맥으로 동봉**해서 받는다:

```
<context_before>앞 청크의 꼬리 ~200토큰 (문장 경계 정렬)</context_before>
<note>청크 본문</note>
<context_after>다음 청크의 머리 ~200토큰 (문장 경계 정렬)</context_after>
```

프롬프트 규칙: context는 대명사·생략 해소와 의미 파악에만 쓰고, **진술은 note에서만 추출한다.**

- **겹침 윈도우(앞 청크 꼬리를 본문에 중복 포함)는 채택하지 않는다** — 겹친 구간이 양쪽 콜에서 추출돼 중복 진술 dedup이라는 새 보정 문제가 생긴다. 읽기 전용 동봉은 추출 대상 구간이 청크끼리 한 글자도 안 겹쳐 **중복이 원천적으로 없다** (Chroma의 청킹 평가에서도 겹침은 중복 비용으로 일관되게 감점). 청크 간 중복 진술 처리 단계는 두지 않는다.
- **앞 청크 요약 전달도 채택하지 않는다** — 요약 생성 콜 추가, "요약·창작 금지" 원칙과 긴장, 그리고 앞 콜 결과 의존으로 청크 직렬화를 강제한다(17청크면 ~10분).
- **뒤쪽 문맥도 동봉하는 이유**: 경계 직후의 번복("…X로 가기로 했다" ‖ "아니다, 역시 Y다")을 앞 청크가 못 보면 한 source 안에 모순 진술 쌍이 생긴다. 1콜이면 모델이 최종 입장으로 정리하던 것 — 뒤 문맥이 그 시야를 복원한다. Claimify(장문 주장 추출, ACL 2025)도 문장 처리에 앞 p문장 + 뒤 f문장 양방향 문맥을 쓴다.
- 문맥은 전부 **원문에서** 오므로 분할 시점에 확정 — 결정적이고, 청크 병렬(5장)과 양립한다.
- 한계: 문맥 창이 닿는 건 이웃 구간뿐이라 **장거리 참조**(글 첫머리 주제를 한참 뒤 대명사로 받기, 글 전체에 깔린 생략 주어)는 못 푼다. 빈도를 검증(6장의 자기완결 실패 분석)으로 재고, 유의미하면 같은 자리에 글 도입부 동봉을 추가한다 — 방식 교체가 아니라 동봉량 조정.
- 창 크기 200토큰은 보정 대상 상수 (시작값).

## 5. 실행과 계약 — 분할은 워커 안에서만 보인다

DB·RPC·마이그레이션 변경 0. 수정은 워커 `processSource` 안쪽뿐이다.

1. **청크 병렬 추출, 동시성 상한 안에서.** 모든 청크 입력이 분할 시점에 확정돼 있어(4장) 병렬 가능. 2시간 전사(17청크)가 직렬 17콜 연쇄 → 병렬은 동시성 3 기준 6웨이브 — 빠른 시간대 ~4분, 직렬 대비 약 1/3. 동시 LLM 콜 상한은 한 군데서 관리한다 — 평가에서 동시 4 초과 시 제공자 타임아웃이 관찰된 전례. 청크 동시성 3으로 시작.
2. **index 전역 연결.** 청크 순번대로 결과 배열을 이어붙인 뒤 index를 0부터 재부여. 청크가 원문 순서로 잘렸고 각 콜 출력이 청크 내 등장 순서이므로, 연결 순서 = 원문 전체 등장 순서 — `locator {"index": n}` 계약 유지.
3. **apply는 지금처럼 1회.** 모든 청크가 성공해야 `apply_ingestion_changeset` 호출 — 원자성 유지, "절반만 저장된 source"라는 중간 상태를 만들지 않는다. 전부 노이즈(진술 0개)면 기존처럼 `complete_source_extraction`만.
4. **부분 실패 = source 전체 실패.** 청크 콜은 콜 레벨 재시도(2~3회)로 먼저 방어하고, 그래도 실패하면 성공분을 버리고 기존 재시도 경로(`increment_source_extraction_retry`, 선형 backoff)를 탄다. 버려지는 비용은 LLM 콜 십몇 개 + 지연 1~2분 — 비동기 파이프라 사용자 체감은 "처리 중"이 길어질 뿐.

**추출 범위는 분할과 무관하게 전부다(요약 선행 없음).** 요약 후 추출은 "뭐가 중요한가"를 추출 전에 결정해 떨어진 진술이 검색에서 영구 유실된다 — 기억 제품의 최악 실패 모드("분명히 말했는데 왜 검색이 안 되지")이고, 절단 원칙 3·원문 무손실 박제와 정면 충돌. 장문의 진술 100개+가 주는 인지 부담은 화면 층의 문제다(추출→요약 방향의 표현은 언제든 더할 수 있다 — 잃는 게 없다).

## 6. 검증 — 네 층 (eval-design 하니스 위에서)

검증할 주장: ① 분할해도 절단 품질이 안 깨진다 ② 일관성·지연이 안정 영역으로 돌아온다 ③ 경계에서 진술이 조용히 빠지지 않는다 ④ 짧은 글 경로는 무영향.

| 층 | 방법 | 합격 기준 |
|---|---|---|
| 분할 전후 A/B | 장문 시드 4급간을 1콜 vs 분할 경로로 — 일관성(쌍대 F1)·품질 3차원·지연 | 일관성 ≥0.85 회복(현 장문 1콜 ±16~18% 분산의 해소가 분할의 존재 이유), 품질 3차원 1콜 대비 하락 없음, 청크당 지연이 타임아웃(120초) 안쪽 안정 |
| **경계 창 요소 포괄성** | 청크 경계 앞뒤 ±200토큰 구간마다 LLM이 원자적 정보 단위를 열거 → 분할 경로 추출 결과가 각 단위를 덮는지 심판 판정 (Claimify의 element-level coverage 방식) | 경계 창 누락이 비경계 구간과 동률 — **누락 검출 전담**: 일관성·품질 심판은 추출된 진술만 보므로 매 실행 똑같이 빠지는 진술을 못 잡는다 |
| 상한 실주행 | ~15,000토큰 시드(1시간 전사급) 추가, verify-e2e에 장문 케이스 — 10청크 → 한 changeset | index가 원문 순서, 원자 적용, 전체 처리 수 분 안쪽 |
| 무영향 회귀 | 기존 run-extraction 풀 측정 재실행 + 분할기 단위 테스트(임계선 미만 무발동·경계 강등·균등 분배·결정성) | 기존 시드(전부 임계선 미만) 숫자 동일 |

- 장문 골든은 만들지 않는다 — 진술 100개+ 골든의 사람 확정은 비현실적("절단 기준의 주인은 사람"). 위 측정은 전부 골든 없이 돈다(일관성·품질 3차원·요소 포괄성 모두 reference-free, eval-design 결정 #2·#5의 심판 + 표본 검사 체계 그대로).
- 도구는 새 러너 대신 `run-length-curve.ts` 확장(분할 경로 비교 모드). 결과는 measurement-log에 기록.
- 자기완결 실패 사례는 경계 부근 여부를 표시해 분석한다 — 장거리 참조 빈도(4장의 문맥 확장 여부)의 재료.

## 7. 후속 / 미결

- **청크 결과 캐싱** — 재시도 시 성공 청크 재활용. 트리거: 장문 source가 재시도 상한을 소진하고 `failed`로 떨어지는 패턴이 Sentry에 보일 때, 또는 청크 수의 자릿수가 바뀔 때(입력 상한 확대). 결정적 분할(3장)이 `(source_id, 청크 순번, 청크 해시)` 캐시 키의 안정성을 이미 보장한다.
- **문맥 창 확장** — 장거리 참조 실패가 유의미하면 글 도입부 동봉 추가 (4장).
- **분할기 교체** — 경계 품질 미달 시 의미 경계 분할로 (3장의 퇴로).
- **입력 길이 상한** — `create_source.p_body`는 현재 무제한. 거부 정책·과금 경계는 운영 데이터 보고.
- **워커 증설 전 lease 정합** — 추출 lease(150초)는 *호출 1회*를 덮는 값이다. 분할 경로의 한 시도는 청크 웨이브 × 호출 상한(예: 17청크 = 6웨이브 → 최악 12분)이라, 워커를 2인스턴스 이상으로 늘리기 전에 lease가 시도 전체를 덮도록 손봐야 한다(청크 완료마다 `last_extraction_attempt` 갱신하는 heartbeat, 또는 분할용 lease 상향). 단일 워커에선 문제없다 — 같은 워커는 in-flight 배치를 기다린 뒤 재인출한다.
- **임계선·창 크기 재보정** — 6장 측정이 쌓이면. 모델 교체 시 곡선 재측정 필수(지연 특성이 모델 종속).
