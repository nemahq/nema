# 시간 질의 설계 — 진술 엔진 (save-engine-v2)

> 시간 질의("이번 주 마감", "지난주에 뭐 했지")를 의미검색에서 떼어내 구조화된 시간 경로로 재배치하는 설계. [`retrieval-design.md`](retrieval-design.md)이 깐 꺼내기 흐름 위에 서고, [`schema-design.md`](schema-design.md)의 `statements` 위에 기한 필드를 더한다. NEM-168 1차 측정(검색 난도↑, 측정 #9)이 드러낸 "임베딩에 잘못 태운 시간 질의"의 치료.
>
> 짝 문서: [`retrieval-design.md`](retrieval-design.md)(꺼내기 — 시간 경로가 갈라져 나오는 곳), [`ingestion-design.md`](ingestion-design.md)(넣기 — 기한 추출이 끼는 곳).

---

## 0. 이 문서가 정하는 것 / 정하지 않는 것

- **정한다**: 두 종류 시간(생성 시각 / 내용 속 기한)의 처리 경로, 시간 표현의 구조화 토큰 문법, 토큰→날짜 범위 환산기(resolver), 질의 라우팅(구조화 레이어), 실행 흐름 3경로, 기한 저장 스키마, eval 재구성.
- **정하지 않는다**: 의미검색 자체의 튜닝(negation·재랭킹 — NEM-168 ②·⑩의 몫), 질의→토큰 LLM 정확도 골든(④ 자동 scoping과 같은 구조화 레이어를 채점하므로 그쪽과 공유), 빈도 낮은 grain 꼬리(상하반기·연말·주말 — 우아한 강등), 구조화 레이어의 모델·프롬프트 최종 확정(데이터로 보정), 화면 설계.

---

## 1. 왜 — 시간은 의미검색 소관이 아니다

측정 #9(검색 난도↑)에서 코퍼스를 골든 39개 → 6,521개로 키우자 temporal 축 recall이 **0.834 → 0.5 → 0.167**로 무너졌다. 다른 축(paraphrase·proper-noun 등)은 0.7~1.0을 유지했다.

임베딩은 **의미 유사도**지 **날짜 산술**이 아니다. "다음주"와 "이번 주"는 임베딩 공간에서 가까워 서로 끼어들고, "이번 주 안에 마감인가"라는 질의를 진술 내용과의 의미 거리로 푸는 한 날짜 비교는 일어나지 않는다. 코퍼스가 빽빽해질수록 이 약점이 그대로 드러난다.

그래서 고칠 대상은 검색 엔진이 아니다. **시간 일을 의미검색에서 떼어 구조화된 경로(날짜 필터)로 넘긴다.** 이건 엔진 결함 수정이 아니라 책임의 재배치다.

## 2. 두 종류의 시간 — 처리가 다르다

| 종류 | 예 | 출처 | 현황 |
|---|---|---|---|
| **생성 시각** | "지난주에 뭐 했지" | `sources.created_at` | 이미 있음 — 컬럼·인덱스(`idx_sources_space_created`) 존재. 필터만 얹으면 됨 |
| **내용 속 기한** | "이번 주 마감" | 진술 *내용 안*의 날짜 표현 | 신규 — 추출·정규화·저장·필터 전부 필요 |

비대칭이 핵심이다. 생성 시각은 거의 공짜(필터 하나), 내용 속 기한은 파이프라인이 통째로 새로 든다.

생성 시각은 **사용자가 글을 쓴 때**라 `sources.created_at`을 쓴다 — `statements.created_at`은 엔진이 추출을 끝낸 때라 사용자 의도("지난주에 적은 것")와 어긋난다.

## 3. 토큰 문법 — 시간 표현의 구조화

시간 표현을 아래 토큰으로 정규화한다. 표현의 다양성(같은 뜻을 100가지로 쓰는 것)은 LLM이 흡수하고, 토큰은 **의미의 모양**만 담는다. 모양 집합은 `.local/tiro-samples` 387개 회의 요약에서 실제 빈도로 검증해 확정했다(상상이나 eval 질의가 아니라 데이터로).

```
time: {
  field: "created" | "due",          // 생성 시각이냐 내용 기한이냐
  boundary: "within" | "by",         // within=그 기간 전체, by=그 시점 이하([기준, 점])
  anchor:
    | { kind: "relative", grain: "day" | "week" | "month" | "quarter", offset: number }
    | { kind: "weekday",  day: "mon".."sun", scope: "this" | "next" }
    | { kind: "absolute", date: "YYYY-MM-DD" }
}
```

- **마감은 별개 종류가 아니라 경계 플래그다.** tiro 데이터에서 "까지/내"(마감류)가 1,444회로 1위였는데, 그것이 *모든* 앵커에 붙었다("이번 주 화요일**까지**", "2월 14일**까지**", "연말**까지**"). 그래서 boundary를 앵커와 따로 두고, 어느 앵커에나 얹는다.
- **relative**: 이번 주=`{week,0}`, 다음주=`{week,1}`, 지난주=`{week,-1}`, 모레=`{day,2}`, 이달=`{month,0}`, 이번 분기=`{quarter,0}`. offset은 `±1`에 갇히지 않는다(모레=+2, "N일 뒤" 임의 N).
- **weekday**: "금요일까지"=`{fri, this}`. 요일은 grain으로 표현 못 한다 — 오늘 요일을 알아야 +N 환산이 되는데 그건 LLM에 맡기지 않을 날짜 산술이다. resolver가 기준일에서 계산한다.
- **absolute**: "2월 14일"=`{2026-02-14}`. tiro에서 절대 날짜가 353회(5위)로 컸다. LLM은 날짜를 그대로 옮기고(산술 없음), 연도만 기준 시각으로 보정한다.

### 범위 결정 — v1에 넣는 것 / 우아한 강등

빈도 절벽이 분기(171회)와 상하반기(46회) 사이에 있다. v1은 **day/week/month/quarter + weekday + absolute**까지만 담는다. 상하반기·연말·주말은 grain·경계 로직을 따로 비틀어야 하는데 빈도가 낮아 손익이 안 맞는다.

토큰으로 못 옮기는 시간 표현은 **의미검색으로 강등**한다(6장 ③). 강등은 오늘과 같은 동작이라 **절대 오늘보다 나빠지지 않는다.** 데이터로 꼬리가 아픈 게 입증되면 그때 grain을 더한다.

## 4. resolver — 토큰 → 날짜 범위

resolver는 **토큰 + 기준 시각**을 받아 실행 필터 `{ from, to }`(한쪽 `null`이면 열린 범위)로 환산하는 순수 함수다. LLM이 없고 결정적이라 단위 테스트로 정확성을 못 박는다 — 날짜 산술(주 경계·요일 환산·연도 보정)이 버그가 사는 곳이다.

대칭이 핵심이다. **같은 토큰 문법·같은 resolver를 두 곳이 기준 시각만 바꿔 쓴다:**

- **질의 파싱**: 토큰 + `now` → `{from, to}` (검색 필터)
- **기한 추출**: 토큰 + `sources.created_at` → 구체 날짜 (저장값, 7장)

| boundary × anchor | from | to |
|---|---|---|
| within + relative/weekday | 그 기간 시작 | 그 기간 끝 |
| within + absolute(단일일) | 그 날 0시 | 그 날 끝 |
| by + 무엇이든 | 기준 시각(또는 `null`) | 그 점의 끝 |

기준 시각·주 시작 규칙(월요일 가정)은 9장 미결로 둔다.

## 5. 질의 라우팅 — 항상 켜는 구조화 레이어

질의를 그대로 임베딩하기 전에, **자연어 질의를 구조화 쿼리로 바꾸는 레이어**를 둔다.

```
질의(자연어) → 구조화 레이어 → { semantic: string | null, time: <3장 토큰> | null, /* topic 자리 */ }
```

- **레이어는 시간만의 것이 아니다.** ④(자동 scoping)도 "질의 → topic 먼저 고르기"라 같은 레이어가 필요하다 — 시간·주제 둘 다 쓸 공용 입구다. 그래서 temporal 전용 정규식 땜빵이 아니라 레이어를 제대로 깐다. `topic` 자리는 비워 두고 ④가 채운다([retrieval-design](retrieval-design.md)의 "확장 가능한 자리" 패턴 그대로).
- **항상 켜되 싸게.** [retrieval-design 2장](retrieval-design.md)은 검색 경로에 LLM을 빼면서 "miss 패턴이 입증되면 되살린다"고 보정 레버를 남겼다 — temporal이 바로 그 입증된 패턴이다. 작은 모델(flash)·짧은 프롬프트·캐시로 한 콜을 싸게 유지한다. 2단 게이트(규칙으로 시간 낌새 있을 때만 LLM)는 로직을 둘로 쪼개고 게이트가 놓치면 우리가 고치려던 "표현 누락"이 그대로 돌아오므로, 단일 레이어로 깔고 **지연·비용을 재서** 아프면 그때 규칙 fast-path를 얹는다.
- **우아한 강등**: 레이어가 시간을 못 떼면 `time: null`로 두고 의미검색만 — 오늘 동작.

## 6. 실행 흐름 — 세 경로

구조화 결과에 따라 갈라진다.

```
질의 → 구조화 레이어 → { semantic, time }

① time만 (semantic = null)   — "다음주 마감인 거 있나"
     → Qdrant 안 탄다. Postgres만:
       WHERE (due_date | source.created_at) ∈ [from, to]

② semantic + time            — "다음주 백엔드 관련 마감"
     → Qdrant 의미검색 → 그 후보를 시간으로 필터 (필터 오버레이)

③ time 없음                  — "토스 결정한 이유"
     → 지금 그대로 의미검색
```

- **순수 시간 질의(①)는 임베딩을 아예 안 탄다.** 이것이 재배치의 본질 — 시간 일을 의미검색에서 완전히 떼어 Postgres 날짜 필터로 넘긴다.
- **②는 시간을 의미검색 위에 거르개로 얹는다.** "시간이냐 의미냐"의 양자택일(fork)이 아니라, 시간 조건을 떼어내 필터로 쓰는 오버레이다. 의미 나머지가 있으면 평소대로 뜻으로 찾고, 시간은 그 결과를 좁힌다.
- `field`가 경로 안에서 필터 컬럼을 가른다: `due` → `statements.due_date`, `created` → `sources.created_at`.

## 7. 저장 스키마 — 내용 속 기한

내용 속 기한은 **글 쓴 시점 기준**이다. "금요일까지"는 *작성 시점*의 금요일이지 검색 시점의 금요일이 아니다 — 3주 전 메모의 "금요일"을 쿼리 때 풀면 틀린다. 그래서 **추출·저장 시점에 정규화해 박는다**, `sources.created_at`을 기준 시각으로(4장 resolver 재사용).

- **컬럼**: `statements.due_date date` 신설 + 인덱스. 기한은 날 단위라 `date`(시각 불필요).
- **단일 날짜로 저장**(범위 아님). 기한은 본질이 "언제까지"라 한 점이다. "이번 주 안에 마감"도 마감으로 보면 점(그 주 끝)으로 수렴한다 — 범위 컬럼 둘은 쿼리 이득 없이 자리만 늘린다. 쿼리 쪽에서 `due_date BETWEEN from AND to`로 거르면 "이번 주 마감"(=[월,일]) 질의가 금요일 기한을 자연히 잡는다.
- **파이프라인**: 추출 LLM이 기한 있는 진술에서 **기한 토큰**(3장)도 함께 뱉고 → resolver가 토큰 + `sources.created_at` → `due_date`로 저장. 기한 없는 진술은 `null`.

추출 프롬프트는 지금 "기한을 task에서 분리하지 말라"(절단 규칙 1)고만 한다. 기한을 *별도 구조 필드로* 뽑으려면 [ingestion-design](ingestion-design.md)과 추출 프롬프트까지 함께 고쳐야 한다. NEM-168 ②(추출 누락)·①(골든 정비)과 파일이 겹치는 지점이라 충돌을 주의한다.

## 8. eval 재구성 — 의미검색에서 temporal 빼기

측정 #9는 temporal을 의미검색 채점에 넣어 "임베딩이 책임 없는 것"으로 점수를 깎고 있었다. 이를 두 부분으로 가른다.

### A. 의미검색 eval에서 제거 (즉시)

- `seed-data.ts`의 `QueryFailureAxis`에서 `"temporal"` 제거.
- 시간 질의 q12("다음주 예정")·q13("이번 주 마감")을 `SEED_QUERIES`(의미검색 코퍼스)에서 빼낸다.
- `run-retrieval.ts`·`run-retrieval-dense.ts`의 byAxis 집계에서 temporal이 자연히 빠진다.
- → dense/sparse recall이 더는 시간 질의로 깎이지 않는다. 의미검색 점수가 정직해진다.

### B. q12·q13의 새 집 = 시간 경로 eval

재배치의 "옮겨감"이다. 새 경로를 시험한다.

- **resolver 단위 테스트** (필수): 토큰 + 기준 시각 → `{from, to}`. 날짜 산술이 버그 사는 곳이라 순수 단위 테스트로 못 박는다(주 경계·요일·연도·boundary).
- **시간 경로 정확도 eval**: q12·q13 같은 (질의 → 기대 진술) 쌍. 골든 진술에 **`due_date` 라벨**이 필요하고(braindump "금요일까지" → 실제 날짜), 고정 `now`·고정 코퍼스 날짜로 채점한다.

### ③의 범위

**A + resolver 단위 테스트**까지 ③에서 짓는다. resolver가 정확성의 핵심(날짜 계산)이고 단위 테스트로 충분히 잠긴다.

**LLM 정확도 eval(질의→토큰, 내용→기한토큰 골든)은 ④와 공유한다.** ④(자동 scoping)도 같은 구조화 레이어(질의→구조화)를 채점해야 하므로, temporal만 위해 지금 따로 골든을 깔면 ④에서 다시 손본다. 그 골든은 ④와 한 번에 만든다.

## 9. 구현 순서 / 미결

### 순서

1. **토큰 + resolver** (순수 함수, 단위 테스트) — 의존 없는 뿌리.
2. **eval 재구성 A** — temporal을 의미검색에서 빼기(가볍고 독립적).
3. **스키마** — `statements.due_date` 컬럼·인덱스 마이그레이션.
4. **추출 파이프라인** — 기한 토큰 출력 + write-time 정규화(①②와 충돌 주의).
5. **구조화 레이어 + 라우팅** — 실행 흐름 3경로 배선.
6. **시간 경로 정확도 eval B** — 골든 `due_date` 라벨.

### 미결 (구현 때 데이터로 정함)

- **`by` 경계의 from**: 마감 질의("이번 주 마감")에서 `from`을 `now`로 둘지 `null`(과거 마감까지 포함)로 둘지 — 지난 기한을 결과에 넣을지의 제품 판단.
- **주 시작 규칙**: "이번 주"의 경계(월요일 시작 가정). resolver 상수.
- **grain 꼬리 트리거**: 상하반기·연말·주말이 실데이터에서 아픈 게 입증되면 grain 추가(우아한 강등의 재오픈 조건).
- **구조화 레이어 모델·프롬프트·캐시**: 지연·비용을 재서 확정. 단일 레이어가 아프면 규칙 fast-path.
