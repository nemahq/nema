# 콘텐츠 입구 MCP 레이어(Track B): 설계 청사진

> 외부 AI(Claude Code 등)가 nema에 초안을 직접 올릴 수 있게 해주는 연결 통로를 만든다. 이번 작업은 올릴 수 있는 기능(도구)을 다 만드는 것이 아니라, 도구가 올라탈 기반(MCP 서버, 인증, 백엔드 호출, 배포)을 먼저 세우는 것이다. 읽기 도구 하나(`list_topics`)로 그 기반이 끝까지 동작하는지 확인하고, 배포 경로를 production까지 미리 깔아 둔다. 그러면 이후에는 도구 하나를 정의만 추가해도 바로 MCP로 동작한다.

대상: NEM-157 콘텐츠 입구의 Track B(외부 입구). 형제 문서 `content-intake-design.md`의 §5.3(MCP 경계)·§6.2(외부 입구 흐름)를 따른다.

이 문서는 구현 청사진이다. 코드는 짜지 않고 설계 결정만 확정한다.

---

## 0. 배경 (이 문서만 읽어도 이해되도록)

nema는 사람이 맥락("왜")을 쌓아 두고 다시 꺼내 쓰는 기억 도구다. "콘텐츠 입구"는 그 맥락을 처음 집어넣는 곳이고, 입구가 둘 있다.

- 앱 입구(Track A): 사람이 nema 앱 안에서 직접 글을 써 넣는다.
- 외부 입구(Track B, 이 문서): 외부 AI가 정리한 결론을 MCP로 올린다.

두 입구 모두, 올라온 글은 곧바로 기억이 되지 않는다. 먼저 "초안" 상태로 대기한다. 사람이 그 초안을 확인하고 확정해야 비로소 기억으로 저장된다. 이 확정 단계를 "확정 게이트"라 부르며, 사람만 통과시킬 수 있다(외부 AI는 초안만 올리고 확정은 못 한다). 이것이 nema의 원칙인 "사람 주권"이다. 사람의 통제권은 입력이 아니라 확정 시점에 있다.

처음 보는 사람을 위한 용어 정리:

- MCP(Model Context Protocol): AI 도구(Claude Code, ChatGPT 등)가 외부 기능을 표준 방식으로 호출하게 해주는 규약. nema가 "MCP 서버"를 열어 두면, MCP를 지원하는 AI들이 nema의 기능을 도구처럼 부를 수 있다.
- tRPC: nema 프론트엔드와 백엔드(`apps/server`)를 잇는 API 호출 방식. 타입이 양쪽에서 맞춰져 컴파일 단계에서 오류를 잡아 준다.
- Supabase: nema가 쓰는 데이터베이스 + 사용자 인증 서비스.
- RLS(Row Level Security): 데이터베이스가 "각 사용자는 자기 데이터만 본다"를 강제하는 기능. nema는 이미 이걸로 사용자별 데이터를 분리한다.
- Track 0: 두 입구가 공유하는 토대. 초안 테이블, 주제 목록, 확정 처리 함수, tRPC 계약이 여기 들어 있다. 이미 staging 브랜치에 병합되어 고정됐고, 이 문서는 그 위에 얹기만 한다(아래 §1 참조).

## 1. 무엇을 만드나

이번에 새로 만드는 것은 "외부 AI가 nema에 닿는 경로" 하나다. 구체적으로 네 가지를 차례로 세운다.

1. 외부 AI가 접속할 원격 MCP 서버를 새 앱 `apps/mcp`로 만든다.
2. 그 서버가 사용자를 로그인시켜, "그 사용자 본인"으로 nema 백엔드에 접근하게 한다.
3. 읽기 도구 `list_topics` 하나를 붙여, 위 경로가 처음부터 끝까지 실제로 동작하는지 확인한다.
4. 이 경로를 로컬에서 production까지 배포 흐름에 얹어 둔다. 그러면 다음 도구는 정의만 추가하면 동작한다.

기존 엔진(올라온 글을 진술로 쪼개고 관계를 잇는 처리)과 Track 0 계약(테이블, 함수, tRPC 시그니처)은 한 줄도 고치지 않는다. 전부 새로 더하기만 한다.

## 2. 합의된 설계 결정 (요약)

**범위 (도구가 아니라 기반을 먼저)**
- 이번에는 읽기 도구 `list_topics` 하나만 노출한다. 글을 올리는 쓰기 도구(`upload_draft`)는 다음 작업으로 미룬다.
- "완료"의 기준: 새 도구를 추가할 때 도구 정의만 작성하면 되고, 통신·인증·배포·CI는 이미 production에 준비돼 있는 상태.
- 이번 확인 대상은 "올린 초안이 DB에 저장되는가"(쓰기)가 아니라 "서버가 토큰으로 사용자를 알아내, 그 사용자의 데이터를 제대로 읽어 오는가"(읽기)다. 데이터를 바꾸지 않으므로 가장 안전한 첫 확인이다.

**통신 방식**
- 원격 Streamable HTTP를 쓴다. 과거 방식인 SSE는 더 이상 권장되지 않아 쓰지 않는다.
- 첫 확인 대상 AI는 Claude Code다(원격 Streamable HTTP를 기본 지원). 같은 서버를 나중에 ChatGPT, Claude 등 다른 AI로 넓힐 수 있다.

**위치 (어디에 두나)**
- 모노레포 안에 `apps/mcp`라는 독립 앱으로 둔다. 별도 저장소로 분리하지 않는다.
- 이유: 이 서버는 공용 스키마(`@nema-io/shared`)와 백엔드 타입(`AppRouter`)을 그대로 가져다 쓴다. 저장소를 분리하면 그 타입들을 따로 배포하거나 복제해야 하고, 타입이 자동으로 맞춰지는 이점을 잃는다.

**백엔드 호출 방식**
- nema 백엔드(`apps/server`)를 tRPC HTTP 클라이언트로 호출한다. 백엔드 함수나 DB 함수를 직접 부르지 않는다.
- 백엔드 타입(`AppRouter`)을 가져와 호출 입출력 타입이 자동으로 맞춰진다. 또한 이미 있는 로그인 검증(`protectedProcedure`)과 RLS를 그대로 재사용하므로, MCP 서버가 인증 로직을 새로 만들 필요가 없다.

**인증 (Supabase OAuth)**
- 인증은 OAuth로 한다. 직접 만드는 개인 토큰(PAT) 방식은 쓰지 않는다(근거는 §3).
- OAuth는 사용자가 브라우저로 로그인하면 시스템이 토큰을 발급·관리해 주는 표준 방식이다. Supabase가 2025년 11월에 공개한 OAuth 서버 기능이 MCP 규약을 그대로 만족한다. 토큰 발급은 Supabase가 맡고, 우리 MCP 서버는 받은 토큰이 유효한지 검증만 한다(이 검증은 기존 백엔드가 이미 한다).
- staging에서는 Dynamic Client Registration(DCR)을 켜서 호스트(Claude Code 등)가 자기를 자동 등록하게 둔다. DCR은 원격 MCP의 표준 등록 경로이고, 단일 사용자 staging에서는 노출 위험이 낮다. production은 그 단계에서 따로 정한다(§6).
- `openid` 항목(로그인한 사람의 신원 정보를 담은 별도 토큰)은 요청하지 않는다. 우리에게 필요한 것은 접근용 토큰뿐이고, 그 토큰은 기존 검증 경로(서버가 Supabase에 토큰 유효성을 물어보는 `auth.getUser` 호출)가 서명 방식과 무관하게 그대로 받아 주므로, production의 기존 인증을 건드리지 않는다.

**구현 도구**
- 공식 라이브러리 `@modelcontextprotocol/sdk`(TypeScript)를 쓴다. 도구가 하나뿐이라 더 추상화된 프레임워크의 이점이 거의 없고, 우리가 의존하는 표준(OAuth 검증, Streamable HTTP)을 가장 먼저 반영하는 쪽이 공식 라이브러리다.

**배포 범위 (production까지)**
- 로컬에서 staging 백엔드로 동작을 확인한 뒤, staging 병합 시 자동 배포되고 태그를 찍으면 production까지 배포되도록 경로를 세운다.
- production에 Supabase OAuth(공개 베타) 기능을 켜는 것을 받아들인다. 그에 따른 위험과 완화책은 §6에 정리했다.

**사람 주권 (확정 금지)**
- 이번에는 읽기 도구만 있으므로 확정 기능(`draft.confirm`)을 아예 노출하지 않는다. "MCP는 확정하지 않는다"는 원칙이 별도 장치 없이 자연히 지켜진다.

## 3. 인증을 PAT에서 OAuth로 바꾼 이유

처음에는 "OAuth는 무겁고, 직접 만드는 토큰(PAT)이 가볍다"고 보고 PAT를 택했다. 그런데 실제 사실을 확인해 보니 그 전제가 틀렸다.

- Supabase OAuth 서버가 OAuth에서 가장 손이 많이 가는 부분(인증 서버 자체, 토큰 발급, 자동 등록, 키 공개)을 대신 처리한다.
- 발급되는 토큰은 평범한 Supabase 토큰이라, 기존 백엔드의 검증 로직(사용자 확인 + RLS)이 손대지 않고 그대로 검증한다.
- 그래서 작업량이 역전된다. PAT는 발급·저장·검증을 우리가 새로 만들어야 하지만, OAuth는 발급을 Supabase가 맡고 우리는 검증만 하면 된다(그 검증도 이미 있다). 수동 발급 코드가 사라지고, 사용자는 브라우저 로그인 한 번으로 끝나 경험도 더 낫다.

결론: 새로 짤 코드가 더 적고, 버리는 작업도 없으며(두 방식 모두 최종 토큰은 Supabase 토큰), 처음부터 최종 형태의 인증으로 간다. 그래서 OAuth를 택했다.

## 4. 동작 흐름 (이번 작업 범위)

```
Claude Code (MCP를 호출하는 AI)
  -> 브라우저로 OAuth 로그인 (Supabase OAuth 서버) -> 접근 토큰(Supabase JWT) 발급
  -> list_topics 도구 호출
       -> apps/mcp: 받은 토큰을 실어 tRPC 클라이언트로 백엔드 호출
            -> apps/server의 topic.list (로그인 검증 + RLS 적용)
                 -> 그 사용자의 주제만 반환
  -> Claude Code에 주제 목록 전달
```

이 한 번의 호출로, 통신(원격 HTTP)·인증(OAuth로 받은 토큰을 사용자/공간으로 풀어내기)·백엔드 호출(tRPC) 세 가지를 데이터 변경 없이 한꺼번에 확인할 수 있다.

다음 도구를 만들 때 따를 공통 형태:

```
도구 = (입력 형식은 @nema-io/shared의 스키마 재사용)
        -> 대응하는 tRPC 함수 호출
        -> 결과 반환
```

다음 작업의 `upload_draft`는 이 형태를 그대로 따라, 새 초안은 `draft.create`(origin='external'), 기존 초안 수정은 `draft.edit`에 연결하면 된다. 확정(`draft.confirm`)은 어떤 경우에도 도구로 노출하지 않는다.

## 5. 만들 것 / 고치지 않을 것

**새 앱 `apps/mcp` (`@nema-io/mcp`)**
- 서버 기본 골격: 공식 라이브러리 + Streamable HTTP 통신.
- 인증: OAuth 검증에 필요한 메타데이터를 공개하고(Supabase를 인증 서버로 가리킴), 들어온 토큰을 검증한다.
- 도구 등록 구조 + `list_topics` 도구(`topic.list`에 연결).
- tRPC 클라이언트 생성 함수: `AppRouter` 타입을 쓰고, 요청마다 사용자 토큰을 실어 보낸다.
- 환경 설정: 환경별 `apps/server` 주소, Supabase OAuth 클라이언트 정보.

**인프라 (한 번 세우면 이후 도구는 기존 배포 흐름을 그대로 탐)**
- Railway 서비스 둘: staging(병합 시 자동 배포) + production(태그 배포).
- Supabase 설정: staging·production 각각 OAuth 서버를 켜고, staging은 DCR을 허용해 호스트가 자기를 등록하게 둔다. redirect URI는 호스트가 등록 시 함께 제출한다.

**고치지 않는 것**
- Track 0 계약 전부(테이블, 함수, tRPC). 기존 엔진 전부. `apps/server`의 인증 로직(그대로 재사용).

## 6. 위험과 수용 판단

**공개 주소가 처음부터 인터넷에 열린다**
- 읽기 전용이지만, 앞단을 OAuth가 막고(로그인한 사용자만 통과) RLS가 그 사용자 데이터로만 좁힌다. 따라서 읽기 전용 공개는 받아들일 수 있다.
- 실제 방어선은 등록 제한이 아니라 동의 화면(사용자가 직접 승인)과 redirect URI 검증이다. staging은 DCR을 켜되 단일 사용자라 노출이 낮고, production으로 갈 때 redirect 패턴 제한·rate limit, 또는 CIMD 같은 가드를 더한다.

**production의 Supabase OAuth가 아직 공개 베타다**
- Supabase가 production 사용을 공식적으로 허용했다.
- 문제가 생겨도 영향 범위가 제한된다. production에서 핵심 경로(토큰 검증 + RLS)는 베타가 아니라 기존 앱이 이미 쓰는 안정된 기능이다. 베타인 부분은 토큰 발급·연결 과정에 한정되므로, 문제의 증상은 "새 연결이 잘 안 됨"이지 "production 인증이 깨지거나 데이터가 새어 나감"이 아니다.
- 베타라서 감수할 점 둘과 대응: (1) 세부 사양이 바뀔 수 있다(예를 들어 토큰 응답 코드 같은 항목이 조정된 적이 있다). 표준 클라이언트와 주요 AI가 알아서 처리하므로 검증하는 우리 쪽 영향은 미미하다. (2) Supabase가 신원 토큰(`openid`)을 발급하려면 프로젝트 서명 방식을 RS256으로 바꿔야 하는데, 신원 토큰이 필요 없어 이 변경을 피한다. 우리의 접근 토큰 검증은 위 `auth.getUser` 호출이라 서명 방식과 무관하므로, 어느 쪽이든 영향받지 않는다.

**production 배포는 확정 게이트(Track A)와 무관하다**
- production에 MCP 서버를 띄우는 것과, 사람이 초안을 확정하는 화면(Track A)이 생기는 것은 서로의 전제 조건이 아니다. 확정 화면이 없어도 올라온 초안은 대기 상태로 쌓일 뿐, 기술적으로 막히지 않는다.
- production 배포가 실제로 필요로 하는 것은 (a) 올릴 가치가 있는 도구(쓰기 도구)와 (b) 인프라(Railway + production OAuth)뿐이다. 이번에는 (a)가 아직 없지만, "기반을 미리 깔아 둔다"는 목표에 따라 인프라를 먼저 세운다.

---

## 7. 만드는 순서

1. `apps/mcp` 기본 골격(공식 라이브러리 + Streamable HTTP) 만들고 연결 확인.
2. tRPC 클라이언트 생성 함수(`AppRouter` 타입, 토큰 실어 보내기).
3. staging Supabase OAuth 서버 켜기(DCR 허용) + 검증 메타데이터 공개.
4. `list_topics` 도구를 `topic.list`에 연결.
5. 로컬에서 Claude Code 연결: 로그인 -> `list_topics` 호출 -> staging의 내 주제가 나오는지 확인.
6. staging 병합(자동 배포) -> 태그 배포로 production 띄우기 + production OAuth 설정.

## 8. 자기 점검

1. 넣기가 가벼운가: 외부 AI가 도구 호출로 바로 닿고, 사람이 손으로 옮길 필요가 없다. 이번에는 읽기뿐이지만 그 가벼움을 향한 기반이 깔린다. 그렇다.
2. 사람 주권을 지키는가: 확정 기능을 도구로 노출하지 않아 MCP는 확정을 할 수 없다. 읽기 전용이라 자연히 지켜진다. 그렇다.
3. 기존 계약을 재사용하는가: Track 0의 테이블·함수·tRPC·인증 로직을 한 줄도 고치지 않고 그 위에 얹는다. 그렇다.
4. 확인할 수 있는가: 내 토큰으로 `list_topics`를 부르면 내 주제만 나온다. 통신·인증·백엔드 호출이 한 번에 확인된다. 그렇다.
