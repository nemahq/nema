# 꺼내기 설계 — 진술 엔진 (save-engine-v2)

> 저장된 진술을 뜻으로 찾아, 흩어진 목록이 아니라 묶음으로 돌려주는 흐름 설계. [`schema-design.md`](schema-design.md)의 스키마·Qdrant payload 계약 위에 선다. 이 문서를 보고 바로 꺼내기 빌드 세션을 띄울 수 있는 수준을 목표로 한다.
>
> 짝 문서: [`ingestion-design.md`](ingestion-design.md) (넣기). 넣기와 꺼내기는 한 고리라 한 세션에서 같이 설계했다.

---

## 0. 이 문서가 정하는 것 / 정하지 않는 것

- **정한다**: 질문이 묶음 응답이 되기까지의 흐름 — 검색어 처리, 벡터 검색의 격리·조회 경로, 묶음 반환 계약(확장 가능한 기준 자리 + 첫 채움), 응답 필드, API 형태.
- **정하지 않는다**: limit·threshold의 실제 값(하니스에서 진술 데이터로 보정), 묶음의 1순위 기준 확정(관계 엔진 설계의 몫), 충돌·지난 것 표시(표식 모양은 [relation-design](relation-design.md) 8장이 확정), 산문 합성(있으면 좋음 — 자리만 안 막음), 화면 설계.

---

## 1. 전체 그림

```
질문 (자연어)
  → 임베딩 (쿼리 모드, 전처리 LLM 없음)
  → Qdrant 검색 (space_id 필터)        … statement_id + score
  → Postgres 조회 (원장 읽기)           … 진술 필드 전부 + locator + 형제 수
  → 묶음으로 조립 (source 단위, 임시 채움)
  → 응답 (단발, 스트리밍 없음)
```

경로에 LLM이 없다. 전체가 임베딩 호출(~100ms) + 저장소 조회라 1초 안쪽의 단발 응답이 된다.

## 2. 질문 → 검색어 — 전처리 없이 그대로 임베딩

질문을 LLM으로 다듬지 않고 그대로 임베딩(쿼리 모드)해서 검색한다.

- v1의 search-query-extractor가 하던 일의 절반(entities 추출)은 수혜 채널(그래프 검색·텍스트 매치)이 사라져 같이 사라졌다. 남은 "쿼리 다듬기"도 필요가 낮아졌다 — v1은 검색 대상이 긴 합성 문서라 다듬을 가치가 컸지만, v2는 진술이 "단독으로 읽히는 한 문장"(ingestion-design 절단 원칙)이라 질문과 진술이 임베딩 공간에서 직접 닿기 좋은 모양이다.
- 검색은 반복하는 동작이라 LLM 한 콜(0.5~1초)이 경로에 박히는 비용이 크다.
- **보정 레버로 남긴다**: v1은 실제로 질문에서 쿼리 1~3개를 뽑아 각각 검색했다(search-query-extractor의 `queries`). 여러 갈래 질문("토스 결정 이유랑 그때 보류한 대안들")엔 그 방식이 유리할 수 있으므로, **신규 도입이 아니라 일단 내렸다가** 하니스에서 miss 패턴이 입증되면 되살린다 — 끼우는 자리가 임베딩 앞 한 곳뿐이라 구조 변경이 없다.

## 3. 벡터 검색 — 격리와 조회 경로

- **격리는 `space_id`**: 내가 멤버인 Space 목록을 Postgres(`space_members`)에서 뽑아 Qdrant 필터에 넣는다. 오늘은 개인 Space 1개라 사실상 1개짜리 목록이지만, 처음부터 목록으로 다뤄 멀티플레이어 전환 시 검색 코드가 안 바뀌게 한다.
- **archived 제외는 필터가 아니라 공짜**: archive된 진술은 워커가 벡터를 지우므로(선언적 동기화, schema 5.3) 검색 공간에 없다. status 필터를 두지 않는다.
- **파라미터는 자리만**: limit·score threshold는 상수 자리만 잡는다(v1 꺼내기는 15개·0.6). 진술은 합성 문서보다 짧고 많아 v1 값이 맞으리란 보장이 없다 — 값은 하니스에서 보정.
- **검색 결과 → 본문은 Postgres에서**: Qdrant에서는 `statement_id`(+score)만 받고, 내용은 그 id로 Postgres를 다시 읽는다. payload의 content는 임베딩 시점의 사본이라 낡을 수 있다(archive 직후 워커가 벡터를 지우기 전의 틈, 추후 modify). Qdrant는 "어디에 있는지"의 색인이고, "무엇인지"는 항상 원장에서 읽는다 — 사본이 진실 행세를 못 하게 하는 원칙. 비용은 인덱스 걸린 `WHERE id IN (...)` 한 번. 이때 원장 기준 `status='archived'`인 진술은 거른다.

## 4. 묶음 — 기준 자리는 비워두고, 원문 묶음이 첫 세입자

09의 요구는 "찾은 진술들이 흩어진 목록이 아니라 묶이고 정렬돼 한눈에"다. 묶음 기준의 본 주인은 관계(지지·반박·대체)지만, 빌드 순서상 꺼내기가 관계 엔진보다 먼저 만들어진다. 그래서:

- **반환 계약에 기준 자리를 비워둔다.** 묶음은 `{ key(kind 유니온 + 기준별 정보), 진술들 }` 모양이고, kind는 확장 가능하다. 지금은 `source` 하나, 관계 엔진 설계가 나오면 관계 기반 kind가 **계약 변경 없이** 추가된다. "무엇으로 묶였나"가 데이터에 드러나므로 화면도 kind별로 그리면 된다.
- **1순위 묶음 기준의 확정은 관계 엔진 설계로 넘긴다.** 이 문서는 그 결정을 하지 않는다.
- **원문(source) 묶음은 자리 채움 구현이다.** 같은 글에서 나온 진술끼리 묶는다 — 한 source = 한 번에 던진 생각 덩어리라 묶음의 의미가 자명하고("그때 그 생각"), `statement_sources`로 공짜이며, 관계 묶음이 와도 출처 축으로 강등돼 영구히 쓰이므로 매몰 비용이 0이다. 의미 클러스터링·LLM 묶기를 피한 이유가 이것 — 둘은 관계가 오면 통째로 버려지는 임시 부품이다.

### 정렬 (원문 묶음의 채움 규칙)

- **묶음 간**: 묶음 내 최고 관련도(score) 내림차순 — 검색이니 관련 있는 덩어리가 위로. 각 묶음에 시점(`sourceCreatedAt`)이 붙어 옛것/최신이 눈에 보인다.
- **묶음 안**: 원문 등장 순서(`statement_sources.locator.index`, ingestion-design 3장) — 한 글의 조각이니 쓴 사람의 생각 흐름대로 읽히게.
- 정렬은 검색 결과를 받아온 뒤 앱 코드에서 한다(묶음당 진술 ~10개 수준이라 SQL 정렬 불필요).

## 5. 반환 형태

```
search({ query: string })  →

{
  groups: [                          // 묶음 간: 묶음 내 최고 score 내림차순
    {
      key: {                         // 묶음 기준 — 확장 가능 유니온 (4장)
        kind: "source",
        sourceId: string,
        sourceCreatedAt: string,     // 묶음의 시점 라벨 ("그때 그 생각")
      },
      totalStatementCount: number,   // 이 원문의 전체 active 진술 수
      statements: [                  // 검색에 닿은 것만. 묶음 안: 원문 순서
        {
          id: string,
          content: string,
          type: "claim" | "question" | "todo",
          confidence: "certain" | "guess" | null,   // claim에만
          createdAt: string,
          score: number,             // 관련도
        }
      ]
    }
  ]
}
```

- **닿은 진술만 싣고, 형제는 수만** — 응답은 검색의 답이어야 한다. 안 닿은 진술을 섞으면 결과가 흐려지고 점수 없는 항목이 끼어 정렬이 애매해진다. `totalStatementCount`가 닿은 수보다 크면 화면이 "이 글의 다른 진술 N개" 펼치기를 만들 수 있고, 펼치기는 `sourceId`로 그 원문의 진술을 가져오는 별도 조회다(화면 작업 몫).
- **source 본문은 싣지 않는다** — 묶음 보기의 주인공은 진술이고, 원문은 출처·검증용이다. 붙여넣기 원문은 수천 자일 수 있어 매번 실어 나르는 건 낭비. "원문 보기"는 `sourceId`로 별도 조회.
- **score는 노출한다** — 하니스의 threshold 보정과 화면의 표시 자유도를 위해. 단, 점수는 임베딩 모델에 종속된 상대값이라 화면이 절대 기준처럼 해석하면 안 된다(모델 바꾸면 분포가 통째로 이동). 정렬·비교용으로만.
- 결과 없음은 `groups: []` — 별도 상태 없음.

## 6. API 형태 — 단발 query, 스트리밍 없음

단발 tRPC query 하나. v1 꺼내기(`handleRetrievalStream`)가 스트리밍이었던 건 LLM이 산문을 생성했기 때문인데, v2의 반환물은 구조화된 묶음이고 경로에 LLM이 없다 — 토큰이 흐를 일이 없고, 전체가 1초 안쪽이라 기다림을 달랠 필요도 없다.

산문 합성(있으면 좋음)이 붙는 날엔 이 query가 묶음을 먼저 반환하고, 그 위에 별도 스트리밍 procedure가 얹힌다(묶음 먼저 보여주고 산문이 차오르는 UX). 지금 결정이 그 길을 막지 않는다.

## 7. 기존 코드의 거취 (빌드 세션 참고)

| 기존 | 거취 |
|---|---|
| `services/chat/retrieval.ts`의 벡터 검색 채널 | 모양 재활용 — 필터를 `user_id`→`space_id` 목록으로, 대상을 memories→statements로 |
| 그래프 검색(Neo4j)·텍스트 매치 채널, boost 로직 | 폐기 (엔티티 그물 정지, 진술엔 tags/title 없음) |
| `prompts/search-query-extractor` | 당장 폐기 — 다중 쿼리 추출이 필요해지면 그때 새 단위로(엔티티 출력이 없는 모양) |
| 스트리밍 답변 생성(`prompts/retrieval`) | 폐기 — 산문 합성이 올 때 새로 |

## 8. 후속 / 미결

- **묶음 1순위 기준** — 관계 엔진 설계([relation-design](relation-design.md))가 받았으나 dogfooding 후로 보류 — 실제 진술·관계 위에서 확정. 그때 원문 묶음은 출처 축으로 강등.
- **충돌·지난 것 표시** — [relation-design](relation-design.md) 8장이 확정: 검색 결과에서 빼지 않고 진술마다 표식(`supersededBy`·`conflictsWith`·`resolvedBy` 모양)을 단다.
- **다중 쿼리 추출** — 하니스에서 miss 패턴이 입증되면 임베딩 앞에 추가.
- **limit·threshold 값** — 하니스에서 진술 데이터로 보정.
- **형제 펼치기·원문 보기 조회** — 화면 작업에서 (`sourceId` 기반 단순 조회).
- **산문 합성** — 별도 스트리밍 procedure로 얹는 자리만 확인해 둠.
