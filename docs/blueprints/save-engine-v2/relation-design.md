# 관계 설계 — 진술 엔진 (save-engine-v2)

> 진술과 진술을 잇는 관계 엔진의 1차 골격. [06(관계)](../../product/06-concept-relation.md)·[07(모델링)](../../product/07-modeling.md)이 정한 관계 4종과 동작 규칙을, [`schema-design.md`](schema-design.md)이 자리만 잡아둔 `statement_relations` 위에서 도는 메커니즘으로 번역한다. **메커니즘(데이터 무관)까지만 정하고, 실제 진술 데이터를 봐야 정할 수 있는 것은 전부 "보류"로 명시한다**(11장).

## 0. 이 문서가 정하는 것 / 정하지 않는 것

- **정한다**: 관계를 언제·어떻게 잇나(워커 단계·배치 단위·상태 추적), 후보를 어떻게 좁히나(골격), 확신/충돌 게이트, 관계 변경셋의 type·묶음 단위, 관계의 저장·상태 동작, 꺼내기 연결(표식), Neo4j의 거취.
- **정하지 않는다**: 후보 K값·점수 하한·LLM 콜 구조·프롬프트(데이터로 보정 — 보류), 묶음 1순위 기준(보류: dogfooding 후), 관계 종류 확장(06 그대로 열어둠), 충돌 해소 흐름, 되돌리기·빼기 흐름, 검토함·화면 설계, 실제 구현(빌드는 이 설계 + dogfooding 후 별도 세션).

## 1. 전체 그림

```
사용자가 글을 던짐
  → [동기] source 박제                                  (ingestion-design 2장)
  → [워커] ① 추출: 글 → 진술 N개                        (〃 3~4장)
           ② 임베딩: 진술 → Qdrant 벡터                  (〃 6장)
           ③ 잇기(linking, 신규): 새 진술 배치 ↔ 기존 진술
                │
                ├─ 후보 좁히기: 벡터 근접 + 같은 글 형제      (4장)
                ├─ LLM 판단: 관계 있나, 4종 중 무엇, 확신하나  (5장)
                └─ 게이트:
                     확신 + 비충돌 → relation 변경셋 applied — 조용히 그래프에
                     애매 또는 충돌 → relation 변경셋 pending — 사람 대기
```

경로 전체가 비동기다. 사용자 응답은 박제에서 끝나고(기존 결정), 관계는 뒤따라 자란다.

## 2. 언제 잇나 — 워커 ③단계, 원문 배치로

**관계 감지는 워커의 세 번째 단계다. 순서는 추출 → 임베딩 → 잇기.** 후보 좁히기의 1차 도구가 새 진술의 벡터로 하는 근접 검색이라, 임베딩이 선행 조건이다. 기존 2단계 파이프(`infra/statement-sync`)에 단계 하나를 얹는 모양이라 파이프 구조는 안 바뀐다.

**검사 단위는 진술 낱개가 아니라 원문(source) 배치다.** 한 글의 진술 전부가 임베딩을 마치면 그 묶음을 한 번에 검사한다.

- 같은 글 안에서도 관계가 생긴다 — 결정과 근거가 한 글에 같이 오는 게 가장 흔한 모양("출시가 급했다. 그래서 토스를 택했다").
- LLM이 글의 진술 묶음을 통째로 보면 "이 글이 무슨 얘기인지" 맥락 안에서 판단한다. 낱개 검사는 그 맥락을 버린다.

**같은 글 안 관계도 ③단계가 전담한다 — 추출 콜은 안 건드린다.** 추출이 글 안 관계를 달고 ③이 글 밖 관계를 달면 같은 판단이 프롬프트 두 곳으로 갈라져, 기준 수정·평가가 두 벌이 된다. 절단 품질이 첫 출시 품질을 좌우하는 가장 큰 미정 항목(09)이라 추출 콜에 책임을 더 얹지 않는 이유도 있다. "쪼개는 순간이 관계를 가장 잘 안다"는 장점은 ③이 같은 글의 배치를 통째로 받으므로 거의 보존된다.

**엔진의 행동반경은 space 한 칸이다.** 후보 검색을 새 진술의 space로 한정하면 자연히 보장되므로 별도 검증 로직이 없다.

- space 안에서는 **작성자 무관**하게 잇는다 — 한 space는 함께 쌓는 맥락 한 칸(10)이라, 내 새 정보가 동료의 지난 결정과 부딪히면 드러나는 게 제품의 약속이다.
- space 사이는 엔진이 넘지 않는다. 엔진이 경계를 넘는 순간 "어디에 적으면 누구에게 보이나"의 약속이 깨진다. cross-space 관계의 1차 주인은 사람의 의식적 행위(다른 space의 진술에 직접 반박을 닮 — 스키마가 same-space 제약을 안 둔 이유)이고, 엔진의 cross-space 확장은 협업 권한 설계의 몫.
- 따라서 `statement_relations`에 same-space 제약은 **추가하지 않는다**(사람의 자리 보존). 좁히는 건 엔진의 검색 범위뿐.

## 3. 방아쇠와 상태 — 원문에 세 번째 상태 컬럼

배치의 단위가 원문이니 추적도 원문 단위다. 기존 파이프와 완전히 대칭이 된다:

```
sources.extraction_status    — 추출 됐나     (①, 원문별)
statements.ingestion_status  — 임베딩 됐나   (②, 진술별)
sources.linking_status       — 잇기 됐나     (③, 원문별 — 신규)
```

- **각 상태는 자기 단계만 안다.** 단계 사이 순서는 상태가 아니라 ③의 인출 조건이 표현한다 — ③은 ②의 상태를 읽기만 하고 소유하지 않는다. 단계 추가·제거가 "컬럼 하나 + 인출 조건 하나"로 닫히는 구조.
- **이름이 `relation_status`가 아닌 이유**: 그 enum은 이미 `statement_relations.status`(active/archived)가 쓴다. 잇기 단계의 코드 용어는 **linking**으로 둔다(glossary에 "잇기(관계 검사) = linking" 추가 — 빌드 범위). enum은 기존 `ingestion_status`(pending/completed/failed) 재사용 — 추출·임베딩과 같은 3-상태(작업 큐 의미론: pending=처리 대상, completed=끝, failed=자동 재시도 멈춤·수동 재개 가능)다.
- 재시도 컬럼(`linking_retry_count`·`last_linking_attempt`)·lease·선형 backoff·수동 재개 RPC(`retry_source_linking`)는 추출 쪽과 대칭. 세부는 빌드.

**방아쇠는 별도 이벤트가 아니라 인출 조건이다.** ③의 인출 RPC가 *"`linking_status='pending'`이고, 추출이 끝났고, 내 진술 중 임베딩 `pending`인 게 없는 원문"*을 집는다. 임베딩 완료를 누가 통지할 필요 없이 사이클이 돌 때 조건 충족된 원문이 잡힌다. `FOR UPDATE SKIP LOCKED` + lease 패턴 그대로라 멀티 워커 안전.

- **임베딩이 영영 실패한 진술이 배치를 막지 않는다** — 조건은 "pending이 없다"이고 `failed`는 정착한 상태로 친다. 실패 진술은 벡터가 없어 검색에 안 잡히는 것과 대칭으로 잇기에서도 빠진다. (수동 재개로 나중에 임베딩이 살아난 진술이 잇기를 놓치는 틈은 보류 — 11장.)
- **진술 0개인 원문**(노이즈뿐): 검사할 게 없으니 LLM 콜 없이 바로 `completed`.
- **적용과 완료 표시는 한 트랜잭션** — 갈라지면 적용 성공 후 크래시 시 같은 배치를 재검사해 관계 제안이 중복된다(ingestion-design 4장과 같은 논리).

## 4. 후보 좁히기 — 두 통로

새 진술을 기존 진술 전부와 비교할 수는 없다(LLM 비용 — brain 이주 같은 대량 유입에서 전수 비교는 즉사). 새 진술마다 후보를 두 통로에서 모은다:

- **ⓐ 뜻의 이웃 (벡터 근접)** — 새 진술의 벡터로 자기 space를 Qdrant 검색, 상위 K개. 관계가 걸릴 쌍(같은 주제의 지지·충돌·대체)은 뜻이 가까울 수밖에 없다는 가정 위에 선다. archived는 벡터가 없어 공짜로 빠지고, **대체된("지난") 진술은 active라 벡터가 있으므로 후보에 남는다** — 대체의 사슬에 또 얹히는 경우를 위해 의도된 동작(8장과 연결).
- **ⓑ 출생의 이웃 (같은 글 형제)** — 같은 배치의 다른 진술들. 글 안 관계를 ③이 전담하므로(2장) 벡터 점수와 무관하게 무조건 후보.

모은 후보를 합치고 중복을 걷어낸 뒤, 이미 같은 종류의 관계가 걸린 쌍은 건너뛰고, **배치(새 진술들) + 후보(기존 진술들)**를 LLM 판단에 넘긴다.

**미채택 통로** — 고려했고, 입장 조건과 함께 기록한다. 끼우는 자리가 전부 같은 곳(후보 수집)이라 나중에 더하는 게 구조 변경이 아니다:

| 통로 | 내용 | 입장 조건 |
| --- | --- | --- |
| 글자 매치 | 같은 키워드·고유명사가 든 진술 | ⓐ의 miss(좌표가 먼 동일 대상 쌍)가 데이터로 입증되면 — 1순위 복귀 후보 |
| 그래프 이웃 | 후보에 이미 걸린 관계의 반대편 끝점(대체 사슬의 이력) | 그래프가 쌓인 뒤, 사슬 판단 오류가 관측되면 |
| 미결 상비군 | 열린 question 전부를 상시 후보로 | resolves 누락이 관측되면 (뜻이 가까워 ⓐ가 잡을 가능성이 높아 일단 제외) |
| 시간 이웃 | 같은 시기·같은 세션의 진술 | ⓑ(같은 글)가 이 직관의 최강 형태를 이미 담음 — 글 경계를 넘는 가치가 입증되면 |

## 5. 판단과 게이트 — 확신은 조용히, 애매는 물어보고, 충돌은 무조건 물어본다

**판정 출력은 이진(확신/애매)이다.** 제안 하나당 `{from, to, 종류, 확신 여부}` — 0~1 점수가 아니라 예/아니오. 점수로 받으면 "몇 점부터 확신인가"라는 임계값 보정 문제가 하나 더 생긴다. eval-design 결정 #4(다단 척도는 모델별 반응이 달라 불안정, 이진으로 통일)와 같은 이유.

**분기 규칙** (07 동작 규칙 그대로):

| 판정 | 변경셋 | 효과 |
| --- | --- | --- |
| `supports`·`replaces`·`resolves` + 확신 | `applied` | 조용히 그래프에 들어감 |
| 애매 (종류 무관) | `pending` | 사람 대기 |
| `conflicts` (확신해도) | `pending` | 사람 대기 — 검토함이 곧 충돌 알림함 |

**충돌이 확신이어도 pending인 이유**: 참·거짓 미판단 원칙(07) — 충돌은 발견 다음에 반드시 "어느 쪽이 맞는데?"가 따라오고, 그 답은 시스템이 안 내린다. 어차피 사람이 결정할 사건이니 처음부터 사람 책상에 올린다. 따라오는 결과: 충돌이 꺼내기에 ⚡로 비치는 건 사람이 검토함에서 적용한 뒤다 — 대신 엔진 오판(거짓 충돌)이 검색 결과를 어지럽히는 일도 없다. 검토 전 pending 충돌의 노출 방식은 화면 설계 몫(보류).

**대체와 충돌을 가르는 기준 — 교대인가, 경합인가.** 작성자는 무관하다(내용 + 시간으로 판단).

- **대체 = 교대.** 새 진술이 옛것을 알고, 물러나게 하면서, 그 자리를 잇는다 — "토스 *접고* 포트원으로 간다"는 스스로 후임자임을 선언한다. 옛것이 틀린 게 아니라 *지난* 것. 교대가 내용에 뚜렷할 때만 엔진이 확신하고 조용히 적용한다 — 사람이 "예전 거 정리"를 안 해도 이력이 갈무리되는 가치가 여기서 나온다.
- **충돌 = 경합.** 두 진술이 둘 다 지금 유효하다고 주장하는데 양립이 안 된다 — 누구도 물러난 적 없다. 교대 선언 없이 어긋나기만 하면 엔진은 대체로 단정하면 안 된다(멀쩡히 유효를 주장하는 진술을 시스템이 멋대로 "지난 것"으로 가리는 꼴) — conflicts로 pending.
- 충돌 해소의 자연스러운 결말 중 하나가 대체다(사람이 "이쪽이 맞아"를 정하면 replaces로 표현될 수 있음). 해소 흐름의 세부는 `conflict` 변경셋 type 거취와 함께 보류(11장).

## 6. 변경셋 — `relation` type 신설, 운명이 같은 것끼리 묶기

**changeset type에 flat 값 `relation`을 추가한다.** 엔진의 관계 변경은 `ingestion`에 못 탄다 — ① ingestion 변경셋은 추출 직후 `applied`로 닫히는데 관계는 임베딩 뒤에 나오고(시점), ② ingestion은 "사람 주도 = 즉시 applied"인데 관계는 pending이 있고(게이트), ③ ingestion의 author는 제출자인데 관계는 엔진 산물이라 author가 없어야 한다(주체). 셋 다 "관계 감지는 저장이 방아쇠일 뿐 다른 종류의 변경"이라는 신호다. 07이 stale 재평가에 `recheck`를 별도 flat 값으로 두기로 한 것과 같은 결.

| type | 역할 | 주체 / status |
| --- | --- | --- |
| `ingestion` | 원문을 진술로 쪼개 저장 | 사람(제출자) / 즉시 `applied` |
| `relation` | **(신규)** 엔진의 관계 감지 제안·적용 | 엔진(author 없음) / 확신 `applied` · 애매·충돌 `pending` |
| `conflict` | 충돌의 해소(사람) — **거취 보류: 충돌 해소 흐름 설계 때.** 기존 해석("엔진이 충돌 발견")은 `relation`의 pending이 흡수 | 보류 / 미사용 |
| `merge` | 같은 뜻 진술의 합치기 — 합치기 흐름 설계 때 | 엔진 / 미사용 |
| `manual` | 사람의 직접 편집(빼기 등) | 사람 / 즉시 `applied` |
| `revert` | applied 변경셋 무르기(append-only) | 사람 / 즉시 `applied` |

- shape 제약(빌드 몫): `type='relation'`은 `source_id IS NOT NULL AND reverts_id IS NULL AND author_id IS NULL` — **`source_id`를 채워 "어느 글의 저장이 방아쇠였나"를 남긴다.** schema-design의 `chk_changeset_shape`·`changeset_type` enum 수정이 동반된다.
- changes 모양: 관계마다 `{action:'create', target_type:'relation', target_id, data:{type, from_id, to_id}}`.

**묶음 단위 — 운명의 경계가 변경셋의 경계다.** 함께 적용되고 함께 되돌려질 것만 한 묶음에:

- **`applied`는 배치(글)당 1개.** 기준은 *되돌리기의 단위* — 자동 잇기가 마음에 안 들면 "이 글 저장하며 달린 것들"을 한 덩어리로 무른다. 이력도 "이 글 → 진술 N개(ingestion) + 관계 M개(relation)"로 나란히 읽힌다.
- **`pending`은 관계 건당 1개.** 기준은 *사람의 결정 단위* — "이 충돌 맞아?"와 "이 근거 달까?"는 무관한 질문이라 하나는 승인, 하나는 거절할 수 있어야 한다. 묶으면 전부 받거나 버리거나가 되어(변경셋 status는 하나) 부분 적용 메커니즘을 새로 발명해야 한다.

**pending 동안 관계 행은 없다.** 제안은 pending 변경셋의 `changes.data`에만 존재하고, 사람이 적용하는 순간 행이 생긴다 — 07의 "활성 그래프 밖에서 대기"의 구현. 재시도로 같은 쌍이 다시 제안될 때의 pending 중복 방지는 빌드 세부.

## 7. 관계의 저장·상태 동작

- **append-only.** 엔진의 잇기는 `create`뿐이다. 관계의 제거는 `archived`(soft)이고 변경셋 경유이며, applied의 되돌리기는 revert 변경셋 *추가*다(07) — 무르는 단위·흐름은 빼기·되돌리기 설계의 몫.
- **schema가 엔진 단계로 미뤄둔 둘을 빌드 범위로 당긴다**: ① 끝점 진술 archived → 걸린 관계 연쇄 archive(되살리면 복귀) 트리거, ② `(from_id, to_id, type)` 중복 방지 unique — 재시도가 같은 관계를 이중 적용하는 것도 이 unique가 막는다.

## 8. 꺼내기 연결 — 빼지 않고 표식을 단다

꺼내기 경로(Qdrant → Postgres 진술 읽기)에 한 단계를 더한다: **방금 읽은 진술 id들에 걸린 active 관계를 조회**(인덱스 1회: `from_id`/`to_id` IN)해서, 진술마다 표식을 붙여 내보낸다.

| 걸린 관계 | 진술에 붙는 표식 | 화면이 할 수 있는 일 |
| --- | --- | --- |
| `replaces`가 나를 가리킴 | "지난 것" + 후임자 id | 흐리게·접기, "지금은 → 이것" |
| `conflicts`가 걸림 (방향 무관 양쪽) | "충돌 중" + 상대 id | ⚡ 표시, 나란히 보여주기 |
| `resolves`가 나를 가리킴 | "닫힘" + 닫은 진술 id | 체크 표시, 답으로 점프 |

- **검색 결과에서 빼지 않는다.** "예전엔 어떻게 생각했더라?"는 정당한 질문이고 지난 것이 그 답이다(06: 폐기를 지우지 않고 이력으로). 그래서 **대체된 진술의 벡터도 지우지 않는다** — archived(벡터 삭제 = 없는 것)와 대체(벡터 유지 = 있되 지난 것)의 차이가 정확히 이것. 가릴지 접을지는 화면의 몫이고, 데이터는 사실(지난 것임 + 후임자)만 나른다.
- **`supports`는 1차에서 표식이 없다.** 근거의 쓸모는 표식이 아니라 묶음("결정과 그 근거들을 한 덩어리로")인데, 그게 retrieval-design이 넘긴 "묶음 1순위 기준"이고 실제 진술 위에서 정하기로 한 보류 항목이다. 1차에서 supports는 저장만 되고, 묶음 kind가 정해지는 날 확장 가능한 key 유니온(retrieval-design 4장)에 계약 변경 없이 끼어든다.
- 응답 계약 변화는 진술 객체의 선택 필드 추가뿐(`supersededBy`·`conflictsWith`·`resolvedBy` 모양 — 이름은 빌드 때). 묶음 구조는 안 건드린다.

## 9. Neo4j — 들이지 않는다 (원장은 Postgres 하나)

schema-design이 "관계 엔진과 함께 후속"으로 넘긴 결정을 여기서 닫는다: **1차 골격에 Neo4j는 없다.**

- 1차의 관계 읽기는 전부 얕다 — 꺼내기 표식(8장)은 1-hop 인덱스 조회다. 그래프 DB가 주는 건 새 능력이 아니라 깊은 탐색의 속도인데, 개인~소규모(진술 수만·관계 수만 — brain 전체 이주도 이 안)에서는 Postgres 재귀 조회·전체 적재로 충분하다.
- **도입 판단 기준(미리 박아둠)**: 깊은 탐색·전역 패턴을 요구하는 동작(근거 사슬 복원, 그래프 뷰, 충돌 클러스터 분석)이 실제로 생겼는데, Postgres로 지어보니 *실측으로 느리거나* 조회가 *누더기가 될 때*. 기능의 존재가 아니라 짓다가 만난 고통이 신호다.
- 들일 때의 지위도 정해져 있다: 원장은 끝까지 `statement_relations`, Neo4j는 Qdrant와 같은 **읽기 전용 사본**(진술=노드, 관계=간선, archived는 사본에서 제거 — 선언적 동기화). 언제든 원장에서 통째로 재구축 가능하므로 도입은 마이그레이션이 아니라 읽기 경로 교체다 — 미루는 비용이 거의 0인 이유.

## 10. 빌드 범위 (이 설계 + dogfooding 후 별도 세션)

| 항목 | 내용 |
| --- | --- |
| 마이그레이션 | `sources.linking_status`(+재시도 컬럼), `changeset_type`에 `relation` + `chk_changeset_shape` 수정, 연쇄 archive 트리거, `(from_id, to_id, type)` unique |
| RPC | `fetch_pending_linking_sources` / `apply_relation_changesets`(적용+완료 한 트랜잭션) / `increment_source_linking_retry` / `retry_source_linking` — 추출 RPC 4종과 대칭 |
| 워커 | `infra/statement-sync`에 ③단계 — 후보 검색(Qdrant) + LLM 판단 + 게이트. ingestion-design 6장의 사이클(①→② 반복)에 세 번째 순환으로 끼어 ①②③ 셋 다 빌 때까지 반복 |
| 프롬프트 | 관계 판단(4종 + 이진 확신, 교대/경합 기준 — 5장이 뼈대) |

## 11. 보류 / 후속 — 해제 조건과 함께

**갈래 1 — dogfooding 보정 세션이 묶어서 푼다.** 엔진 빌드 → brain 이주(첫 대량 도그푸딩) → 관측 → 보정의 순서에서, 같은 데이터를 보는 한 세션이 아래를 한꺼번에 재심한다:

| 보류 | 해제 재료 |
| --- | --- |
| 묶음 1순위 기준 (retrieval-design이 넘긴 것 — supports를 묶음에 어떻게 쓸지 포함) | 실제 진술·관계 위에서 묶임새 관찰 |
| 관계 종류 확장 (인과·시간순·연관 — 06) | 확정 4종과 다른 동작을 만들어내는 사례 |
| 후보 K값·점수 하한 | 놓친 관계의 벡터 거리 분포 (특히 충돌 쌍이 얼마나 먼지) |
| LLM 콜 구조 (배치 1콜 vs 진술별) | 후보 수·프롬프트 길이 실측 |
| 미채택 통로 4종의 입장 (4장 표) | 각 통로의 입장 조건 = ⓐⓑ의 miss 패턴 |
| replaces 확신 문턱 (교대 판정의 과감함) | 잘못 가린/안 가린 사례 |
| 대량 유입의 순서 효과·비용 | brain 이주 그 자체가 관측 |

**갈래 2 — 주인이 따로 있는 후속.** 그 작업이 시작되는 날 첫 안건으로 올라온다:

- 충돌 해소 흐름 + `conflict` 변경셋 type 거취 (해소→replaces 전환 포함) — 검토함 설계
- pending 충돌의 검토 전 노출 방식 — 화면 설계
- 수동 재개로 늦게 임베딩된 진술의 잇기 누락 틈 — 운영 경로 정리
- 진술 modify 시 stale 관계 재평가(`recheck`) — 07 기존 보류 재확인
- 관계 평가셋 — eval-design이 후속으로 미룬 것, 엔진 빌드와 함께 또는 직후

**갈래 3 — 신호 대기.** Neo4j(9장의 판단 기준) — 신호가 안 오면 영영 안 올려도 된다.
