# 표면 인벤토리: MVP 화면 목록

> nema MVP가 가질 화면(표면) 전체와 각 화면의 역할을 정리한다. 설계 방법론·판단 근거·리스크·자기검산은 `surface-design.md`가 맡고, 이 문서는 "지금 화면이 뭐고 무슨 역할인지"만 압축해서 담는다.

### 함께 보는 문서

- 표면 설계(`surface-design.md`): 이 인벤토리를 도출한 방법론과 굳힌 설계 원칙(판정 시 사람 주권, 아직 안 풀린 리스크, 나중으로 미룬 것 등).
- 용어 사전(`docs/guides/glossary.md`): 아래 등장하는 Source·Digest·Statement·Relation·Reference·Changeset·Topic·Tag·Thread·Workspace·Space·User·Member 정의.

---

## 로그인

User를 식별해 Workspace로 진입시킨다. Space가 없으면 기본 Space를 자동 생성해 그 Space 오버뷰로 보낸다(신규 유저 — 아직 콘텐츠가 없어 홈에 보여줄 게 없음). Space가 이미 있는 기존 유저는 Space 개수와 무관하게 항상 [홈](#홈)으로 보낸다 — "마지막 활성 Space로 복원"보다 "여러 Space에 걸쳐 뭘 놓쳤는지 안 놓치고 보여주는" 쪽이 핵심 가치에 더 맞고, Space 개수에 따라 랜딩 지점이 달라지면 예측 가능성이 깨진다(Slack·Gmail·Notion 등도 콘텐츠 양과 무관하게 항상 같은 곳으로 연다).

## LNB

Workspace·User 표시 + 홈·Space 전환·생성 + 묻기·해설 + Reference 목록 + 초안 진입점을 제공하는 전역 셸. (Tag는 별도 표면 없이 Digest 리뷰 화면·Digest 상세의 칩 인풋으로 생성·수정됨)

위에서 아래로: **[Workspace 이름] → 홈 → 묻기·해설 → Workspace(레이블, Reference 목록) → Space(레이블, Space 목록 + 새 Space)**. 최상단엔 Workspace 이름만 두고, User 프로필(아바타·이름)은 그걸 클릭했을 때 뜨는 드롭다운(계정 설정) 안으로 옮긴다.

- **홈**은 로그인 시 실제로 떨어지는 자리라 묻기·해설보다도 위, Workspace 이름 바로 아래에 둔다. 자세한 내용은 [홈](#홈) 참고.
- **묻기·해설**은 nema의 핵심 차별점 기능이라 다른 항목보다 눈에 띄어야 하지만, 구체적 시각 스타일은 표면 디자인 라운드에서 정한다. 위치는 최상단 쪽으로 지금 확정.
- **Workspace 레이블**: Reference 목록을 감싸는 섹션 이름 — Reference가 Space가 아니라 Workspace 스코프라는 걸 SPACE 섹션과 시각적으로 구분해서 드러낸다.
- **초안**: `Changeset` 없이 pending으로 남은 Source(리뷰를 버렸거나, 되돌려졌거나, 아직 1단계 처리 중인 것들) 카드 목록으로 이동. **있을 때만 나타난다**(Linear의 Drafts처럼) — 다 처리되면 항목 자체가 사라진다. Space 스코프 데이터지만, 잘못된 Space에 들어간 걸 한눈에 보고 바로잡을 수 있어야 해서 Workspace 전역으로 모아 보여준다(카드마다 Space 셀렉트). 자세한 카드 구성·액션은 [초안](#초안) 참고.

**휴지통 UI는 지금 두지 않는다** — `trashed` Source를 다시 보여주고 복원하는 화면은 만들지 않고, "완전히 버리기"를 일방향 조작으로 둔다(모델의 `trashed`·보관 기간·배치 purge 자체는 그대로 유지). 실제 사용에서 복원 니즈가 잦아지면 그때 전용 화면을 고려한다.

## 홈

LNB 최상단(Workspace 이름 바로 아래, 묻기·해설과 나란히)에서 진입. 모든 Space를 가로질러 Digest를 시간순으로 통합해서 보여주는 화면 — Space 오버뷰의 스레드 탭과 같은 카드·무한 스크롤을 재사용하되, Topic·Tag 필터는 없다(Topic은 Space 안에서만 재사용되는 라벨이라 여러 Space를 섞으면 의미가 안 맞고, Tag 필터는 아직 어디에도 없는 기능이라 여기서만 먼저 넣으면 비일관적이라 나중에 한 번에 다룬다). 카드마다 소속 Space가 표시된다(Space 안 스레드 피드와 달리, 여긴 카드마다 출처가 다를 수 있어서 — Digest 상세의 "소속 Space 표시"와 같은 이유). 카드 클릭 시 Digest 상세가 사이드 패널로 열리는 것은 Space 오버뷰와 동일.

**넣기 입력창이 있다** — 다만 활성 Space가 없는 화면이라 Space를 명시적으로 골라야 한다. 초안 화면이 이미 쓰는 "Space 셀렉트"(표시+변경 겸용) 컴포넌트를 자동 확장 textarea 앞에 붙이는 조합으로, 새 패턴을 만들지 않는다. Source는 항상 특정 Space에 담겨야 한다는 원칙은 그대로 지키면서, 로그인 직후 첫 화면에서도 캡처가 가능하게 한다.

기존 유저는 로그인하면 Space 개수와 무관하게 이 화면으로 온다(위 "로그인" 참고).

## Space 오버뷰

**스레드 / 변경셋**, 2개 탭으로 나뉘는 화면. 넣기 진입점을 함께 제공한다. (탭 이름은 "변경 이력"이 아니라 "변경셋" — 대기 중인 것은 아직 "일어난" 게 아니라 "이력"이라는 이름과 안 맞음. GitHub도 "PR History"가 아니라 "Pull Requests"라고 부르는 것과 같은 이유. 변경셋 탭엔 대기 중 개수가 있으면 항상 배지로 표시돼(예: "변경셋 (2)") 탭을 안 열어도 대기 중임을 알 수 있다.)

**넣기 진입점(Source 작성)은 모달이 아니라 인라인 자동 확장 textarea다.** 타이핑·붙여넣기하면 내용에 맞춰 늘어나다 최대 높이 이후는 내부 스크롤로 넘어간다(원래는 별도 화면 "Source 작성 (모달)"이었으나 폐기 — 아래 근거). 판단 기준: (1) nema의 넣기는 "가벼운 캡처"지 저작 행위가 아니고(`surface-design.md` 자기검산 "넣는 일이 가벼운가"), (2) `Source`엔 `body` 외 필드가 없어 공개범위·서식 같은 부가 UI가 필요 없다 — 이 둘이 성립하는 한 자동 확장으로 충분하고, "긴 글도 편하게"라는 원래 목적도 이걸로 달성된다. (나중에 첨부 등 부가 기능이 생기면: 인라인에 자연스럽게 들어가는 정도(예: 첨부 아이콘 하나)는 그대로 두고, 제출 전 여러 결정을 강제하는 구조가 되면 그때 모달을 재검토한다.)

**스레드 탭**: 시간순 내림차순 무한 스크롤 단일 피드. Topic은 그룹핑이 아니라 필터(기본값 "전체" — 여러 Topic이 섞인 채로 최근 순 훑어보기가 재방문 시나리오에 더 맞음)고, 옆에 "오래된 판단만" 토글 필터가 추가로 있다 — 판정 대기는 변경셋 탭이 주 발견 경로지만, 오래된 미결·가정은 아직 전용 목록 화면이 없어 스레드 피드 자체의 필터로 존재한다. 각 Digest 카드엔 타입(결정·미결·학습·아이디어·가정)·Topic 태그가 붙고, 제목 옆에 다음 중 하나가 조건부로 뜬다(셋은 배타적 — 더 급한 신호가 우선):
- 이 Digest의 Statement·Relation 생성이 아직 진행 중이면 그 표시(완료되면 아무 표시도 없음 — GitHub PR 체크마크처럼 완결된 카드 위 일시적 조건)
- 이 Digest에 연결된 Statement가 판정 대기 변경셋(충돌·중복)에 걸려 있으면 가벼운 "리뷰 대기" 배지. 필터는 아니고 표시만 — 대기 항목을 찾는 주된 경로는 변경셋 탭이다. (Statement 하나를 주면 걸린 대기 중 변경셋을 돌려주는 조회 하나로 판단 — 같은 조회를 변경셋 탭·Digest 상세·묻기·해설이 공유한다)
- 미결·가정 타입이면서 오래된 판단 서피싱 조건(07-modeling.md 참고)을 충족하면 가벼운 "오래됨" 배지 — 위 둘보다 우선순위가 낮다(더 급한 신호가 없을 때만 뜬다)

**Topic으로 필터링하면 archived Digest도 보인다(접힌 채로, 원래 시간 순서 그 자리에)** — 07-modeling.md "Thread는 archived Digest 제외 규칙의 예외" 참고. 기본값 "전체" 피드는 여러 Topic이 섞인 최근 순 훑어보기 용도라 archived는 그대로 제외되지만(일반 규칙), 특정 Topic으로 좁히는 순간 그 필터링된 결과가 사실상 그 Topic의 Thread라, Digest 수정이나 duplicates 병합으로 archive된 옛 버전도 접힌 얇은 자리로 나타난다 — 안 그러면 그 Topic을 반복 수정·병합해온 히스토리 자체가 안 보이게 된다. 펼치면 그 시점 내용을 그대로 확인할 수 있다.

빈 상태는 데모 데이터 없이 단순 안내 문구만 — 첫 진입 온보딩을 다듬는 건 나중으로 미룬다(`surface-design.md` §6 참고).

**변경셋 탭**: [변경셋](#변경셋) 참고.

## Digest 상세 (사이드 패널)

목록(스레드 피드·묻기·해설 등)에서 Digest를 클릭하면 우측 사이드 패널로 뜬다 — 원래 화면의 흐름(스크롤 위치·대화 흐름)을 안 끊기 위함. 두 진입 방식이 있다:

- **평소 열람**: 클릭한 Digest의 내용(타입별 구조화된 본문)과, Statement 관계를 근거로 계산된 다른 Digest와의 관계를 보여준다(둘 다 없으면 그 섹션은 생략). 이 Digest에 판정 대기 변경셋이 걸려 있으면 맨 위에 가벼운 목록("리뷰 대기" 항목들 + 이동 버튼, 여러 개 가능)만 뜬다 — 판정 UI 자체를 여기서 안 보여주는 이유는 이 화면이 스스로 판정 대기를 계산할 수 없기 때문(Digest→Statement→Relation→Changeset을 거꾸로 조인하려면 아직 정의 안 된 `Change.data` 형식에 의존하게 됨). 이 Digest가 미결·가정 타입이면 나이·오래됨 여부와 무관하게 본문 영역에 "해소 작성" 버튼이 항상 뜬다 — 누르면 이 Digest를 미리 지칭한 채로 문서형 편집 폼이 열린다(07-modeling.md "미결·가정 해소 작성" 참고). 이와 별개로, 오래된 판단 서피싱 조건까지 충족하면 판정 대기와 같은 자리(맨 위)에 "오래됨" 표시가 추가로 뜬다(판정 대기가 있으면 그게 먼저, 오래됨은 그다음 — 스레드 카드와 같은 우선순위). "해소 작성" 버튼 자체는 이 오래됨 표시 여부와 무관하게 항상 노출된다.

  패널 헤더는 **좌측 Topic 브레드크럼 / 우측 공유·원문 보기·⋯(미트볼)**로 나뉜다 — 공유·원문 보기는 둘 다 Digest 전체 스코프의 참고·부가 액션이라 같이 묶이고, Topic도 여기로 옮겨와 헤더 한 줄에서 맥락(어느 스레드)과 부가 액션을 같이 보여준다. 원문 보기는 패널 하단 접기/펼치기가 아니라 사이드 패널의 공유 "원문" 탭을 열거나 포커스 이동하는 방식(Digest 리뷰 화면과 같은 메커니즘) — 본문을 읽던 탭과 원문 탭을 오가며 각자 스크롤 위치를 유지한 채 비교할 수 있어야 하기 때문.

**미트볼(⋯) 메뉴엔 "변경 이력"·"아카이브" 둘이 있다** — 위험하지 않은 조회(변경 이력)를 위, 위험한 액션(아카이브)을 아래에 둔다(공유·원문 보기 → ⋯ 순서와 같은 "안전한 것부터" 배치). "아카이브" 라벨은 "삭제"가 아니라 **"아카이브"** — 실제로 하는 일이 소프트 archive(되돌릴 수 있음)인데 "삭제"라고 하면 완전히 없어지는 것처럼 오해를 준다. "완전히 삭제하기"(초안 화면, `trashed`→30일 뒤 배치 purge)와는 무게가 다른 액션이라 단어도 구분한다. 위치는 "편집"과 성격이 달라 헤드라인 줄이 아니라 여기 둔다 — 편집은 콘텐츠를 고치는 액션(그 콘텐츠 옆에 붙어야 함, GitHub·Linear 패턴)인데, 아카이브는 콘텐츠 수정이 아니라 **Digest 전체를 대상으로 하는 액션**이라 공유·원문 보기와 스코프가 같다. 다만 위험한 액션이라 원문 보기처럼 바로 노출하지 않고 미트볼 뒤에 한 단계 숨긴다 — 자주 쓰는 원문 보기의 즉시 접근성은 그대로 지키면서 아카이브만 덜 눈에 띄게. (예전에 "..." 메뉴가 있다가 항목이 "편집" 하나뿐이라 없앤 적이 있는데, 그때와 지금은 반대 논리다 — 그때는 "항목 하나짜리 메뉴는 무의미하니 바로 보이는 링크로"였고, 지금은 "위험한 액션이라 일부러 한 단계 덜 보이게"라 메뉴 형태 자체가 목적에 맞다.)

확인 모달: "아카이브하면 피드·검색 등에서는 안 보이지만, 스레드에서는 접힌 채로 남고 이력·상세는 계속 확인할 수 있습니다." — 처음엔 "목록에서 사라집니다"라고 썼는데 부정확했다(07-modeling.md "Thread는 archived Digest 제외 규칙의 예외" — 스레드에서는 접힌 채로 계속 남는다).

**"이 판단이 대체함" 표시(`digest-supersedes-banner`)** — 진 쪽에 붙는 "대체됨"/"병합됨"의 반대편으로, 이긴 쪽엔 지금까지 아무 표시가 없었다. 처음엔 아카이브 확인 모달에 "여기 근거를 두고 있던 판단이 있다면 영향받을 수 있어요"라는 막연한 경고를 넣었는데, 정작 **그걸 Digest 안에서 뭘로 확인할 수 있냐는 질문에 답이 없었다** — 그래서 모달의 막연한 경고 대신, Digest 상세 자체에 "이 판단이 [진 쪽 제목]을 대체함 →" 상시 표시(조건부, 없으면 생략)를 추가했다. 아카이브하기 전에 이 표시를 보고 영향 범위를 미리 확인할 수 있다. 진 쪽은 archived Statement라도 "안 지우고 가린다" 원칙대로 직접 링크 타면 그대로 읽을 수 있다(새 탭으로 열림).

**아카이브 확정 후 "다시 활성화"는 같은 화면 안에서** — 확인 모달에 있던 "Changeset 상세에서 언제든 되돌릴 수 있습니다" 문구를 빼고, 대신 아카이브를 확정하면 Digest 상세 안에 "아카이브됨" 배너 + "다시 활성화" 버튼이 바로 뜬다. 다른 화면(Changeset 상세)으로 보내는 대신, 방금 있던 자리에서 바로 되돌릴 수 있게 한다.

**캐스케이드 엣지 케이스**: "끝점 archived → 관계 연쇄" 규칙 덕에 DB 무결성 문제(관계가 대롱대롱 매달리는 것)는 없다. 다만 처음엔 Digest 단위로 착각해서 헤맸다 — 정확히는 **충돌 판정에서 archive되는 건 Digest가 아니라 진술 하나뿐**이라, 진 쪽 Digest 자체는 항상 멀쩡히 살아있다(그 안의 진 진술 하나만 취소선 표시). 진짜 문제는 더 좁다: B(이겼던 쪽)를 아카이브하면 "B replaces A" 관계도 연쇄로 archived되는데, **A 진술 자체의 archived 상태는 안 돌아온다**(지금 규칙은 "진술 archived → 관계 archived" 방향뿐, 반대 방향은 없음) — 그러면 A는 그 표시를 설명하던 관계도 없이 계속 취소선으로 남는다.

해결책은 **아카이브 확인 모달에 조건부 체크박스**("대체됐던 판단도 함께 다시 활성화")를 추가하는 것으로 정했다 — 자동 복원(관계가 사라지면 A도 기계적으로 되살리기, git revert와 비슷한 논리)도 검토했지만 폐기했다. 자동 복원이 데이터상 깔끔해 보여도, B를 아카이브하는 의도가 꼭 "그 판정을 취소하고 싶어서"가 아니라 "이 Digest를 그냥 치우고 싶어서"일 수도 있어 의도치 않은 부작용이 될 위험이 있다 — 이 세션 내내 지켜온 "판정은 자동으로 하지 않는다" 원칙과, 체크박스 하나 추가하는 비용이 거의 없다는 점을 고려해 사람이 그 자리에서 명시적으로 고르게 했다.

**"변경 이력"은 미트볼(⋯) 메뉴에서 모달로 연다** — 이 Digest를 대상으로 한 `manual` changeset(수정·아카이브) 목록을 보여준다. `manual`은 변경셋 탭엔 아예 안 뜨므로(07-modeling.md "Digest·Reference 직접 편집은 변경셋 목록에 안 뜬다" 참고) 그 대상인 Digest 자신이 스스로 조회하는 게 유일한 경로다. 가운데 뜨는 일반 모달이고(Digest 전체 화면을 덮는 드로어가 아님), 안이 **좌우 2단**으로 나뉜다(Notion "Version history" 참고): 좌측이 diff 콘텐츠, 우측이 이력 목록("변경 이력 (N)", 항목마다 **수정 시각**·**수정한 사람** 두 줄만 — "수정"이라는 라벨이나 `#N`(changeset 번호)은 안 뜬다, 이 목록 자체가 이미 "그 대상의 수정 이력"이라는 맥락이라 반복할 필요가 없고 번호는 애초에 이 화면 밖(변경셋 목록)에서만 의미 있는 앵커라서다(위 "변경셋" §"manual은 Open·Closed 어디에도 안 뜬다" 참고). 시각은 다른 목록(피드·변경셋 목록 등)의 상대 시각("N일 전")과 달리 **절대 시각**("2026-07-05 14:20")을 쓴다 — 여긴 "최근에 뭐가 있었나"를 훑는 목록이 아니라 "정확히 언제 바뀌었나"를 감사(audit)하듯 확인하는 자리라 정밀도가 더 중요하다고 판단. 화면 전환 없이 우측 목록에서 다른 항목을 클릭하면 좌측 diff만 바뀌고, 방금 누른 항목은 목록에 선택 표시(테두리+배경)로 남는다 — 열었을 때도 빈 화면이 아니라 최신 항목의 diff가 기본 선택된 채로 뜬다. 좌측 diff는 Changeset 상세의 필드 diff와 같은 컴포넌트(`digest-readonly`, `diff-remove`/`diff-insert`)를 재사용한다. **별도 화면(Changeset 상세)으로 안 나간다** — 변경 이력 조회는 아카이브 확인처럼 가벼운 팝업 무게가 맞다고 봤다. 되돌리기(그 수정 자체를 되돌려 이전 버전으로 복원)는 이번 라운드에 안 채웠다 — 아카이브의 "다시 활성화"만 우선 구현했고(위 참고), 수정 건의 되돌리기는 다음 라운드.

**이 목록에 들어가는 것과 안 들어가는 것**: `manual`(수정·아카이브) changeset만 들어간다. **수정으로 인해 캐스케이드된 `relation`(재판정된 충돌·중복)은 안 들어간다** — 타입이 다르고(이 모달은 `manual` 전용), 그 재판정은 이미 Digest 상세의 "리뷰 대기"(아직 안 끝남)·"대체됨"/"대체함" 배너(끝남)·변경셋 목록(`relation`은 거기 뜸)으로 다 노출되고 있어서, 여기 또 넣으면 같은 정보를 두 군데 적는 중복 축이 된다(07-modeling.md가 `Changeset.type`을 계속 "트리거" 기준으로만 나눠온 것과 같은 원칙). **아카이브는 이 목록에 들어가는 게 맞다**(수정과 같은 `manual` changeset) — 다만 "지금 활성 상태인 Digest 자신의 이력"에는 archive 항목이 안 뜬다(archive된 순간 그 Digest 자체가 더 이상 활성이 아니게 되므로, 활성 버전 입장에선 "나를 만든 수정들"만 보인다). archive 항목은 **그 archive된 Digest 자신**의 상세("안 지우고 가린다" 원칙대로 계속 열람 가능)에서 자기 이력을 열었을 때 마지막 항목으로 보인다 — 이번 라운드는 그 화면(archived Digest 자신의 전체 상세+미트볼)까지는 안 만들어서 실제 예시로는 못 넣었다.

  본문 콘텐츠는 실제 기사·블로그 관습(제목 → 시간 → 요약 → 본문 → 태그)을 참고했다: [타입 배지]제목(+ 우측에 가볍게 "편집") → 시간(제목 아래 작게, 협업 확장 시 작성자가 여기 같이 붙을 자리) → 요약 → 본문 → **Tag**(본문 다 지나서 맨 끝) → **관련 Digest** → 외부 링크. "편집"이 헤드라인 줄에 단순 링크로 남는 이유는, 본문을 직접 고치는 액션이라 그 콘텐츠 바로 옆에 있어야 한다는 GitHub·Linear 근거가 여전히 유효하기 때문(원문 보기·공유는 반대로 Digest 전체 스코프라 패널 헤더가 더 맞음). Tag를 본문 뒤로 둔 이유는 "본문 편집 영역"(아래 참고)이 타입·제목·본문으로만 뭉쳐 있어야 편집 진입점의 범위가 안 헷갈리기 때문이기도 하다. 관련 Digest가 외부 링크보다 위인 이유는, 엔진이 2단계(Statement·Relation 생성)로 계산해낸 의미 있는 연결이 원문에서 그냥 뽑아낸 외부 링크(부산물에 가까움)보다 nema의 핵심 가치(맥락이 어떻게 이어지는지)에 더 가깝기 때문(Notion 백링크·GitHub Linked issues가 첨부파일보다 우선하는 것과 같은 이유). "변경 이력"은 이 본문 콘텐츠 흐름 안에 없다 — 위 미트볼 메뉴 참고.

  별도의 "레퍼런스" 요약 섹션은 없다 — 본문 안 `@` 멘션이 유일한 인용 경로다(본문에 없는 걸 레퍼런스로 걸 수 없어야 "이 Digest가 언급하는 것"이라는 뜻이 안 깨짐). 멘션을 클릭하면 그 Reference 탭이 열린다.

  편집은 두 층으로 나뉜다(07-modeling.md `Change` 절 참고), 둘 다 이 화면 안에서 끝난다(별도 화면으로 안 넘어감):
  - **가볍게, 그 자리에서 바로**: Topic·Tag·관련 Digest·외부 링크는 칩 형태로 그 자리에서 추가·삭제(changeset 없음) — 판단 콘텐츠가 아니라 찾기·참고용 메타라서. 관련 Digest는 사람이 여기서 처음 심는 게 아니라, 확정 후 2단계(Statement·Relation 생성)가 끝나면 엔진이 자동으로 채워 넣은 걸 보고 자유롭게 더하거나 뺀다. 레퍼런스(멘션)는 이 목록에 없다 — 본문과 한 몸이라 아래 무거운 편집에 딸려서만 바뀐다. 다른 Digest가 지금 이 Digest를 관련 Digest로 물고 있는 상태에서 이 Digest가 수정(archive+create)되면, 그 참조는 새 Digest ID로 자동 치환된다(07-modeling.md 참고) — archived Digest가 목록에 남는 경우 자체가 생기지 않는다.

    Topic·Tag 칩 자체를 클릭하면(추가·삭제 액션과는 별개 진입점) 그 라벨 엔티티를 고치는 편집 팝오버가 뜬다 — 이름 변경과 아카이브(Tag는 정의 편집도 추가, `description` 필드가 있어서)를 담았다. 07-modeling.md가 Topic·Tag를 changeset 없이 가볍게 CRUD하도록(soft delete만 유지) 정해둔 것의 UI 표면이다. 아카이브는 이미 붙어 있는 Digest·Reference와의 연결을 끊지 않는다("안 지우고 가린다" 원칙) — 재사용 제안 후보에서만 빠지고, Topic은 스레드 피드의 Topic 필터에서 계속 선택할 수 있어 이미 태그된 Digest를 계속 찾을 수 있다(Tag는 별도 필터가 아직 없어, 이미 태그된 항목에 남아 있는 칩을 통해서만 다시 접근·되살릴 수 있다).
  - **무겁게, 본문 영역 자체의 "편집" 링크로 인라인 전환**: 제목·요약·본문(타입별 구조화 내용)·타입은 Statement가 근거로 삼는 판단 콘텐츠라 `manual` changeset(옛 Digest는 archive, 새 Digest는 create)을 거친다. 누르면 그 영역이 그 자리에서 편집 가능한 형태(Digest 리뷰 화면과 같은 문서형 편집 패턴 — doc-input, 타입 전환, @ 멘션)로 바뀐다(화면 이동 없이). 편집 모드로 들어가면(액션이 늘어나서) 그때서야 "편집 중" 표시+"취소"·"제출" 액션이 담긴 헤더가 나타난다. **편집 중엔 changeset이 아직 안 생긴다** — 프론트엔드 로컬 상태로만 존재하다가, "제출"을 누르는 순간에야 `manual` changeset이 만들어져 곧바로 확정(옛 Digest archive + 새 Digest create)된다(컨펌 모달로 "기존 내용이 archive되고 대체된다"는 걸 미리 알림). 취소하거나 그냥 나가면 로컬 상태만 사라질 뿐 서버엔 아무 흔적도 안 남는다(아직 아무것도 안 바뀐 상태라 되살릴 대상이 없음 — 브라우저가 죽어 미완성 편집을 잃는 정도는 감수, 가벼운 교정용 기능이라 손실 비용이 낮음). 제출 시점엔 옛 Digest가 여전히 active인지 확인하는 낙관적 동시성 체크를 거쳐, 협업 중 다른 사람이 먼저 같은 Digest를 고쳤다면 오류로 막고 새로고침을 유도한다(편집 내내 잠가두는 것보다 가벼운 절충 — 07-modeling.md 참고).

  **원문 보기**는 패널 하단 접기/펼치기가 아니라 Digest 리뷰 화면과 같은 메커니즘(사이드 패널의 공유 "원문" 탭을 열거나 포커스 이동)을 재사용한다 — 화면마다 원문 대조 방식이 다르면 안 되고, 본문을 읽던 탭과 원문 탭을 오가며 각자 스크롤 위치를 유지한 채 비교할 수 있어야 하기 때문(패널 하단 접기/펼치기는 스크롤을 오가야 해서 비교에 불리).

    (Digest 리뷰 화면과 이 편집 모드를 처음엔 같은 화면으로 재사용하려 했으나, "가벼운 필드만 고치고 확정해도 무거운 changeset이 남아야 하나" 하는 모호함이 생겨 폐기 — 두 흐름을 트리거 자체로 분리해 모호함이 구조적으로 안 생기게 함. Digest 리뷰 화면은 이제 신규 ingestion 리뷰(여러 Digest·Reference 후보를 한 번에) 전용.)
- **"리뷰 대기" 목록**: 이 Digest에 걸린 relation changeset(충돌·중복)이 있으면 패널 헤더 아래 조건부로 뜬다(없으면 섹션 생략, 여러 개 가능). **표식은 시간순으로 나중에 들어와 충돌을 일으킨 쪽(=이 판정을 촉발한 Digest)에만 붙는다** — 먼저 있던 쪽은 안 건드린다. 항목을 누르면 [관계 판정 화면](#관계-판정-화면)으로 이동한다(예전엔 "Digest 상세 안의 판정 모드"로 잡았었는데, 두 Statement가 서로 다른 Digest·Source에서 올 수 있어 "하나의 Digest를 보여주는 화면"이라는 정체성과 안 맞아 독립된 화면으로 재검토함).
- **판정이 끝나면 "리뷰 대기" 항목은 목록에서 사라진다**(이겼든 졌든) — 리뷰 대기는 "지금 판정이 필요하다"는 액션 유도라, 액션이 끝나면 더 볼 이유가 없다. 진 경우, 그 자리에서 문구만 바꿔치기(예전 안)하지 않고 **별도의 "대체됨" 배너를 새로 추가**한다 — 리뷰 대기(일시적 액션 유도)와 대체됨(영구적 사실 기록)은 성격이 달라서 같은 목록 항목이 모습만 바꾸는 것보다 서로 다른 블록으로 분리하는 게 맞다. 배너는 배지+"[이긴 쪽 제목]으로 대체됨 →" 링크로, **대체한 Digest(A) 자신**을 사이드 패널의 새 탭으로 연다(기존 "관련 Digest" 탭과 같은 메커니즘) — 판정 기록([Changeset 상세](#changeset-상세))으로 보내는 건 부정확하다, "무엇으로 대체됐는지"에 대한 답은 그 changeset이 아니라 그 Digest 자체이기 때문이다. **본문 안에서도** 대체된 문장(위 예시는 "선택" 필드)에 취소선을 그어 짚어준다 — 배너만으론 "본문 전체가 지났다"로 오해할 수 있어서다. "조용히 덮지 않는다"는 원칙(surface-design.md §2·§3) 때문에 셋 다(항목 제거·배너·본문 표시) 필요하다 — 표시가 없으면 이 Digest를 나중에 그냥 읽었을 때 그 판단이 이미 밀려났다는 걸 전혀 알 수 없다.

**사이드뷰는 브라우저 탭처럼 여러 개를 동시에 열어둘 수 있다.** Digest 하나의 상세를 읽다가 레퍼런스·관련 Digest를 클릭하면 그게 새 탭으로 열리고(같은 대상이 이미 열려 있으면 중복 없이 그 탭으로 전환), 원래 보던 탭은 그대로 남아 있다. 탭마다 개별 닫기(×)만 있고 "전체 닫기"는 없음 — 마지막 탭이 닫히면 사이드뷰 자체가 사라진다. 이 탭 컨테이너는 Digest 상세뿐 아니라 Reference 상세도 공유하는 하나의 사이드뷰 시스템이다(Changeset 상세는 사이드뷰가 아니라 메인 뷰 — 아래 참고).

사이드뷰는 **Space 스코프**다 — 콘텐츠(Digest·Reference)가 Space에 속하므로, 다른 Space로 전환하면 사이드뷰는 자동으로 닫힌다(탭이 몇 개 열려 있든 전부). 같은 Space 안에서 화면만 오가는 것(예: Digest 리뷰 화면 확정 후 Space 오버뷰로 복귀)과는 다른 경우다 — 그건 Space를 벗어난 게 아니라서 사이드뷰가 그대로 유지된다.

## Digest 리뷰 화면

1개 Source에서 추출된 N개 Digest와 N개 Reference 후보를 확인하고 확정하는 전체 화면. 원본 대조가 이 화면의 핵심 작업이라, 들어오면 사이드 패널의 원문 탭이 기본으로 열려있다(첫 후보 카드의 locator가 하이라이트된 채로) — 탭 라벨·본문 상단 모두 "원문"이라는 고정 텍스트 대신 `Source.title`을 그대로 쓴다(이 시점엔 open ingestion changeset이 이미 있어 읽기 전용, 07-modeling.md 참고) — 다른 탭도 각자 자기 콘텐츠의 이름을 라벨로 쓰지 "이건 다이제스트 탭입니다" 식 메타 라벨을 따로 안 두는 것과 같은 일관성. 신규 ingestion 리뷰 전용 — 확정된 Digest를 고치는 건 Digest 상세 안의 인라인 편집 모드가 맡는다(위 참고). 화면 제목·우측 상단 확정 버튼은 같은 줄에 — 화면 제목은 그 `open` 변경셋의 `Changeset.title`이라 변경셋 탭 목록의 그 행과 같은 값으로 이어진다. 제목 내용은 대표 Digest 제목을 기계적으로 조합한 게 아니라, 엔진(LLM)이 **원문 전체**를 보고 그때그때 생성한다(대화·논의의 상위 주제, 예: "CS 채팅 UX 개선") — 결정·미결·아이디어 등 서로 다른 타입의 Digest 여럿을 낳는 상위 단위는 개별 판단이 아니라 그것들이 나온 대화 자체이기 때문이다. 여러 Digest가 같은 주제를 공유하면 자연스럽게 그 주제가 제목이 되고, 주제가 갈려도 LLM이 전체를 아우르는 요약형 제목("~에 대한 논의" 등)을 알아서 만들어 별도의 폴백 분기 로직이 필요 없다(07-modeling.md "title" 필드 생성 규칙 참고). 제목은 GitHub PR 제목처럼 초기값은 엔진이 채우지만 사람이 직접 고칠 수 있다(제안은 엔진이, 수정은 사람이) — 문서형 편집(`.doc-input`)이라 클릭하면 바로 고쳐 쓴다. 제목 바로 옆엔 `Changeset.number`(`#12`처럼, GitHub의 PR 번호와 같은 역할)를 붙여둔다 — title은 편집 가능해 안정적인 지칭 앵커가 못 되므로, 그 역할은 안 바뀌는 이 번호가 대신한다. 제목 입력창은 텍스트 길이만큼 늘어나되 max-width로 상한을 두고, 넘치면 줄바꿈 대신 말줄임표로 자른다(번호가 항상 제목 바로 옆에 붙어있어야 하므로 여러 줄로 안 늘어남). 헤더 자체는 스크롤 시 상단에 고정(sticky)돼, 후보 카드가 많아 화면이 길어져도 취소·확정이 항상 보인다(GitHub PR 헤더가 스크롤해도 압축된 형태로 남는 것과 같은 이유).

부제 줄은 **status | authorId | createdAt** 세 요소로 깔끔하게 정리한다 — GitHub PR 헤더의 "Merged 배지 · igy95 merged ... · 53 minutes ago" 구성과 같다. 상태 배지는 이 화면이 `open`(리뷰 대기)만 다루는 동안엔 항상 고정값이고, `closed`(적용됨/버려짐)는 별도 화면인 [Changeset 상세](#changeset-상세)가 맡는다 — 두 화면은 같은 헤더 정보 구성(제목+번호 · status | author | time)을 공유하는 짝이지만 코드 레벨로 같은 화면은 아니다.

`authorId` 자리는 이름만 평범한 텍스트로 보여준다(아바타·역할 태그 없이) — 처음엔 relation처럼 리뷰어가 여러 명일 수 있는 경우를 대비해 아바타+역할 컴포넌트를 만들었었는데, 다시 보면 relation도 결국 그 changeset을 일으킨 쪽(새로 들어온 Source) 한 명이 리뷰어다 — 충돌 상대(기존 Digest)의 출처는 리뷰어가 아니라 비교 내용(콘텐츠) 쪽에서 보여줄 정보라 위계가 다르다. 항상 한 명이면 되므로 굳이 아바타·역할 태그로 미리 대비할 필요가 없어 단순화했다.

그 자리에 들어가는 값의 뜻은 changeset 타입마다 다르다:
- **ingestion**(지금 이 화면): changeset 자체의 `authorId`는 없다 — Source 제출이 방아쇠이긴 해도 구체적 내용(Digest 개수·제목·Reference 후보)은 엔진이 만든 것이라서다(07-modeling.md "authorId 규칙" 참고). 그 자리엔 대신 이 changeset의 원본(Source)을 제출한 사람(`Source.authorId`)을 채운다 — 원본을 던진 사람이 추출 결과에 가장 맥락이 많아 리뷰하기 적합하다는 전제다.
- **manual·revert**: 사람이 changeset 내용 자체를 직접 만들어 `authorId`가 실제로 있다 — 같은 자리에 그 사람(작성자)을 보여준다.
- **relation**: 그 관계 판정을 촉발한 새 Source의 제출자 한 명 — 위 이유로 ingestion과 같은 단수 규칙을 그대로 쓴다.

지금은 혼자 쓰는 Space라 리뷰어가 누구여야 하는지 모호할 일이 없지만, `authorId` 기반 프로필 컴포넌트를 지금부터 하나로 통일해두면 나중에 협업이 열려도 다른 타입 화면에서 그대로 재사용되고, 변경셋 목록에서 이 값 기준으로 필터링하기도 쉬워진다. 특정 사람에게 리뷰를 할당·알림하는 것은 별개의 협업 기능이라 지금은 다루지 않는다.

Digest·Reference 개수는 헤더가 아니라 각 목록 바로 위 라벨로 둔다 — "Digest (1)" / "Reference (2)"처럼 짝을 맞춰서("후보"라는 말은 뺌, 라벨은 짧게), 헤더는 changeset 자체의 정체성(제목·번호·상태·생성 정보)만 담당하고 콘텐츠 스코프는 그 콘텐츠 옆에 붙인다.

이 화면은 `open` 변경셋을 사람이 직접 고쳐 쓰는 초안 편집 화면이다("open은 확정 전 초안" 원칙) — 후보별 accept/reject이 따로 있는 게 아니라, 마음에 안 드는 Digest·Reference 후보는 초안에서 삭제(컨펌 모달 거침)하고 남은 걸 한 번에 확정한다. 확정 버튼 옆엔 "버리기" 버튼도 있어 — 이 changeset을 `closed`+`outcome: discarded`로 남긴다(하드 삭제 아님, 나중에 되살릴 수 있음). 버튼 이름을 "취소"가 아니라 "버리기"로 한 이유는, 컨펌 모달 안의 "취소"(모달을 그냥 닫는 액션)와 같은 단어가 헤더·모달에 동시에 다른 뜻으로 나오는 걸 피하기 위함이다.

확정·버리기 모두 **Space 오버뷰로 나가지 않고 이 화면에 그대로 남아 상태만 전환**된다 — GitHub PR을 merge/close해도 그 PR 페이지에 그대로 남아있는 것과 같다. 상태 배지가 "리뷰 대기"에서 "적용됨"/"버려짐"으로 바뀐다. **확정되면 각 Digest 후보 카드도 편집 폼에서 읽기 전용 카드(`.digest-readonly`)로 전환된다** — 확정된 Digest는 더 이상 만질 수 있는 대상이 아니므로, "만질 수 있어 보이는데 실제로는 안 만져지는" 정직하지 못한 상태를 그대로 두지 않는다. 이 읽기 전용 카드는 Digest 상세 읽기 모드와 같은 마크업(headline-row+badge+digest-title, digest-description, body-field×N)을 쓰고, [Changeset 상세](#changeset-상세)의 스냅샷 카드도 정확히 같은 컴포넌트를 재사용한다 — "확정된 Digest를 읽기 전용으로 보여준다"는 같은 일이라 화면마다 다른 컴포넌트를 만들 이유가 없다.

**"버리기"는 모달·체크박스 없이 바로 실행된다.** 원본(Source)을 같이 완전히 삭제할지 미리 묻지 않는 이유는, GitHub이 PR을 merge한 뒤에야 "Delete branch" 후속 버튼을 보여주는 것과 같은 패턴을 따랐기 때문이다 — 사전에 다 묻지 않고, 주된 행동(버리기)은 가볍게 두고 부가 선택(원본 삭제)은 그 직후 자연스러운 순간에 제안한다. 버려지는 즉시 그 원본은 `pending`으로 남아 "초안"에서 나중에 "처리하기"로 재시도할 수 있고, 헤더에는 **"원본도 삭제하기"** 후속 버튼이 나타난다. 이 버튼을 누르면 원본이 즉시 삭제되고 버튼도 사라진다 — `pending`↔`trashed` 전환은 07-modeling.md상 changeset에 안 남는 동작이라(변경이력 대상 아님) 되돌릴 방법이 없다. 휴지통 UI 자체를 지금 두지 않기로 했으니(위 "휴지통 UI는 없앰" 참고) 이 정도 무게(정말로 되돌릴 수 없음)를 버튼 한 번으로 처리해도 괜찮다고 판단했다 — 나중에 복구 니즈가 잦아지면 그때 휴지통을 도입해서 더 신중한 확인을 추가하면 된다.

헤더 액션은 결과에 따라 다르다:
- **적용됨** → 바로 "되돌리기" 버튼이 남는다. 누르면 원래 changeset의 status·outcome은 안 바뀐다 — "되돌리기(append-only)" 원칙대로 `closed`+`outcome: applied`로 그대로 남는 게 "이건 실제로 적용됐었다"는 사실 자체이고, 되돌린 효과는 별도의 새 `revert` changeset(즉시 `closed`+`outcome: applied`)으로 기록된다. 그 순간 버튼 자체가 그 revert changeset의 [Changeset 상세](#changeset-상세)("되돌림 #13 보기")로 가는 링크로 바뀐다. 재적용이 필요하면 특별한 토글을 여기 더 만들 필요 없이, 그 화면의 revert changeset도 똑같이 "되돌리기" 버튼을 가진 또 하나의 `closed`+`applied` changeset이라 거기서 같은 버튼을 누르면 된다(revert의 revert = 재적용, 재귀적으로 이미 풀림). 버튼이 링크로 바뀌는 것과 별개로 그 화면이 자동으로 열리진 않는다 — 누른 즉시 강제로 화면을 전환시키면 하던 작업 흐름을 끊는다. 이 되돌리기도 결국 원본을 `pending`으로 되돌리는 것과 같은 동작이라(07-modeling.md "ingestion 되돌리기" 참고), 버리기와 똑같이 그 옆에 "원본도 삭제하기" 후속 버튼이 나란히 붙는다.
- **버려짐** → 헤더 액션이 "원본도 삭제하기" 하나뿐이다("되돌리기" 버튼은 안 둠). discard는 애초에 만든 게 없어 archive할 대상 자체가 없어 되돌리기 자체가 성립하지 않는다.

버리기·되돌리기(적용됨) 둘 다 결과적으로 그 원본을 "초안"에 다시 나타나게 하는데, 이건 이미 있는 "초안" 버튼의 조건부 노출(있을 때만 나타남, Linear Drafts처럼)로 자연스럽게 신호가 간다 — 화면을 억지로 초안 탭으로 전환시키거나 별도 안내 문구를 넣지 않는다. Gmail이 보관 처리해도 보관함으로 안 끌고 가고 "실행취소" 토스트만 띄우는 것과 같은 이유로, 하던 작업 흐름을 안 끊는 쪽을 택했다.

**Digest 후보 카드**: 폼이 아니라 문서(Notion류)에 가깝게 보인다 — Digest 상세(평소 열람)와 같은 레이아웃(Topic 브레드크럼 → [타입 배지]제목 → 본문 → Tag → 외부 링크)을 그대로 재사용해 편집 가능하게만 바꾼 것으로, 읽기 화면과 편집 화면을 따로 나누지 않는다. Tag가 본문 뒤에 있는 이유도 Digest 상세와 같다(실제 기사·블로그 관습, 본문 편집 진입점이 타입·제목·본문으로만 뭉쳐 안 끊김). 라벨은 꼭 필요한 곳(Tag 칩, 타입별 본문 필드명)에만 최소로 쓴다.

- 본문 필드는 타입(결정·미결·학습·아이디어·가정)에 따라 필드 이름·개수만 다르고 렌더링 규칙은 하나다 — `string` 필드는 필드명 아래 텍스트(늘어나면 자동 확장) + @ 버튼(레퍼런스 멘션), `string[]` 필드는 필드명 아래 항목별 추가·삭제 목록. 원문에 없어 못 채운 optional 필드는 특별한 설명 없이 그냥 빈 칸으로 둔다(다른 빈 폼 필드와 동일하게 채우고 싶으면 채우면 됨).
- 타입을 바꾸면 그 타입 전용 본문 필드가 다른 타입 필드로 옮겨지지 않고 초기화되므로(컨펌 모달) 확인을 거친다.
- 카드마다 타입 개수가 달라 카드 높이가 들쭉날쭉해도 괜찮다 — 세로 스크롤 목록에서 항목 높이가 다른 건 스레드 피드·GitHub PR의 Files changed 등 보편적인 패턴이라 별도 처리가 필요 없다.
- **@ 멘션**: 본문 필드 옆 "@" 버튼을 누르면 레퍼런스 검색·선택 목록이 뜬다("이 리뷰에서 새로 만드는 레퍼런스" / "레퍼런스" 두 그룹, 검색은 둘 다 필터링, 없으면 "+ 새 레퍼런스로 만들기"로 그 자리에서 Reference 후보가 하나 생성됨). 실시간 caret 위치 자동완성(Slack·Notion류)이 아니라 버튼으로 단순화한 것 — 실제로 하려면 `contenteditable` + caret 좌표 계산이 필요해 범위 밖. 본문 문자열 안에 멘션을 어떻게 직렬화할지는 별도 모델링 질문으로 남겨둠.
- **externalUrls**: 원문에서 뽑힌 외부 링크. 추가·수정·삭제 전부 가능(트레이드오프·대안과 같은 목록 패턴). 링크 제목·설명은 모델에 안 저장하고 화면에서 렌더링 시점에 언퍼롤(Slack·Notion처럼)해서 보여준다 — 모델은 URL 문자열 배열 그대로 단순하게 유지.
- **원문 대조**: 화면 진입 시 사이드 패널(Digest 상세·Reference 상세가 쓰는 것과 같은 다중 탭 시스템 — 원문 탭만 특별 취급하지 않고 자유롭게 열고 닫을 수 있음)의 "원문" 탭이 기본으로 열려 `Digest.locator` 영역이 하이라이트돼 있다(첫 후보 카드 기준). 카드마다 있는 "원문에서 보기" 트리거를 누르면(이미 열려 있으면 새 탭이 아니라 그 탭으로 포커스 이동) 같은 원문 탭 안에서 하이라이트만 갱신 — 하나의 Source를 가리키는 거라 탭이 여러 개일 이유가 없다. "원본을 통째로 깔면 다시 읽는 수고가 되살아난다"는 원칙과는 안 부딪힌다 — 그 원칙은 하이라이트 없이 전체를 보여주지 말자는 것이지 패널이 열려있냐 닫혀있냐의 문제가 아니고, 지금도 관련 부분만 하이라이트해서 보여준다.
- **원문 링크 활성**(`.candidate-source-link.active`, 링크 자체가 진하게): "원문에서 보기"를 클릭하면 그 링크 자신이 활성 표시된다 — "지금 원문 탭이 보여주는 게 이 카드 얘기"를 링크가 직접 알려준다. 같은 탭(`tab-source`)을 가리키는 링크끼리만 배타적이고(하나의 공유 탭을 여러 카드가 가리킬 수 있어서), 그 탭을 닫으면 활성 표시도 같이 풀린다.
- **카드 포커스**(`.source-focused`, 테두리만): 원문 링크 활성과는 **독립된 별개 상태**다 — 카드가 여러 개일 때 "지금 어느 카드를 보고 있는지" 표시. 트리거는 **읽기 전용 카드(확정 후) 자체를 클릭**하는 것이다 — "원문에서 보기"는 원문 탭을 여는 것과 그 링크 자신을 활성화하는 것만 하고, 카드 포커스는 안 건드린다(하위 요소 클릭이 카드 레벨 상태까지 같이 바꾸지 않도록 분리, [관계 판정 화면](#관계-판정-화면)의 카드 선택과 같은 원칙). 편집 뷰(확정 전, 폼)는 클릭 포커스 대상에서 뺀다 — 텍스트 편집 클릭과 빈 공간 클릭을 구분하기 애매해서다. **화면 진입 시 기본으로 켜져 있지 않는다** — 첫 카드가 대부분 편집 뷰로 시작하는데, 거기에 기본값으로 켜두면 "원문에서 보기를 눌러서 켜졌다"는 착시(클릭과 무관하게 이미 켜져 있던 것)를 준다. 배타적(한 번에 하나만) — 여기도, 관계 판정 화면의 A·B 선택도 둘 다 배타적이지만 이유는 다르다: 여기는 "원문 탭이 한 번에 하나만 보일 수 있어서"고, 관계 판정 화면은 "충돌 관계는 A·B가 동시에 참일 수 없어서"다(아래 참고). **체크 배지는 안 붙인다** — 관계 판정 화면의 체크는 "내가 이걸 골랐다"는 판정 의미인데, 여기는 "원문 탭이 지금 이 카드 얘기"라는 추적 표시일 뿐이라 체크를 붙이면 실제로 없는 "선택했다"는 뜻이 생겨버린다.

**Reference 후보**: Digest 후보 목록과 이어지는 같은 문서형 톤(카드 폭·여백·테두리 없는 입력)으로 스크롤 전환 시 이질감이 없게 한다. 신규/기존을 알려주는 별도 배지는 없다 — 필드 구조 자체가 이미 구분해준다(신규는 "설명" 하나뿐, 기존은 "기존 설명"+"바뀔 설명" 두 라벨이 따로 있음). 같은 정보를 배지로 또 말하는 중복이라 뺐다.

Digest 후보와 마찬가지로 **확정되면 편집 폼에서 읽기 전용(`.digest-readonly`)으로 전환된다** — 확정된 Reference도 더 이상 편집 대상이 아니므로, 여기서도 "만질 수 있어 보이는데 안 만져지는" 상태를 그대로 두지 않는다. 신규는 타입 배지+제목+설명만 남고, 기존(짧은 설명·긴 설명 둘 다)은 "기존 설명"·"바뀔 설명" 두 필드의 diff가 사라지고 **최종 병합된 설명 하나만** 남는다 — git diff가 merge 후엔 그냥 새 파일 내용이 되는 것과 같다. 긴 설명(개념 문서류)은 확정 후에도 접기/펼치기를 유지한다 — Digest 판단 카드(짧은 구조화 필드라 접을 이유가 없어 뺐음)와 달리, 여기는 그대로 긴 산문이라 접어둘 이유가 여전히 있다.
- **신규**(레지스트리에 매칭 안 됨): 미니 생성 폼처럼 — 타입 배지 + 이름 + 설명, 전부 편집 가능.
- **기존**(레지스트리 매칭됨): 타입·이름 둘 다 읽기 전용이다 — 잘못 분류됐어도 그건 이 changeset 하나가 아니라 레지스트리 전체 그 엔티티를 재분류하는 무거운 조작이라, 이 가벼운 리뷰 흐름에서 다루지 않는다(별도 Reference 수정 흐름은 아직 미설계). "기존 설명"(읽기 전용)을 위에 참고용으로 보여주고, 그 아래 "바뀔 설명"(엔진이 제안한 병합 내용으로 미리 채워진 평범한 편집 필드)을 따로 둔다 — diff를 직접 편집 가능하게 만들진 않는다(그러려면 `contenteditable` + 실시간 재계산이 필요해 범위 밖). 위키피디아 리비전 비교·CRM 데이터 보강 승인 화면과 같은 패턴(비교는 읽기 전용, 편집은 별도 필드). diff 하이라이트(삭제될 부분은 줄 그어 흐리게, 추가될 부분은 밑줄+진하게)는 "기존 설명"이 짧든 길든 일관되게 적용한다 — 어느 기존 레퍼런스든 "뭐가 바뀌는지"를 같은 방식으로 보여줘야 하기 때문이다. 다만 접기/펼치기는 긴 글에서만 의미가 있다 — 개념(term) 문서처럼 긴 글이면 기본은 접혀있고 "더 보기"로 펼쳐야 diff가 드러나서(원문을 다시 읽는 부담을 기본 상태에서 없앰), 짧은 설명(예: 사람 한 줄 설명)은 접을 이유가 없어 항상 펼쳐진 채로 diff만 보여준다.

이 시점엔 Statement가 아직 없어 충돌 판정은 여기서 하지 않고, 관련 Digest도 여기서 안 보여준다(Digest 상세 참고). 확정하면 그 Changeset이 `closed`(`outcome: applied`)로 바뀌며 Statement·Relation 생성(2단계)이 시작된다 — 화면은 이동하지 않고 그대로 이 화면에 남아 상태 배지만 바뀐다(위 "확정·버리기" 참고).

## 변경셋

Space 오버뷰의 변경셋 탭. **Open / Closed** 서브 필터로 나뉜다 — GitHub PR과 같은 패턴(같은 Changeset이 거치는 두 생애주기 단계라 겹치지 않음), 탭 라벨도 GitHub 그대로 영문으로 표기한다. Open이 있으면 기본으로 그쪽이 선택된다(GitHub이 Open을 기본으로 보여주는 것과 동일).

행 구성은 둘 다 같다: **제목+번호 · 리뷰어/작성자 · 시각**(Digest 리뷰 화면 헤더의 "status | authorId | createdAt"과 같은 정보를 리스트 행으로 압축) — 상태는 행에 안 넣는다, 어느 서브탭에 있는지가 이미 상태를 말해주기 때문이다(초안 화면에서 "대기 중" 배지를 생략한 것과 같은 이유).

- **Open**: `status: open`인 Changeset. `open`이 가능한 건 `ingestion`·`relation`뿐이다 — `manual`·`revert`는 제출 시점에 바로 `closed`+`applied`로 생성돼 open을 거치지 않는다(lazy changeset creation, 07-modeling.md 참고). 클릭하면 `ingestion`은 [Digest 리뷰 화면](#digest-리뷰-화면)으로, `relation`은 충돌이면 [관계 판정 화면](#관계-판정-화면)으로, 중복이면 [관계 판정 화면(중복/병합)](#관계-판정-화면-중복병합)으로 실제로 이동한다.
- **Closed**: `status: closed`인 Changeset을 `outcome`(적용됨/버려짐) 구분 없이 다 보여준다 — 행마다 작은 outcome 배지로 구분한다(GitHub Closed 탭이 Merged·Closed를 배지로만 나누는 것과 같은 패턴). `discarded`를 숨기지 않는 이유는, 검토했다가 버린 이력 자체가 조용히 사라지면 nema 자신의 원칙(매끄러움이 아니라 충실함, 지난 것을 안 덮는다 — surface-design.md §2·§3)과 부딪히기 때문이다 — 버려도 원본(Source)은 "초안"에 남아 재료는 안 사라지지만, "검토했었다"는 사실 자체는 이 목록에서만 확인할 수 있다. `discarded`는 `ingestion`·`relation` 둘 다 있다 — `ingestion`은 리뷰를 버린 경우, `relation`은 엔진이 제안한 충돌·중복 자체가 틀렸다고("이건 실제로 충돌·중복이 아니다") 사람이 판단해 버린 경우다(그 쌍은 재제안 가드에 걸려 엔진이 다시 안 물어봄, 07-modeling.md 참고) — "진짜 충돌·중복이면 어느 쪽이 맞는지는 반드시 판정해야 한다"는 것과 "애초에 그 제안 자체가 틀렸을 수 있다"는 건 별개의 문제라서다. `revert`는 제출=즉시 적용이라 discard 자체가 성립하지 않는다. 클릭하면 [Changeset 상세](#changeset-상세)로 이동.

**`manual`은 Open·Closed 어디에도 안 뜬다** — 모델엔 그대로 있지만(07-modeling.md "Digest·Reference 직접 편집은 변경셋 목록에 안 뜬다"), 이 목록은 `ingestion`·`relation`·`revert` 셋만 보여준다. `manual`은 애초에 `open` 단계가 없어(만드는 사람=확정하는 사람) 이 목록의 핵심 가치("판정 대기 중인 걸 보여준다")가 안 맞기 때문이다 — 그 대신 각 Digest·Reference 자신의 미트볼(⋯) → "변경 이력"에서 자기 몫만 조회한다(위 Digest 상세·Reference 상세 참고). `number`(#N)는 `manual`도 같은 시퀀스를 공유하므로(화면에 안 보인다고 번호 체계까지 따로 두지 않음, GitHub PR·Issue가 번호를 공유하는 것과 같음) 이 목록에 번호가 띄엄띄엄(#2·#3·#4가 빠짐) 보이는 게 정상이다.

**타입 배지**도 outcome 배지 옆에 나란히 붙는다(Open·Closed 둘 다) — outcome 배지만으로는 "이게 ingestion인지 relation인지"가 제목 문구를 읽어야만 구분돼 스캔하기 약하다는 문제가 있었다. 타입 배지는 outcome 배지와 시각적으로 구분되도록 배경을 채운다(outcome은 테두리만). 값은 이 목록에 실제로 뜨는 3개 타입(`ingestion`/`relation`/`revert`)을 그대로 영문으로 쓴다.

**10개 케이스를 각각 확인할 수 있도록 행을 하나씩 둔다** — 화면 하나로 이 목록에 뜨는 3개 타입 × 상태·outcome 조합을 다 검증하기 위한 예시 목록이다:

| 상태 | 타입 | 케이스 |
| --- | --- | --- |
| Open | ingestion | 리뷰 대기 |
| Open | relation(충돌) | 판정 대기 |
| Open | relation(중복) | 판정 대기 |
| Closed | ingestion | 적용됨 |
| Closed | ingestion | 버려짐 |
| Closed | relation(충돌) | 판정 완료(적용됨) |
| Closed | relation(중복) | 판정 완료(적용됨) |
| Closed | relation(충돌) | 버려짐(제안 자체가 틀림) |
| Closed | relation(중복) | 버려짐(제안 자체가 틀림) |
| Closed | revert | 되돌림(적용됨) |

Open의 relation 두 행은 실제 판정 화면으로 이동한다 — 충돌은 [관계 판정 화면](#관계-판정-화면), 중복은 [관계 판정 화면(중복/병합)](#관계-판정-화면-중복병합). Closed 쪽 relation(충돌·중복) 적용됨은 그 판정 화면의 비교 카드를 그대로 스냅샷으로 얼려서 보여주고(Changeset 상세 참고), relation 버려짐 두 행은 "이 둘은 실제로 충돌·같은 내용이 아니라고 판단되어, 둘 다 그대로 유지됐다"는 안내만 보여준다(ingestion-discarded와 같은 톤). `revert`는 되돌려진 changeset(#12)이 만든 파생물이 다 archive되고 원본이 초안으로 돌아갔다는 요약 + 그 원본 changeset으로 가는 링크를 보여준다("되돌리기(append-only)" 원칙대로 되돌려진 changeset 자체의 스냅샷을 여기 또 얼려서 중복하지 않는다).

**"원본도 삭제하기" 버튼은 `ingestion` 버려짐 전용이다** — Closed 헤더의 [되살리기]는 outcome이 버려짐이면 타입 무관하게 다 뜨지만(위 "헤더는... 공통" 참고), 그 옆의 [원본도 삭제하기]는 `ingestion-discarded`에만 붙는다. `relation` 버려짐은 그 changeset의 트리거가 된 원본이 이미 `active`로 확정돼 있어야 2단계 판정 자체가 나온 것이라, 버려도 pending으로 남는 원본이 없기 때문이다(원본이 pending으로 남는 건 ingestion을 버렸을 때만의 특수한 결과).

**`discarded` 항목을 되살리는 흐름(재리뷰)** — Digest 리뷰 화면의 "버려짐" 헤더, Changeset 상세의 discarded 케이스 둘 다에 "되살리기" 버튼이 있다("원본도 삭제하기" 왼쪽, 더 건설적인 액션이 먼저 오도록). 새 changeset을 만들지 않고 같은 changeset의 status를 `open`으로 되돌린다(07-modeling.md "버려짐 되살리기" 참고) — 버리기가 한 일(상태 배지·헤더 액션 전환, "초안" 카운트 증가)을 정확히 반대로 되돌리고, 변경셋 목록에서도 그 행이 Closed에서 Open으로 실제로 옮겨간다. "원본도 삭제하기"를 먼저 누르면 되살리기 버튼도 같이 사라진다 — Source가 `trashed`가 돼 되살리기 조건(`pending`)이 깨지기 때문이다. 마찬가지로 "처리"(초안에서 처음부터 재추출)를 누르면 그 Source에 새 open changeset이 생겨 같은 이유로 되살리기가 막힌다.

초안 카드에 그 Source와 엮인 discarded changeset이나 revert changeset이 있으면(예: "메시지 전송 정책 재검토") "처리"·"삭제" 옆에 **"이전 리뷰 보기"** 링크가 추가로 붙는다 — 예전 상태를 다시 집어들지, 처음부터 새로 뽑을지(처리) 사용자가 선택할 수 있게 한다. 라벨은 하나로 통일하지만 실제 타겟은 다르다: discarded 유래면 그 discarded changeset(거기서 "되살리기"), revert 유래면 최신 revert changeset(거기서 "되돌리기" = 재적용) — 원래 applied였던 changeset 자체로는 안 보낸다(이미 한 번 되돌려진 걸 또 되돌리는 중복 액션이 되어서). 한 번도 처리 안 된 초안엔 이 링크가 없다(돌아갈 예전 상태 자체가 없어서). "처리"를 누르면 이 링크도 흐려지며 비활성화된다.

## 초안

LNB에서 진입(있을 때만 노출, Linear Drafts처럼 — 다 처리되면 LNB 버튼 자체가 없어짐). `Changeset`이 없이 `pending`으로 남은 Source 목록 — 리뷰를 버렸거나(changeset이 `closed`+`outcome: discarded`가 되며 Source는 계속 pending), 되돌려졌거나(적용된 changeset을 되돌리면 같은 방식으로 pending에 남음), 아직 1단계(추출) 처리 중이거나. Workspace 전역에서 모아 보여준다 — Source는 Space 스코프 데이터지만, 잘못된 Space에 들어간 걸 여기서 한눈에 보고 바로잡을 수 있어야 하기 때문이다.

**카드형**(리스트 아님) — Space 오버뷰의 Digest 피드 카드와 같은 시각 언어를 재사용한다. 카드 너비는 full-width가 아니라 고정 너비(좁은 화면에선 줄어듦) — 가로로 넓은 화면에서 카드가 늘어나면 footer의 시각·액션 버튼이 스니펫과 너무 멀어져 한 카드처럼 안 읽히기 때문이다.

카드 구성: **Space 셀렉트**(맨 위, 표시+변경 겸용 — Digest·Reference 타입 셀렉트와 같은 패턴이라 별도의 "Space 이동" 버튼을 안 둔다. Space를 여기서 바로잡는 게 가장 싼 시점이다 — 일단 처리가 끝나 그 Space 안에 Digest·관계가 쌓이면 옮기는 게 훨씬 무거운 캐스케이드가 된다) → **`Source.title`**(문서형 편집, 07-modeling.md 참고 — 초안에 머무는 동안만 편집 가능. 처리 중일 땐 Space 셀렉트·처리하기·완전히 삭제하기와 같은 이유로 잠김) → 본문 스니펫(+더 보기/접기) → 시각+액션.

상태는 **딱 하나만 구분한다: 지금 엔진이 처리 중이냐 아니냐.** "버려짐"·"되돌려짐"은 결과가 똑같이 pending 대기고 액션도 똑같아서(처리하기/완전히 삭제하기) 구분할 실익이 없다 — 초안에 있다는 사실 자체가 이미 "대기 중"을 말해주므로 별도 배지가 없다. 처리 중일 때만 "처리 중 ●" 배지(Space 오버뷰 피드의 "[진행중 ●]"와 같은 톤, 정확한 진행률을 모르는 작업이라 프로그레스 바 대신 가벼운 점 표시)가 뜨고, 이때는 Space 셀렉트·처리하기·완전히 삭제하기 셋 다 비활성화된다 — 엔진이 그 Space 맥락으로 한창 처리 중인데 옮기거나 지우거나 재트리거하면 앞뒤가 안 맞기 때문이다. 대신 **"취소"** 하나만 보여주고, 취소하면 진행 중이던 1단계 작업이 멈추고 평범한 대기 상태로 돌아가 나머지 액션이 다시 열린다.

평범한 대기 상태의 액션: **처리**(1단계 실행) / **삭제**(그냥 삭제 — Digest 리뷰 화면의 "원본도 삭제하기"와 같은 이유로 휴지통·보관 기간 문구는 노출하지 않는다). 버튼 라벨은 "-하기"도 붙이지 않고 짧게 둔다. 그 Source에 discarded changeset이나 revert changeset이 있으면(버려졌거나 되돌려진 이력이 있는 경우) 이 두 액션 왼쪽에 **"이전 리뷰 보기"** 링크가 추가된다 — discarded 유래면 그 changeset의 Changeset 상세로 이동해 "되살리기"(버리기 직전 편집 상태 그대로 복원), revert 유래면 최신 revert changeset의 Changeset 상세로 이동해 "되돌리기"(=재적용, archive됐던 Digest 복원)를 할 수 있다(아래 [변경셋](#변경셋) 참고). "처리"를 누르면 이 링크는 비활성화된다 — 새 open changeset이 생겨 되살리기 조건이 깨지기 때문이다.

## 휴지통

LNB에서 진입(항상 고정 표시). `trashed` 상태인 Source 목록과 남은 보관 기간(30일 중 며칠 남았는지)을 보여준다. Workspace 전역. 항목별로 복원(`pending`으로) 가능.

## Reference 상세 (사이드 패널)

Digest 상세와 같은 다중 탭 사이드뷰 시스템을 공유한다(위 "사이드뷰는 브라우저 탭처럼" 참고). 본문 안 `@` 멘션을 클릭하거나 [Reference 목록](#reference-목록)에서 엔트리를 클릭하면 열린다.

**읽기/편집 모드도 Digest 상세와 같은 패턴을 그대로 재사용한다**(`.detail-read-view` 공용 클래스, `body-edit-zone` 토글) — 다만 Reference는 Digest와 성격이 다르다. Digest는 확정 후 불변이라 수정하면 archive+create(옛 버전은 그대로 얼려두고 새 버전을 따로 만듦)인데, Reference는 **그 자리에서 계속 다듬어지는 레코드**다(glossary.md "관련 입력이 들어올 때마다 새로 쌓이지 않고 기존 것이 다듬어진다" — in-place update, archive+create가 아님). 그래서:
- 시간 필드가 "확정 시각"이 아니라 **"최종 수정: [날짜]"**(`updatedAt`) — Digest는 이 필드 자체가 없다(불변이라 "언제 수정됐는지"가 없음).
- 편집 제출 확인 모달 문구도 Digest용("기존 Digest가 archive되고 대체됩니다")과 다르게, "이 Reference의 설명이 지금 이 내용으로 **바뀝니다**. 이걸 인용하는 Digest들도 영향을 받을 수 있어요"로 간다.

**패널 헤더는 Digest와 같은 미트볼(⋯) 메뉴 패턴을 재사용한다** — "변경 이력"·"아카이브" 둘, 안전한 조회부터·위험한 액션은 한 단계 덜 보이게 두는 순서도 같다. 다만 Topic 브레드크럼·공유·원문 보기는 없다(우측 끝에 ⋯만) — Reference는 Topic에 안 묶이고, 원문도 여러 Digest가 각자 다른 시점에 인용하며 다듬어 하나로 못 좁혀진다.

**"변경 이력"도 Digest와 같은 좌(diff)·우(목록) 2단 모달**을 재사용한다 — 이 Reference를 대상으로 한 `manual` changeset(수정·아카이브) 목록, 우측 목록에서 항목을 클릭하면 화면 전환 없이 좌측 diff만 바뀐다. Reference는 필드가 "설명" 하나뿐이라 Digest보다 diff가 더 단순하다. 07-modeling.md에 정리된 대로 저장 방식은 이미 확정돼 있다(그 `manual` changeset들의 `Change` 기록 `{ before, after }`를 시간순으로 훑으면 재구성됨, 별도 버전 필드 불필요) — "최종 수정일"도 이 값들 중 가장 최근 것에서 파생된다.

**Reference 아카이브는 Digest보다 단순하다.** Digest 아카이브의 캐스케이드 엣지 케이스(위 참고)는 conflicts·duplicates 판정처럼 Statement 레벨 관계가 걸려 있어서 생기는데, Reference는 그런 관계의 끝점이 아니다 — 그래서 확인 모달에 조건부 체크박스가 없다. 문구도 다르게 간다: "아카이브하면 검색·멘션 추천 등에서는 안 보이지만, 이미 인용 중인 Digest에서는 계속 확인할 수 있습니다" — Digest처럼 "스레드" 개념이 없는 대신, 이미 본문에 멘션으로 박힌 Reference는 "안 지우고 가린다" 원칙대로 그 Digest 안에서 계속 읽힌다. **"다시 활성화"는 첫 구현(2026-07-21) 범위에 없다** — 아카이브(active→archived)만 우선 만들었고, 되돌리는 RPC·버튼은 후속 슬라이스로 미룬다. 그 전까지 아카이브됨 배너는 상태만 보여주고 액션이 없다. Reference 목록의 상태 필터(활성/아카이브됨/전체)로 발견은 가능하다.

**구성**: [타입 배지] 제목 → 최종 수정일 → 설명 → Tag(changeset 없이 가볍게 CRUD) → **인용하는 Digest (N)**.
- **인용하는 Digest**는 Digest 상세의 "관련 Digest"와 시각적으로는 비슷하지만 편집(×삭제·+추가)이 없다 — 본문 `@` 멘션에서 파생되는 역방향 목록이라 여기서 직접 편집할 대상이 아니다. 조건부(없으면 섹션 생략). 클릭하면 그 Digest 탭이 열린다(관련 Digest와 같은 메커니즘). Reference 삭제를 고려할 때 "지금 몇 개가 인용 중인지" 확인하는 자리이기도 하다(위 "Reference 삭제" 논의 참고). "변경 이력"은 이 본문 콘텐츠 흐름 안에 없다 — 위 미트볼 메뉴 참고.

## Reference 목록

Workspace 전체에서 재사용되는 대상(사람·조직 등)·개념을 모아 보여주는 목록. 같은 이름이라도 서로 다른 대상이면 별개 엔트리로 존재하며, 각 Statement는 문맥에 따라 올바른 엔트리에 매핑된다. LNB "WORKSPACE" 섹션에서 진입(Space가 아니라 Workspace 스코프임을 그 위치로 드러냄).

**Digest 피드와 달리 시간순 카드가 아니라 컬럼형 테이블이다** — Digest 피드는 "최근 뭐가 있었나"를 훑는 화면인데, Reference 목록은 그 대상을 다시 찾는 **사전·위키(찾아보기) 목적**이라 성격이 다르다. 정렬 기본값도 최신순이 아니라 **이름 가나다순**이다.

**컬럼**: 타입 · 이름(정렬 가능) · 상태 · 생성일(정렬 가능) — lean list, Changeset 목록의 기존 결정(#18 "listChangesets는 메타데이터 전용 유지")과 같은 패턴이다. 설명·태그·인용(N, 인용하는 Digest 수)·최종 수정은 애초 설계에 있었지만 `reference.list`가 메타데이터만 내려주는 계약으로 착지하면서 목록 컬럼에서 뺐다 — 행을 클릭하면 그 값들을 전부 보여주는 [Reference 상세](#reference-상세-사이드-패널)로 넘어가므로, 목록에 중복해서 만들지 않는다(design-decisions-log.md 2026-07-21 참고).

**필터는 검색(이름)·타입·상태 셋** — 태그 필터는 목록 응답에 태그가 없어 뺐다(위 lean list 조정과 같은 이유). 상태 필터(활성/아카이브됨/전체, 기본값 활성)는 아카이브된 항목을 다시 찾는 용도로 새로 추가했다. 정렬 가능 컬럼(이름·생성일)은 헤더를 클릭하면 활성 컬럼·방향(▾오름/▴내림) 표시와 함께 실제로 재정렬된다(기본값은 이름 가나다순). 인용·최종 수정 기준 정렬, "안 쓰이는 레퍼런스 찾기" 시나리오는 목록이 다시 풍부해지면 재검토한다.

**"+ 새 Reference" 같은 생성 진입점은 없다** — Reference는 `ingestion`(Digest 리뷰 화면의 후보 확정)에서만 만들어진다(07-modeling.md 참고). 이 화면에서 직접 새로 만드는 경로 자체가 모델상 없다.

(협업 확장 시 원칙: Reference 병합은 접근 권한이 일치하는 Space끼리만 허용하고, 권한이 다르면 중복을 허용한다 — 이력에 부분 가림이 생기는 걸 막기 위함)

## Changeset 상세

변경셋 탭(Closed)에서 행을 클릭하면 이동. **사이드 패널이 아니라 메인 뷰(base-screen)**로 뜬다 — Digest 리뷰 화면과 같은 급의 화면이라서(사이드 패널은 지금 보던 화면의 흐름을 안 끊기 위한 보조 열람 장치인데, Changeset 상세는 그 자체로 하나의 목적지다).

**Digest 리뷰 화면(액션 화면)과 짝을 이루는 기록 화면이다.** 처음엔 `ingestion` 타입에 한해 Digest 리뷰 화면 자체를 재사용(상태 배지만 바꿔치기)하는 방향을 검토했는데, 폐기했다 — 리뷰 화면의 편집 가능한 input·select·textarea가 그대로 남아있으면 "만질 수 있어 보이는데 실제로는 안 만져지는" 정직하지 못한 화면이 된다. 그래서 화면 자체는 별도로 새로 지었다. 다만 "읽기 전용 카드"(`.digest-readonly`, [Digest 리뷰 화면](#digest-리뷰-화면) 참고)는 결국 필요해졌다 — 관계 판정 화면을 만들면서 "확정된 Digest를 읽기 전용으로 보여준다"는 일이 여기(스냅샷 카드)·Digest 리뷰 화면(확정 직후 카드)·관계 판정 화면(A·B 비교 카드) 세 군데에서 똑같이 필요하다는 게 드러나서, 하나의 컴포넌트로 세 화면이 공유한다.

**헤더는 여기 뜨는 3개 타입(`ingestion`·`relation`·`revert`) 공통**: 제목+번호 · status(적용됨/버려짐) | 리뷰어/작성자 | 시각 — Digest 리뷰 화면 헤더와 같은 정보 구성이지만 여기선 편집 불가한 텍스트다. `manual`은 애초에 이 화면에 안 뜨므로(아래 "manual은 여기 없다" 참고) 이 타입 목록에서 뺐다. **"되돌리기"는 outcome이 discarded면 없다**(archive할 대상 자체가 없어서 — Digest 리뷰 화면의 "버려짐" 케이스와 같은 이유). 그 외 모든 `closed`+`applied`엔 **타입 무관하게 공통으로 붙는다** — 관계 판정도 잘못됐으면 되돌릴 수 있어야 한다는 원칙이다(surface-design.md "판정: 사람 주권"의 "진 쪽은 지우지 않고 가린다(보존·되살리기 가능)"이 relation 판정에도 그대로 적용돼야 한다는 논리 — ingestion 전용 기능이 아니다).

본문은 타입·outcome 조합(케이스)마다 다른 내용을 보여준다. **이번 라운드는 ingestion 두 케이스 + relation(충돌·중복) 다섯 케이스를 채웠다**:
- **ingestion 적용됨**: 그 changeset이 만든 Digest 목록을 읽기 전용 스냅샷으로 보여준다(git이 옛 커밋의 diff를 그 시점 파일 모습으로 보여주는 것과 같음 — 그 뒤 그 Digest가 또 수정(archive+create)됐어도 이 스냅샷은 갱신되지 않는다). 스냅샷 카드에 "Digest 상세에서 보기" 링크를 둬서, 이미 archive돼 지금은 안 보이는 옛 버전이어도 그 계보의 현재 살아있는 버전으로 바로 넘어갈 수 있게 한다.
- **ingestion 버려짐**: "아무것도 만들어지지 않았다"는 안내 + 원본이 남아있는 [초안](#초안)으로 가는 링크.
- **relation(충돌) 적용됨**: [관계 판정 화면](#관계-판정-화면)의 `.rj-digest-card`(A·B)를 그대로 재사용해서 **그때 뭘 놓고 비교했는지까지 얼려서** 보여준다 — 이긴 쪽만 보여주는 것보다 충실하다(진 쪽도 뭐였는지 알아야 "조용히 덮지 않는다"는 원칙에 맞음, surface-design.md §2·§3). ingestion-applied가 "무엇을 만들었는지" 보여주는 것과 달리, 여기는 "무엇을 놓고 비교해서 무엇이 이겼는지"가 판정의 결과다. 이긴 쪽 카드에 `.selected`(테두리+체크)가 고정으로 걸려 있지만 **클릭해도 안 바뀐다** — 선택 토글 JS는 관계 판정 화면으로만 스코프돼 있고, 여긴 그 순간을 얼려 보여주는 기록이라서다.
- **relation(충돌) 버려짐**: "이 둘은 실제로 충돌하지 않는다고 판단되어, 둘 다 그대로 유지됐다"는 안내(ingestion-discarded와 같은 톤 — 아무것도 안 바뀌었다는 사실 자체를 전달).
- **relation(중복) 적용됨**: [관계 판정 화면(중복/병합)](#관계-판정-화면-중복병합)의 결과물인 병합 Digest 스냅샷(`.digest-readonly`, "Digest 상세에서 보기"는 `tab-digest-merged`로 연결) + **원본이었던 A·B도 읽기 전용으로 같이 남긴다**(겹치는 부분 하이라이트 포함) — conflicts-applied가 진 쪽까지 얼려서 보여주는 것과 같은 이유다. ingestion-applied가 "무엇을 만들었는지"만 보여주는 것과 달리, 여긴 "무엇을 근거로 병합했는지"까지 남겨야 조용히 덮지 않는 게 된다.
- **relation(중복) 버려짐**: "이 둘은 실제로 같은 내용이 아니라고 판단되어, 둘 다 그대로 유지됐다"는 안내 — 다만 이 문구는 "사람이 중복이 아니라고 판단한" 경우 전용이다. 같은 `outcome: discarded`라도 "다른 병합에 먼저 흡수돼 이 판정 자체가 무효화된" 경우는 뜻이 다르므로 문구를 구분해야 한다(07-modeling.md "한 Digest가 여러 곳과 동시에 중복될 수 있다" 참고) — 이 케이스는 이번 라운드에 아직 안 채움.
- **revert**: 그 타입을 다듬을 차례가 오면 채울 스텁으로 남겨뒀다. 다만 헤더·되돌리기 버튼은 공통이라 지금도 정상 동작한다.

**`manual`은 여기 없다** — 처음엔 `manual`(Digest·Reference 직접 수정·아카이브)도 여기서 필드 diff·스냅샷으로 보여주는 케이스를 만들었었는데(새 버전 카드 안에서 바뀐 필드만 diff, Reference는 필드가 "설명" 하나뿐이라 더 단순, 아카이브는 대상 자체를 읽기 전용 스냅샷으로), 변경셋 탭이 `manual`을 걸러내기로 하면서(07-modeling.md "Digest·Reference 직접 편집은 변경셋 목록에 안 뜬다") 이 화면에 들어올 진입점 자체가 없어졌다. 그 diff 콘텐츠는 그대로 버리지 않고 [Digest 상세](#digest-상세-사이드-패널)·[Reference 상세](#reference-상세-사이드-패널)의 미트볼(⋯) → "변경 이력" 모달로 옮겨졌다 — 같은 컴포넌트(필드 단위 `diff-remove`/`diff-insert`, 타입 안 바뀐 케이스만 필드 diff로 충분·바뀌면 카드 두 벌로 따로)를 그 자리에서 그대로 재사용한다.

## 관계 판정 화면

`relation` changeset(충돌·중복)을 판정하는 액션 화면. **Digest 리뷰 화면과 짝을 이루는 구조**(헤더에 상태·리뷰어·시각·버리기·확정, 본문 카드는 표시·선택만) — 원래는 "Digest 상세 안의 판정 모드"로 잡았었는데 재검토했다. 두 Statement가 서로 다른 Digest·Source에서 올 수 있는데, Digest 상세는 "하나의 Digest를 보여주는 화면"이라는 정체성이 뚜렷해서 두 Digest를 나란히 비교하는 걸 욱여넣기 어려웠다.

**진입하면 사이드 패널(열려 있었다면)을 닫는다.** Digest 상세의 "리뷰 대기" 항목을 눌러 들어온 경우, 그 Digest를 "읽기" 수준으로 보여주던 옛 패널을 열어둔 채로 비교 화면까지 겹쳐 보이면 중복이다(비교 화면 자체가 A·B 내용을 이미 다 보여준다). 원문 대조가 필요하면 이 화면 안의 "원문에서 보기"가 새로 `tab-source-a`/`tab-source-b`를 연다. 판정을 마치고 다시 Digest 상세로 돌아왔을 때(별도 진입)에야 "대체됨" 결과를 보게 하는 편이, 판정 중간에 옛 패널이 배경에 떠 있는 것보다 명확하다.

**범위는 항상 정확히 한 쌍(A·B)이다** — 07-modeling.md의 "쌍 하나마다 별도의 relation 변경셋" 규칙이 이미 그렇게 정해준다. 한 Digest가 여러 건과 동시에 부딪혀도(예: B가 A1·A2 둘 다와 충돌) 화면 하나가 다 떠맡지 않고, Digest 상세의 "리뷰 대기" 목록이 항목별로 나열해 각각 독립된 화면으로 보낸다 — 안 그러면 "일부만 판정하고 나머지는 나중에" 같은 부분 판정을 changeset 하나로는 표현할 수 없다.

**헤더**: 제목("A vs B" 형태, `Statement` 내용 요약 — Digest 제목이 아니다. 07-modeling.md `Changeset.title` 규칙 참고. Digest 제목은 더 넓은 주제를 담을 수 있어서 그대로 쓰면 정작 뭐가 부딪히는지 안 보일 수 있다)+번호, status(리뷰 대기/적용됨/버려짐)+**충돌/중복 타입 배지**(변경셋 목록의 타입 배지와 같은 이유 — 제목 문구만으론 스캔하기 약함)+리뷰어(그 판정을 촉발한 새 Source의 제출자 — ingestion과 같은 단수 규칙, "두 Source의 제출자 두 명"이 아니다)+시각, [버리기][확정].

**본문**: A(먼저 확정돼 있던 Digest)·B(나중에 확정되며 충돌을 일으킨 Digest)를 **위아래로 스택**한다(나란히 2열도 검토했으나, 사이드뷰(원문 대조)까지 뜨면 이미 좁아진 메인 영역을 또 쪼개는 셈이라 폐기 — Git 계열 병합 도구가 표준으로 쓰는 나란히 배치보다, 세로 스크롤 위주인 이 와이어프레임의 기존 관습과 맞는 스택을 택했다).

카드 내용 자체는 **`.digest-readonly` 컴포넌트를 그대로 재사용한다** — Digest 리뷰 화면이 확정 직후 후보 카드를 전환하는 것, Changeset 상세의 스냅샷 카드와 정확히 같은 컴포넌트다("확정된 Digest를 읽기 전용으로 보여준다"는 같은 일이라 화면마다 따로 만들 이유가 없다). headline-row(타입 배지+제목)+작성자·시각(`Digest.authorId`+`Digest.createdAt`, 제목 아래 한 줄 — Digest 리뷰 화면의 리뷰어 표시와 같은 이유로 지금부터 명시. 지금은 혼자 쓰는 Space라 둘 다 같은 이름으로 재미없어 보이지만, 협업이 열리면 "누구의 판단과 누구의 판단이 부딪히는가"가 판정에 실질적인 맥락이 된다)+body-field×N(충돌을 일으킨 문장은 하이라이트). 접기/펼치기는 없다 — surface-design.md의 "하이라이트 주변 맥락 한 토막을 기본으로, 전체는 펼치기" 원칙은 길고 비정형적인 원문 텍스트를 위한 것이지, 이미 짧고 구조화된 Digest 본문까지 접어둘 이유는 아니다. 판단하려면 맥락이 처음부터 다 보여야 하는데 "더보기"가 오히려 방해가 된다.

**선택은 체크박스가 아니라 카드 전체 클릭이다** — "이 판단을 유지한다"는 뜻으로 카드를 클릭하면 선택 상태가 된다(기본은 둘 다 미선택, 자동 판정 금지 원칙 — surface-design.md "판정: 사람 주권" 참고). `.digest-readonly` 자체는 판정 액션을 모르는 순수 콘텐츠 컴포넌트라 체크박스 같은 판정 전용 UI를 안에 안 섞고, 그 바깥을 감싸는 카드 전체가 클릭 대상이 된다 — 작은 체크박스보다 클릭 영역이 넓고, "카드를 다 읽고 그 카드를 고른다"는 흐름과도 맞는다. 카드 안의 **"원문에서 보기"**(사이드 패널에 A·B 각자 독립된 탭으로 열림, 서로 다른 Source일 수 있어서)만 클릭 전파를 막아 제외한다 — 안 그러면 원문 보러 간 것뿐인데 선택이 같이 바뀌어버린다. 그 링크 자신은 클릭하면 독립적으로 활성(진하게) 표시되는데([Digest 리뷰 화면](#digest-리뷰-화면)의 원문 링크 활성과 같은 메커니즘), A·B가 서로 다른 탭을 가리켜서 둘 다 동시에 활성일 수 있다 — Digest 리뷰 화면의 하나의 공유 탭과 달리 여기는 배타적일 이유가 없다.

**A·B 선택은 배타적이다(라디오처럼 하나만)** — 충돌(conflicts) 관계는 애초에 A·B가 동시에 참일 수 없다는 뜻이라, 둘 다 체크되면 "둘 다 유지"라는 모순된 결과가 된다. "사실 둘 다 안 부딪힌다"는 케이스는 카드 체크가 아니라 아래 "버리기"가 따로 맡는다. 이미 선택된 카드를 다시 클릭하면 선택이 풀려 미결정 상태로 돌아간다.

선택 상태는 **테두리+좌상단 체크 배지**로 표시한다(테두리만은 아님) — [Digest 리뷰 화면](#digest-리뷰-화면)의 `.source-focused`도 테두리를 쓰지만 그건 "지금 원문 탭이 이 카드 얘기"라는 추적 표시일 뿐이라 체크는 안 붙인다. 여기는 실제로 "내가 이걸 골랐다"는 판정이라 체크까지 더해 구분한다 — 테두리만으론 은은해서 훑어볼 때 놓치기 쉽고, 무거운 판정 액션에는 애매한 신호보다 명확한 신호가 낫다. 배지는 카드 좌상단에 떠 있는 형태다 — 체크박스류 선택 표시는 관습적으로 좌측에 오고(메일함·파일 탐색기·할 일 목록 등), 실질적으로도 우측은 "원문에서 보기"가 이미 차지하고 있어 겹친다.

**버리기**는 헤더에만 있다 — "둘 다 유지"(엔진이 제안한 충돌 자체가 틀림)라는 뜻이라 어느 한쪽 카드에도 안 속하지만, 그렇다고 카드 밖에 별도 버튼을 하나 더 둘 이유는 없다(하나의 액션은 하나의 자리에만).

**archived 범위는 Digest 전체가 아니라 그 Statement 하나뿐이다** — 07-modeling.md `Relation.type: replaces`의 정의("진술의 폐기는 여기서 파생된다")가 이미 Statement 단위로 못박아 둬서, 확정해도 두 Digest 본문이나 그 안의 무관한 다른 문장은 전혀 안 건드린다.

**진 Digest 쪽 표시**: Digest 상세에서 그 Digest를 다시 읽었을 때, "리뷰 대기" 항목은 사라지고 별도의 "대체됨" 배너(배지+"[이긴 쪽 제목]으로 대체됨 →" 링크, 대체한 Digest 자신을 새 탭으로 엶)가 새로 뜬다. **본문 안 그 문장도 취소선으로 표시한다**(위 [Digest 상세](#digest-상세-사이드-패널)의 "판정이 끝나면" 참고) — 배너만으론 "본문 전체가 지났다"로 오해할 수 있어서, 정확히 어느 문장이 대체됐는지 그 자리에서도 짚어준다. 셋 다(항목 제거·배너·본문 표시) 조용히 덮지 않는다는 원칙(surface-design.md §2·§3) 때문에 필요하고, 이번 라운드에 실제로 배선했다.

**버려짐**: 카드는 그대로 남고(체크만 초기화), 헤더가 `[되살리기]`만 남는다 — **"원본도 삭제하기" 후속 버튼은 없다.** ingestion과 달리 relation이 트리거된 Source는 이미 확정·활성 상태라(초안에 있는 draft가 아님), "이참에 원본까지 지울까"라는 후속 제안 자체가 안 맞는다. 되살리기 가드 조건도 ingestion과 다르다 — ingestion은 "Source가 pending + open인 changeset 없음"인데, relation은 Source 상태와 무관하게 **"같은 Statement 쌍에 open인 relation changeset이 없을 때"**면 된다.

**진 Digest를 나중에 수정하면?** 실제 백엔드(`confirm_digest_edit`)를 확인한 결과: 대체됐던 관계 자체(A가 이겼다는 기록)는 그 Digest가 archive될 때 이미 archived였던 Statement를 다시 안 건드리므로 영구 보존된다. 새로 만든 Digest(B2)는 처음부터 다시 추출 대상이 되고, 그 원본 전체가 기존 활성 그래프와 다시 대조된다 — B2가 충돌 부분을 실제로 고쳤으면 아무 일도 안 생기고, 안 고쳤으면 같은 충돌이 새 relation changeset으로 다시 뜬다. **재제안 가드는 discarded(제안 자체가 틀렸다고 판단된 쌍)만 막아야 하고, applied(이미 판정 완료된 쌍)는 막으면 안 된다** — 판정 완료된 쌍을 시스템이 "예전에도 A가 이겼으니 이번에도"라고 조용히 재적용해버리면 자동 판정 금지 원칙과 부딪힌다. (이 가드가 실제로 그렇게 구현됐는지는 별도 확인 필요.)

이 화면은 **충돌 전용이다** — 중복(duplicates)은 판정 방식이 근본적으로 달라(아래 참고) 이 화면을 재사용하지 않고 별도 화면([관계 판정 화면(중복/병합)](#관계-판정-화면-중복병합))으로 분리했다.

## 관계 판정 화면(중복/병합)

`relation` changeset(duplicates)을 판정하는 액션 화면. 위 [관계 판정 화면](#관계-판정-화면)(충돌)과 트리거는 같다("엔진이 감지한 Statement 관계에 대한 판정") — 하지만 conflicts를 그대로 재사용하려 했다가 폐기했다: conflicts는 A·B가 동시에 참일 수 없어 "하나를 고르고 나머지는 archive"가 맞는데, duplicates는 겹치는 진술 하나가 같을 뿐 각자의 나머지 내용(상황·이유·트레이드오프 등)은 고유한 정보라, 그대로 "고르기"를 적용하면 고르지 않은 쪽의 고유한 내용이 통째로 사라진다. 그래서 **"고르기"가 아니라 "병합"** — 겹치는 진술은 하나로 합치고 나머지는 살리는 새 Digest를, 엔진이 미리 만들어서 제안하고 사람이 검토·수정·확정한다.

**모델**: 새 changeset 타입은 필요 없다 — `Changeset.type`은 지금까지 일관되게 "왜 이 changeset이 생겼나"(트리거) 기준이지 "변경 내용이 얼마나 무거운가" 기준이 아니었다(`manual` 안에서도 Digest 수정·삭제·Reference 수정이 서로 다른 모양이지만 다 `manual`인 것과 같다). duplicates도 트리거가 conflicts와 같으니(엔진이 Statement 관계를 감지해 판정을 요청) 여전히 `relation` 타입이고, 다른 건 `changes`의 모양뿐이다(conflicts는 진술 하나 `replaces`, duplicates는 Digest 둘 archive + 하나 create).

**병합 제안은 즉시(eager) 생성된다** — 중복이 감지되는 2단계 시점에 엔진이 병합 Digest 초안까지 같이 만들어 changeset에 담아둔다(ingestion의 1단계 추출과 같은 결 — 사람이 화면을 열기 전에 이미 끝나 있음). 사람이 판정 화면을 여는 순간 그때 LLM을 불러 생성하면, 이 와이어프레임 전체에서 한 번도 없었던 로딩 상태가 이 화면에만 생겨 일관성이 깨진다.

**겹치는 정도로 메커닉을 나누지 않는다** — 처음엔 "Digest 전체가 겹치면 병합, 진술 하나만 겹치면 conflicts처럼 그 진술만 archive"로 나누는 안을 검토했는데 폐기했다. "얼마나 겹쳐야 전체냐"를 시스템이 정확히 계산할 방법이 없고, 이 화면 자체가 사람이 검토·수정·거절할 수 있는 리뷰 화면이라(Digest 리뷰 화면의 후보 카드와 같은 성격) 엔진이 만든 병합 제안이 무관한 내용까지 억지로 합친 이상한 모습이면 사람이 그 자리에서 고치거나 "버리기"로 거절하면 된다 — 판단을 시스템이 미리 정확히 하는 대신 사람이 매번 리뷰하며 하는 쪽을 택했다.

**재제안 가드는 discarded만 필요하다** — conflicts와 같은 이유(내용이 안 바뀐 채로 다시 비교되면 같은 제안이 또 뜨는 걸 막아야 함)로 버려진(중복 아님) 쌍은 가드가 필요하다. 반대로 applied(병합 완료)는 별도 가드가 필요 없다 — conflicts는 진 진술이 archived 상태로나마 원본 Digest에 남아있어 그 Digest가 나중에 수정되면 재비교 대상이 될 수 있는데, duplicates는 병합되는 순간 A·B의 Digest 자체가 둘 다 archive되니 비교할 "그 A·B"가 활성 상태로 더 이상 존재하지 않아 구조상 이미 막혀 있다.

**소유(authorId)**: 리뷰어는 conflicts와 같은 규칙(나중에 제출된 쪽=B의 제출자) — "원작성자(A) 동의가 필요한가"는 아직 없는 협업 권한 규칙(07-modeling.md "열어두는 것")에 편입시키고 지금은 단수 리뷰어 규칙을 그대로 쓴다. 병합된 새 Digest의 `authorId`는 **확정한 사람**(=리뷰어)이 된다 — manual Digest 수정에서 "archive+create"의 새 버전이 원 작성자가 아니라 그 수정을 확정한 사람의 것이 되는 것과 같은 논리다.

**제목**: "A vs B" 형태가 아니다(대립 프레임이 병합에 안 맞음) — **이 changeset의 결과물인 병합 제안 Digest 자신의 제목**을 changeset 제목으로 그대로 쓴다. conflicts는 결과물이 없어(Statement 관계 조정뿐) 별도 요약이 필요했지만, duplicates는 결과물(병합 Digest)이 있으니 그 제목을 재사용하면 충분하다. "중복"이라는 사실 자체는 헤더의 `rm-kind-badge`가 이미 말해주므로 제목에 "병합"을 또 넣지 않는다. **헤더 제목은 읽기 전용 — 실제 편집은 병합 제안 카드의 제목 입력 하나뿐**이고 헤더는 그 값을 그대로 따라간다(유일한 결과물의 제목을 두 군데서 각각 편집하게 두면 중복이라서).

**본문 레이아웃**: 병합 제안(가장 위, 크고 편집 가능) → "원본 (2)" 라벨 → A·B 참고 카드(작고 읽기 전용).
- **병합 제안**: Digest 리뷰 화면의 후보 카드와 같은 편집 폼(타입 전환·본문 필드 편집·@ 멘션) — 엔진 제안을 사람이 고칠 수 있어야 한다는 원칙이 여기도 그대로 적용된다. 가장 눈에 띄어야 할 유일한 작업 대상이라 위쪽에, 크게 둔다.
- **A·B 참고 카드**: `.digest-readonly` 재사용(다른 3개 화면과 같은 컴포넌트) — "왜 이 병합이 제안됐는지" 확인하는 용도라 위계가 낮다. **겹치는(같은) 부분을 하이라이트**한다 — conflicts의 하이라이트(서로 어긋나는 부분)와 정반대 의도라 클래스명을 분리했다(`rm-overlap-highlight`). 병합 제안 카드 자체엔 하이라이트가 없다 — 이미 하나로 합쳐진 상태라 "뭐랑 뭐가 겹치는지" 보여줄 대상이 없어서다.

**"대체됨" 대신 "병합됨"**: Digest 상세에서 A·B를 다시 읽었을 때, conflicts처럼 진 쪽 하나만이 아니라 **A·B 둘 다**에 표시가 필요하다(둘 다 archive되므로). 배너 문구도 "대체됨"이 아니라 "병합됨 — [새 Digest 제목]으로 병합됨 →"으로 다르게 간다 — conflicts의 "대체됨"은 "이 판단은 틀렸다/밀렸다"는 뜻인데, duplicates는 진 쪽이 틀린 게 아니라 그냥 같은 말이 중복으로 남지 않게 정리된 것뿐이라 같은 문구를 쓰면 오해를 줄 수 있다. **본문 안 인라인 취소선은 안 쓴다** — conflicts는 Digest 안의 특정 필드 하나만 밀려난 거라 그 문장만 짚는 게 의미가 있었지만, 병합은 Digest 전체가 archive되는 거라 특정 문장을 짚기보다 배너로 "이 Digest 전체가 새 Digest로 흡수됐다"를 전달하는 게 더 정확하다.

**Thread(Topic 필터) 안에서는 A·B 둘 다 완전히 안 사라진다** — 07-modeling.md "Thread는 archived Digest 제외 규칙의 예외" 참고. archive된 A·B는 원래 있던 시간 순서 그 자리에 접힌 채로 남고, 새로 만들어진 병합 Digest는 지금 시점 자리에 따로 나타난다 — 어느 한쪽으로 옛 버전을 흡수·이동시키지 않고 두 자리에 나눠 보여주는 절충이다(manual Digest 수정도 같은 archive+create 구조라 똑같이 적용됨).

**새 화면으로 분리한 이유**: `screen-relation-judgment`에 조건 분기로 욱여넣지 않고 `screen-relation-merge`라는 별도 base-screen을 만들었다 — 레이아웃도 액션도 완전히 다르다(읽기 전용 비교+선택 vs 편집 가능한 병합 초안 검토). Changeset 상세를 Digest 리뷰 화면에서 분리했던 것과 같은 이유다.

## Space 설정 모달

LNB에서 새 Space를 만들거나 기존 Space의 이름을 바꿀 때 쓰는 가벼운 모달 — Space 모델 필드가 `name` 하나뿐이라(07-modeling.md 참고) 입력값도 그만큼 가볍다. 생성 목적으로 열면 이름을 비우고 만들 수 있고(비우면 "새 Space"로 대체 — Source에 title 없이도 가볍게 넣을 수 있게 한 것과 같은 최소 마찰 원칙, 별도 인라인 검증 에러는 안 둠), 생성하면 LNB SPACE 목록에 새 항목이 추가되고 그 자리에서 바로 그 Space로 전환된다(기존 Space 전환과 같은 경로 재사용 — 사이드뷰 닫기·활성 표시 전환 포함). 이름 변경 목적으로 열면 기존 이름이 채워진 채로 열리고, 저장하면 그 Space의 이름만 갱신된다(전환·사이드뷰 닫기는 일어나지 않음). 아이콘·색상·삭제 같은 관리 기능은 필요성이 커지면 별도 설정 화면으로 확장을 고려한다.

## 계정 설정 (오버레이)

LNB 최상단(Workspace 이름)을 클릭하면 뜨는 작은 드롭다운. User 프로필(아바타·이름·이메일)을 보여주고, 그 아래 **설정**·**로그아웃** 순으로 액션이 있다 — LNB엔 Workspace 이름만 상시 노출하고 프로필은 여기서만 드러난다. "설정"을 누르면 아래 [설정 모달](#설정-모달)이 뜬다. 결제는 MVP에서 수동 처리라 이 드롭다운엔 "플랜"·"결제" 항목이 없다.

## 설정 (모달)

계정 드롭다운의 "설정"에서 연다. **좌측 섹션 내비 + 우측 콘텐츠**의 2단 구조(Slack·Notion류 설정 창 관습) — [Digest·Reference 상세의 "변경 이력" 모달](#digest-상세-사이드-패널)과 같은 컴포넌트 골격(목록/내비가 클릭될 때마다 콘텐츠 쪽만 바뀌는 방식)을 재사용하되, 좌우 배치는 반대다(변경 이력은 우측이 목록, 여긴 좌측이 내비 — 그래서 클래스는 따로 선언, 이 문서 전반의 "화면마다 다시 선언" 관례와 같음). 열릴 때마다 "일반" 섹션부터 보인다.

- **일반**: Theme(라이트/다크/시스템 설정 따르기), 앱 언어(한국어/English — Tolgee가 서빙하는 UI 언어), 콘텐츠 언어(`profiles.content_language` — 붙여넣는 원문 언어와 무관하게, 저장된 내용을 어떤 언어로 정리해줄지 사용자가 고르는 축). 앱 언어와는 서로 다른 축이라 나란히 두되 별개 설정으로 노출한다.
- **계정**: User 프로필(아바타·이름·이메일)을 표시하고, 그 아래 **계정 삭제** 진입점을 둔다. 로그아웃은 이미 [계정 설정 (오버레이)](#계정-설정-오버레이)가 담당하므로("하나의 액션은 하나의 자리에만") 여기서 다시 두지 않는다 — 이 섹션은 계정 정보 조회와 계정 삭제만 맡는다. **계정 삭제**는 확인 단계를 거치는 위험 액션이고, 실행하기 전에 유저가 속한 워크스페이스마다 처리가 갈린다: 유저가 유일한 멤버인 워크스페이스는 계정과 함께 완전히 삭제되고, 다른 멤버가 있는 워크스페이스는 유지된 채 이 유저의 멤버십만 빠진다. 다만 **다른 멤버가 있는데 이 유저가 유일한 소유자(owner)인 워크스페이스가 하나라도 있으면**, 삭제 액션에 앞서 소유권 이전이 필요한 워크스페이스 목록이 먼저 안내되고, 그게 남아 있는 한 삭제 자체가 진행되지 않는다(게이팅 — 소유자 없는 워크스페이스가 남는 걸 막기 위함). 확인 단계에서 취소하면 아무것도 삭제되지 않고 이 계정 섹션으로 돌아온다. 게이팅이 걸릴 워크스페이스가 없어 삭제가 실제로 실행되면, 위 워크스페이스 정리가 끝난 뒤 로그아웃 상태로 [로그인](#로그인) 화면으로 나간다.
- **MCP 연결**: 연결된 MCP 클라이언트(Claude Desktop, Cursor 등) 목록 + 각각 "연결 해제". **"+ 새로 연결" 진입점은 의도적으로 없다** — MCP 연결은 항상 외부 클라이언트 쪽에서 먼저 시작해 nema로 리다이렉트되는 OAuth 플로우다(GitHub App을 GitHub 안이 아니라 그 앱 쪽에서 설치를 시작하는 것과 같은 구조). 그래서 이 화면은 조회·해제(관리)만 담당하고, 새로 연결하는 화면(OAuth 동의)은 nema가 직접 그리는 화면이 아니라 그 흐름의 일부로만 스쳐 지나간다. "연결 해제"는 가볍고 되돌리기 쉬운 액션(그 클라이언트 쪽에서 다시 연결하면 그만)이라 확인 모달 없이 바로 처리된다.
- **Billing은 지금 안 넣는다** — 좌측 섹션 내비 구조라 나중에 필요해지면 항목 하나만 추가하면 되는 형태로 미리 만들어뒀다.

## 묻기·해설

LNB에서 접근하는 전역 질문 화면. ChatGPT·Perplexity 같은 챗 인터페이스를 따라 입력창과 답변이 한 화면에서 대화형으로 이어진다. 질문을 던지면 Space를 가로질러 Statement·Relation·Digest·Reference를 검색하고, 그 결과를 Narration(산문 답)으로 보여준다.

일반 AI 챗봇과 다른 점: 답변의 모든 문장에 사용자 자신의 과거 Statement를 가리키는 근거 핸들이 달리고, 충돌이 있는 Digest는 클릭하면 Digest 상세 사이드 패널이 열려 대화 흐름을 유지한 채 그 자리에서 판정할 수 있으며, 근거가 없으면 지어내지 않고 명시적으로 모른다고 표시한다.
