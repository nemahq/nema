# 정보 구조: 넣기 표면과 공유 확정 게이트 (NEM-157 Track A)

> **⚠️ Legacy — 재설계 필요 문서**
>
> 이 문서는 v1.5 넣기 구현(초안 페이지·제목/주제만 확정·인박스) 당시의 설계 기록이다. 이후 Source→Digest→Reference 모델(`docs/guides/glossary.md`, `docs/blueprints/first-product/surface-inventory.md`)로 넣기 흐름 자체가 바뀌면서, 이 문서의 사이트맵·확정 게이트·인박스 설계는 지금 구조와 맞지 않는다.
>
> - "지도"는 Space 오버뷰로 대체됐다(`surface-design.md` §4 참고).
> - 확정 단위가 "제목·주제"에서 "N개 Digest(Topic·Tag·타입별 구조화 본문 포함) + N개 Reference"로 바뀌었다(`surface-inventory.md`의 Digest 리뷰 화면 참고).
> - 새 모델 기준의 넣기 IA는 아직 재설계되지 않았다. 그 전까지 이 문서는 참고용 역사 기록으로만 남긴다.

> 앱의 넣기 표면, 공유 확정, 초안 인박스를 세우는 슬라이스의 설계. 화면 픽셀이 아니라 정보 구조(IA), 유저 플로우, 지면과 그 연결을 못박는다. 거친 글이 깎여 초안으로 대기하고, 사람이 확정해 기억이 되는 한 바퀴의 앱 쪽 조각이다.

이 문서는 구조 청사진이다. 화면 레이아웃과 카피는 뒤 단계의 몫이고, 여기서는 어떤 지면이 있고 어떻게 이어지는지까지만 정한다.

## 기대는 개념 (자세한 정의는 `docs/guides/glossary.md`)

- 초안(draft): 확정 전 대기하는 글. 두 입구(앱·MCP)가 공유하고, 사람과 AI가 공동 편집한다. 용어 사전 v2의 다이제스트(Digest)와는 다른 자리다(draft는 원본 승격 전, 다이제스트는 원본 이후).
- 원본(source): 확정된 초안이 승격된 원재료. 진술이 여기서 추출된다.
- 주제(topic): 원본에 붙는 평평한 단일 라벨(0..N, 무태그 허용). 같은 주제가 붙은 원본들의 묶음이 한 줄기다.
- 줄기: 한 주제로 묶인 맥락 한 갈래. 주제 하나 = 줄기 하나. 사용자 눈엔 자기가 다루는 주제·프로젝트 하나로 보인다. 용어 사전 v2의 스레드(Thread)를 이 문서에서는 줄기로 적었다.

## 함께 보는 문서

- 콘텐츠 입구(`docs/archive/content-intake-design.archive.md`): Track 0가 깐 계약(draft·topic 라우터, 확정 게이트 백엔드)을 정한 문서. 이 문서는 그 계약 위에 앱 표면을 얹는다.
- 해설(`docs/blueprints/first-product/narration-design.md`): 다시켜기의 묻기 표면. 이 문서는 해설을 배경으로만 다루고, 넣기가 그 옆에 어떻게 앉는지까지만 본다.
- MCP(`docs/blueprints/first-product/mcp-design.md`): 외부에서 올리기 입구. 이번 라운드는 읽기 전용이고, 넣기와 초안·확정 게이트를 공유한다.
- 첫 제품 방향(`docs/foundations/11-first-product-direction.md`, 이하 방향 문서): 누구에게 무엇부터 만드는지 정한 문서. 아래에서 "방향 문서 §4"처럼 가리킨다.
- 표면 설계(`surface-design.md`): 사용자 여정으로 본 표면 전체의 우산 문서. 이 문서의 사이트맵 중 지도의 역할과 재방문 진입 동선을 거기서 개정한다(지도를 눌러 해설로 가는 허브에서 줄기 현황판으로, 재방문 주 진입을 지도에서 묻기로). 아래 사이트맵은 그 개정 전 그림이다.

## 0. 이 문서가 정하는 것 / 정하지 않는 것

- 정한다: 출발점(무엇을 세우나), 세 목표와 전체 IA, 넣기 플로우의 지면과 연결, 초안 페이지와 인박스의 정체, 확정과 그 후의 책임 경계, v1 철거 범위.
- 정하지 않는다: 화면 레이아웃과 시각 디자인(weave 룩으로 뒤 단계에서). 사용자 노출 카피(ux-writing 규칙 + Tolgee에서). 지도·해설·안전장치의 내부 설계(각 슬라이스의 몫, 여기서는 윤곽과 연결 지점만). 엔진의 추출·잇기(save-engine의 몫).
- 전제: 지금 구현된 화면은 v1이고 v2에서 새로 만든다. 기존 프론트엔드 재사용에 매이지 않는다. 단 Track 0 계약, weave 디자인 시스템, 인증·공간 셸은 받침으로 그대로 쓴다.

## 1. 출발점

우리가 세우는 것은 v1 채팅 화면을 손보는 일이 아니다. 거친 글이 한 방에 깎여 공간 단위 초안으로 모이고, 사람이 확정해 기억으로 올리는, 세션과 분리된 가벼운 넣기 표면이다.

근거 셋.

- 세션 독립은 기획이 아니라 박힌 데이터 사실이다. `drafts`에 session_id가 없다. 초안은 공간 단위로 존재한다. 그러니 "어느 세션에서 넣나"는 질문 자체가 성립하지 않는다.
- 넣기와 다시보기는 다른 순간이다. 방향 문서가 세션 표면의 미래를 re-entry(해설)로 넘겼다. 이번 트랙은 넣기다.
- 이 조각의 무게중심은 입력창이 아니라 확정이다. 앱이든 MCP든 어느 입구로 들어온 초안이든, 사람이 확정해야 기억이 된다.

## 2. 목표와 전체 IA

### 2.1 세 목표

방향 문서 §4의 하루를 목표로 추리면 셋이다.

1. 넣기: 외부 LLM 결론이나 직접 쓴 거친 글을 기억에 쌓는다.
2. 다시켜기: 지도로 큰 그림을 잡고, 줄기를 눌러 해설로 특정 맥락을 푼다.
3. 내보내기: 복원한 맥락을 외부 LLM으로 가져가 사고를 이어간다.

여기에 "사람의 판정"이 횡단으로 박힌다. 독립 목표가 아니라 넣기와 다시켜기를 가로지른다. 넣기에선 "넣기" 버튼(확정)이고, 다시켜기에선 충돌 판정이다. 방향 문서 §3-4의 "사람이 쥐는 건 입력이 아니라 판단의 갈림길"이 이 자리다.

### 2.2 전체 사이트맵

```
                          ┌──────────────┐
   앱 열기 ──────────────→ │     지도      │  허브 · 첫 화면 (줄기 목록)
                          └──────┬───────┘
            ┌────────────────────┼────────────────────┐
       줄기 눌러 묻기          "맥락 넣기"          "확정 대기 N개"
            │                    │                    │
            ▼                    ▼                    ▼
        ┌────────┐        ┌──────────┐         ┌──────────┐
        │  해설   │        │ 초안 페이지 │ ◀─초안 열기─ │  인박스   │
        └───┬────┘        └─────┬────┘         └──────────┘
      ┌─────┼─────┐             │
      ▼     ▼     ▼         "저장(넣기)"
  원본보기 충돌판정 가져가기        │
  (출처)(안전장치)(내보내기)   엔진 추출 → (충돌 시 충돌판정으로)
```

### 2.3 지면 목록과 책임 경계

| 지면 | 목표 | 누구 몫 |
| --- | --- | --- |
| 지도 | 다시켜기 (허브) | 지도 슬라이스 |
| 해설 | 다시켜기 | 해설 슬라이스 |
| 원본 보기 | 다시켜기 (출처 되짚기) | 해설 슬라이스 |
| 충돌 판정 | 안전장치 | 안전장치 슬라이스 |
| 초안 페이지 | 넣기 | 이번 트랙 |
| 인박스 | 넣기 | 이번 트랙 |
| 내보내기 | (해설에 붙는 출구, 지면 없음) | NEM-161 |

지도가 허브다. 모든 가지가 여기서 뻗고 일이 끝나면 여기로 돌아온다. 이번 트랙이 짓는 건 초안 페이지와 인박스 둘뿐이고, 둘 다 자기완결 라우트다. 지도가 두 입구("맥락 넣기", "확정 대기 N개")를 꽂는 일은 지도 슬라이스 몫이라, 그때까지 우리는 임시 진입점으로 둔다.

## 3. 넣기 플로우

### 3.1 입구는 둘, 지면은 둘

입구는 둘이다. 목표는 하나지만 경로가 갈린다.

- 앱 내: 거친 글을 직접 쓰거나 붙여넣는다. 이번 트랙.
- 외부에서 올리기(MCP): 외부 LLM이 다듬은 결론을 올린다. 본문 재가공 없음. 병렬 트랙.

지면은 둘이다.

- 초안 페이지: 쓰고, 정리하고, 검토하고, 저장하는 한 곳.
- 인박스: 확정 대기 초안 목록. 두 입구가 모이는 대기 저장소.

### 3.2 단일 초안 페이지 (입력 화면을 따로 두지 않는다)

입력 화면을 따로 두고 초안 화면으로 넘기는 전환은 어색하다. 대신 초안 페이지 하나가 입력부터 저장까지 맡는다. 이 페이지는 일반 메모 화면처럼 사람이 직접 기록할 수 있고, 그 안에서 세 방식이 같은 표면을 공유한다.

```
"맥락 넣기" → 초안 페이지 (메모 에디터)
                ├─ 사람이 직접 쓴다             ← 기본
                ├─ MCP로 외부 LLM이 써서 올린다
                └─ 어시스턴트를 불러 한 번 정리시킨다
              검토 후 "저장(넣기)" → 엔진이 진술·관계 추출
인박스 ─────→ 초안 페이지 (기존 초안 열기)
```

### 3.3 계약 매핑 (Track 0)

| 동작 | 계약 |
| --- | --- |
| 페이지 열기 (빈 초안) | `draft.create` |
| 페이지 열기 (기존 초안) | `draft.get` |
| 직접 쓰기 (수정) | `draft.edit` |
| 어시스턴트 한 번 정리 | `draft.assist` |
| 저장(넣기) | `draft.confirm` |
| 인박스 목록 | `draft.list` |
| 주제 재사용 | `topic.list` |

## 4. 초안 페이지

### 4.1 사람이 다루는 것

초안 페이지에서 사람이 만지는 것은 본문, 제목, 주제다. 본문은 통짜로 검토하고 수정한다. 진술로 쪼개진 모습을 보는 게 아니다. 제목은 저장 시 필수가 되고, 주제는 0..N개(무태그 허용, 레지스트리 재사용)로 확정한다.

### 4.2 저장이 곧 확정이다

별도의 확정 게이트 단계는 없다. 검토하던 화면에서 "저장(넣기)"을 누르는 순간이 확정이다. 그 클릭이 `draft.confirm`이고, 제목과 주제는 그때 확정된다. 그 전까지는 어시스턴트가 채워둔 제안이거나 사람이 쓰던 초안일 뿐이다.

페이지에서 나가는 길은 둘이다.

| 출구 | 계약 | 결과 |
| --- | --- | --- |
| "저장(넣기)" | `draft.confirm` | 제목·주제 확정 + 승격(추출 시작). 비가역 |
| 그냥 둠 / 나중에 | `draft.edit` 또는 미저장 | 초안으로 인박스에 머묾. 되돌릴 수 있음 |

### 4.3 어시스턴트는 한 번 정리하는 도구다

앱 입구의 어시스턴트는 거친 글을 한 번 깎아 초안으로 만드는 한 방짜리다(`draft.assist`). 미저장 상태에서 정리를 부르면 그게 곧 초안 생성이라 계약과 자연스럽게 맞는다. 사람은 그 결과에서 잘못 잡힌 데만 직접 고친다.

대화형 어시스턴트(주고받으며 반복 교정)는 이번 범위 밖이다. 근거는 방향 문서 §6이 "nema 안에서 직접 사고하게 돕는" 길을 외부 LLM을 쓰지 않는 사람까지 넓힐 때로 미뤘고, §9-3이 "초안을 한 번 더 다듬는 길"을 도우미 품질을 보고 정한다며 조건부로 열어둔 데 있다. 대화로 다듬는 욕구는 외부 입구(MCP)가 충족한다. 외부 LLM에서 대화로 깎은 결론을 올리면 된다. 자세한 갈래는 9장에 미결로 둔다.

### 4.4 MCP도 같은 표면을 공유한다

"MCP로 쓴다"는 외부 LLM이 실시간으로 이 페이지에 타이핑하는 게 아니라, `draft.create`로 초안을 만들어 인박스에 올리는 것이다. 사람이 나중에 그 초안 페이지를 열어 검토하고 확정한다. 사람·MCP·어시스턴트가 같은 초안 페이지 표면을 공유하되, 동시 실시간 협업은 이번 범위가 아니다.

## 5. 인박스

인박스는 확정 대기 초안의 저장소다. 두 입구가 모이지만 관계가 비대칭이다. 앱 내 초안은 보통 만들고 바로 저장해 인박스를 스쳐가고, 외부에서 올라온 초안은 인박스에 머물다 사람이 집어든다.

위상은 넣기와 다시켜기에 걸친다. 단순히 둘 다가 아니라 역할이 갈린다.

- 발견은 다시켜기 쪽이다. 사람이 인박스를 마주치는 순간은 앱을 다시 열었을 때다. 그래서 입구는 지도에 박힌다("확정 대기 N개").
- 처리는 넣기 쪽이다. 그 신호를 눌러 인박스 목록에서 초안을 골라 초안 페이지로 가서 확정한다.

이번 트랙은 처리(인박스 목록 + 초안 페이지)를 자기완결로 짓고, 발견 입구는 지도 슬라이스가 나중에 꽂는다.

## 6. 확정과 그 후

"저장(넣기)" 이후는 사람 손을 떠난다. `draft.confirm`이 `create_source`로 본문을 원본으로 박제하고 워커를 깨운다. 엔진이 비동기로 본문에서 진술을 추출하고, 임베딩하고, 기존 기억과 잇는다. 충돌이나 애매한 것은 pending changeset이 되어 나중에 다시켜기 쪽 안전장치에서 부딪히는 것만 콕 집어 사람에게 온다. 평상시엔 백그라운드에서 조용히 돈다.

진술 추출을 사람이 확정 시점에 보지 않는 것이 의도다. 방향 문서 §4의 "가볍게", §3-2의 "틀릴 만한 것은 자세히 단정하지 않는다"가 근거다. 사람 주권은 제목·주제를 확정하는 가벼운 게이트에 있지, 진술 검수에 있지 않다.

## 7. 배경 윤곽 (의존·연결 지점)

다시켜기와 내보내기는 다른 슬라이스다. 여기서는 넣기가 의존하거나 연결되는 지점까지만 둔다.

- 지도: 다시켜기의 첫 화면이자 허브. 넣기의 두 입구("맥락 넣기", "확정 대기 N개")가 여기 박힌다. 지도가 줄기를 어떻게 보여주고 연결을 어떻게 시각화할지는 지도 슬라이스 몫이다. 단 연결을 미리 다 그리는 마인드맵식 그래프는 §3-2(큰 그림 먼저)와 거리가 있고, 연결은 해설에서 파고들 때 발견된다.
- 해설: 질문(필수) + 줄기 범위(선택)를 입력받아 산문 + 근거를 돌려준다. 겉모습은 채팅이어도 단발 질의다. 넣기와는 직접 연결이 없다.
- 내보내기: 해설과 같은 `assembleEvidence` 코어를 쓴다. 질문 기반이라 줄기를 통째로 가져가는 게 아니라 질문에 대한 근거를 조립한다. 그래서 앱에서 미는 경로는 해설에 붙는 "가져가기" 출구이지 독립 지면이 아니다.

## 8. v1 철거

v2 자유 전제다. 넣기·묻기·세션 UI를 전면 철거하고, 그 자리에 자기완결 넣기 라우트를 세운다. 단 검색 코어·엔진·인증·공간 셸은 받침이라 그대로 둔다. 전면 철거라 빈 화면만 남으므로, 철거와 넣기 라우트 신설은 한 묶음으로 간다.

### 8.1 철거

- 프론트: `DraftTabContent`, `useDraftTab`, `ChatComposer`의 remember 모드와 모드 토글, `ActionMessage`의 draft intent, `useCancelDraft`, 관련 draft 훅. 묻기 표면(세션 사이드바, MessageList, ask 입력창 등)도 전면 철거에 포함.
- 백엔드: `orchestrator`의 getDraft/setDraft/clearDraft와 drafting 분기, `cancelDraftAction`, `confirmDraftIntentStream`, `message-router`의 cancelDraft·confirmDraftIntent, `services/chat/drafting.ts`, `prompts/drafting.ts`와 `draft-intent.ts`.
- 스키마: `SessionDraft`, `DraftIntent`, 관련 message 스키마.
- DB: `sessions.draft` 컬럼 드롭. `sessions` 테이블은 이 트랙에서는 남기되, 세션 개념 폐기(용어 사전 v2)에 따라 최종적으로 `sources.session_id`를 끊고 테이블째 드롭한다.

### 8.2 유지 (받침)

- Track 0 계약: `drafts`·`topics`·`source_topics`·`sources.title`, `confirm_draft`·`create_source` RPC, `draft.*`·`topic.list` 라우터, 공유 스키마.
- 셸: 인증, 공간(MVP에선 화면에 안 드러나는 암묵 배경), 앱 컨테이너. 넣기는 바깥 셸에 무관한 중앙 콘텐츠로 앉는다.
- 엔진: 검색 코어(`searchStatements` 등), 추출 워커. 다시켜기·해설 슬라이스가 재사용한다.

## 9. 열어둔 것

만들며 답하거나, 다음 단계에서 정할 것들이다.

- 대화형 어시스턴트: 외부 LLM을 쓰지 않는 사용자에게는 값이 있다(오너 의견). 단 방향 문서 §2가 첫 타겟을 외부 LLM 사용자로 좁혔고 §6이 그 확장을 나중으로 미뤘다. 첫 제품 우선순위를 건드리는 결정이라 이번 트랙 단독으로 정하지 않는다. 설계는 초안 페이지에 어시스턴트 호출 지점을 두어 확장에 열어두되, 이번 구현은 한 방으로 채운다.
- 저장(넣기) 후 동선: 지도로 돌아가나, 인박스로, 아니면 다음 넣기로 이어지나.
- 초안 페이지 진입의 임시 입구: 지도가 아직 없는 동안 사람이 넣기 화면에 도달할 임시 진입점.
- 한 방 도우미 품질: 회의록 전사처럼 거친 입력에서 한 방 정리가 충분한지는 직접 써보며 본다(방향 문서 §8). 자꾸 부실하면 §9-3(한 번 더 다듬기)을 재검토할 신호다.
- 줄기·연결 시각화: 줄기를 가로지르는 연결을 지도에서 어떻게 보여줄지는 실제 시각화를 해보며 정한다. 지도 슬라이스 몫.
- 회의록처럼 여러 맥락이 섞인 초안을 쪼개 넣는 UX는 이번 범위 밖. 한 초안에 여러 주제로 둔다.

## 10. 자기검산 (방향 문서 §10의 네 질문)

1. 오랜만에 다시 켜는 순간을 돕는가. 넣기는 그 순간을 직접 섬기진 않지만, 가벼운 넣기로 평소에 줄기가 쌓이게 해 다시 켰을 때 볼 큰 그림을 채운다. 인박스는 다시 켰을 때 확정 대기를 발견하는 자리로 다시켜기와 맞물린다.
2. 신뢰를 올리는가. 확정은 사람 게이트에서만 일어나고, 확정 후에도 충돌·애매는 pending으로 사람에게 온다. 미확정 초안은 인박스에 보존되고, 전면 철거는 대체물 없이 사용자를 길 잃게 하지 않도록 넣기 라우트 신설과 한 묶음으로 간다.
3. 넣는 일이 가벼운가. 어시스턴트가 한 번 깎고 사람은 보고 고치기만 한다. 대화형 반복은 닫아 노션화를 막았다. 저장이 곧 확정이라 별도 게이트 단계가 없다.
4. 큰 그림이 먼저인가. 사람은 진술이 아니라 본문을 통짜로 보고, 제목·주제만 확정한다. 진술 추출은 엔진이 뒤에서 돌고, 세부(충돌)는 부딪힐 때만 떠오른다.
