# LLM 모델 매핑

동작마다 어떤 모델을 쓰고 왜 그렇게 골랐는지. 코드 상 매핑은 `apps/server/src/infra/llm/models.ts`.

## 판단 기준

품질이 먼저다. 비용보다 안정성을 앞에 둔다.

| 축 | 무엇을 묻나 |
|---|---|
| 오류 영향도 | 틀렸을 때 얼마나 치명적이고, 되돌릴 수 있나 |
| 작업 복잡도 | 얼마나 깊은 추론과 맥락 이해가 필요한가 |
| 사용자 노출 | 결과를 사용자가 직접 보나 |

## 동작별 배정

| 동작 | 모델 | 근거 |
|---|---|---|
| 다이제스트 생성 | `gpt-5.6-terra` | 규칙 밀도가 높은 프롬프트를 지키는 게 관건이고, 오류가 진술·관계로 그대로 번진다 |
| 겹치는 카드 걸러내기 | `gpt-5.6-terra` | 아래 참고 |
| 거르기 | 미정 | 후보를 줄이는 게 목적이라 놓치지만 않으면 된다. 짧고 잦아 단가가 곧 총액이 된다 |
| 관계 판정 | 미정 | 되돌릴 수 없는 유일한 자리. 틀린 관계가 저장되면 사용자가 지난 판단을 현재로 믿는다 |
| 진술 임베딩 | Voyage | 아래 참고 |

미정인 것은 그 슬라이스가 설 때 실제 프롬프트를 놓고 재서 정한다. 프롬프트가 없는
상태에서 미리 고르면 근거 없이 비싼 쪽을 박게 된다.

**겹치는 카드 걸러내기**는 저장 직전에 겹치는 다이제스트를 빼는 자리다. "거르기"와 성격이
반대다 — 그쪽은 놓쳐도 다음 단계에서 만회되지만, 여기서 잘못 지운 카드는 사용자가 그런
판단이 있었다는 사실조차 모른 채 사라진다. 짧고 잦아 단가를 내리고 싶은 유인이 크지만
어느 등급까지 내려도 되는지 잴 자료가 없어, 일단 생성과 같은 모델로 두고 걸러낸 목록이
로그에 쌓이면 내린다. 위 "미리 고르면 근거 없이 비싼 쪽을 박는다"의 반대 방향도 마찬가지라
싼 쪽을 미리 박지 않는다.

## 환경별로 갈리는 것

기본은 전 환경 OpenAI다. Google Vertex(Gemini)는 명시적으로 켤 때만 돈다.

Vertex를 남겨둔 이유는 GCP 무료 크레딧을 로컬 작업에 태우려는 것뿐이다. 크레딧이
소진되면 걷어낸다. 그러니 Vertex 경로를 정성껏 다듬지 않는다.

**품질을 재는 것은 언제나 prod에서 실제로 도는 모델로 한다.** 다른 모델로 재고
prod에 다른 걸 올리면, 잰 것과 나가는 것이 달라져 측정이 뜻을 잃는다.

## 모델을 바꿀 때 무엇이 따라오나

바꿔도 그대로 가는 것과, 다시 재야 하는 것이 갈린다.

| 구분 | 무엇 | 모델을 바꾸면 |
|---|---|---|
| 모델 무관 | 파이프라인 · 스키마 · 배선 · 규칙 기반 프롬프트 본문 | 그대로 간다 |
| 모델 종속 | 프롬프트 미세조정 · 임계값 · effort · timeout | 다시 재야 한다 |

프롬프트 본문은 모델 중립으로 쓴다. 그러면 교체할 때 깨지는 건 프롬프트가 아니라
출력 분포에 맞춰 잡아둔 소수의 보정값뿐이다.

## 하지 말 것

- **모델과 프롬프트를 같이 바꾸지 않는다.** 무엇 덕에 좋아졌는지 못 가른다. 모델만
  바꿔서 재고, 프롬프트를 고칠 일이 보이면 목록에 적어 다음으로 넘긴다.
- **채점하는 모델을 엔진과 같은 계열로 두지 않는다.** 자기 계열 출력을 후하게 보는
  편향이 생긴다. 사람이 눈으로 보는 단계에서는 해당 없고, LLM 자동 채점을 만들 때
  지킨다.
- **임베딩 프로바이더를 가볍게 바꾸지 않는다.** 벡터 공간이 달라져 쌓인 것을 전부
  다시 색인해야 한다. 지금은 색인된 벡터가 없어 비용이 0이지만, 한 번 쌓이기 시작하면
  그때부터는 되돌리기 비싼 결정이 된다.
