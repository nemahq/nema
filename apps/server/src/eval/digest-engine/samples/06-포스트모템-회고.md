# 삭제 처리 테스트 성공률 이슈 — 회고

참석: 도현(엔지니어), 세아(QA), 준(PM)

## 무슨 일이 있었나

지난주 상담 봇의 "대화 삭제 처리" 기능을 붙이면서, 실패했던 대화 히스토리를 그대로 재생시켜 검증하는 방식으로 테스트를 돌렸다. 동작 자체는 단순한 편인데도 edge case 테스트에서 성공률이 60%, 80%로 나왔다 — 다들 이 정도로 낮을 줄은 예상 못 했다.

## 배운 것

**단순해 보이는 동작도 성공률이 낮게 나올 수 있다.** "삭제 호출 여부 판단"처럼 로직만 보면 간단한 동작인데도 프롬프트만으로는 60~80%밖에 안 나왔다. 복잡도와 성공률이 항상 비례하는 게 아니라는 걸 이번에 체감했다.

**한 번 성공했다고 끝난 게 아니다.** PPA 테스트를 한 번 통과시켜 놓고 안심했던 적이 있는데, 같은 프롬프트를 다섯 번, 열 번 반복 돌리면 결과가 매번 달랐다. LLM 응답의 랜덤성을 확인하려면 최소 반복 실행이 필요하다는 걸 이번에 규칙으로 세웠다.

**예전 방식(시스템 프롬프트를 한 줄씩 손으로 읽으며 문제점을 찾아 고치는 것)은 너무 번거로웠다.** 리플레이 기능으로 전환하고 나서야 이 과정이 확 줄었다 — 진작 바꿨어야 했다는 이야기가 나왔다.

**자동 개선 제안을 그대로 받아들이면 안 된다.** 자동화 도구가 프롬프트 수정안을 출력해주긴 하는데, 이번에 몇 번은 제안대로 적용했다가 다른 케이스가 깨진 적이 있었다. 제안은 참고만 하고 사람이 검토하는 단계를 꼭 거쳐야 한다는 걸 다시 확인했다.

## 이번에 확정한 것

- 성공률 기준: 단순한 동작은 100% 통과를 목표로 하고, 복잡한 동작은 10번 중 1번 실패까지는 허용한다.
- 프롬프트를 고친 뒤엔 기존 회귀 테스트를 전부 통과해야만 배포한다 — 이번 이슈 이전엔 이 단계가 느슨했다.

## 아직 안 풀린 것

서브 에이전트와 루트 에이전트로 역할을 쪼갤지, 아니면 지금처럼 하나의 에이전트가 다 처리하게 둘지는 이번에도 결론을 못 냈다. 루트 에이전트가 서브 에이전트의 지식을 전부 알고 있어야 역할 분리가 의미 있는데, 지금 구조로는 그게 안 된다 — 다음에 시간 잡고 다시 보기로 했다.
