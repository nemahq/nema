# 이슈 기반 워크플로우 자유토론

참석: 하은(PM), 정우(엔지니어), 소이(CS)

### 이슈 기반 워크플로우 제안

하은은 고객사가 자기 문제를 "이슈"로 등록하면 그 뒤 처리가 자동으로 돌아가는 구조를 제안했다. 지금처럼 담당자가 일일이 상담을 붙잡고 있는 대신, 이슈 단위로 큐에 쌓이고 처리되는 편이 자동화하기 쉽다는 게 요지였다.

### 정우의 반박 — "이슈"라는 개념 자체가 낯설다

정우는 이슈라는 개념 자체가 고객사 입장에서 너무 낯설고 모호하다고 지적했다. 실제 상담은 "이거 좀 이상한데요" 수준으로 잡다하게 들어오지, 처음부터 "이슈"로 딱 떨어지는 형태가 아니라는 것이다. 태스크 기반으로 훨씬 잘게 쪼개는 쪽이 오히려 더 자연스러울 수 있다고 대안을 냈다.

### 소이의 데이터 — 애매한 요청이 더 많다

소이는 실제 CS 로그를 보면 이슈 하나로 딱 떨어지는 문의보다 애매하게 걸쳐 있는 요청이 훨씬 많다며 정우 쪽을 거들었다. "이거 왜 안 돼요"라는 문의 하나가 버그 신고이기도 하고 사용법 질문이기도 하고 요금제 불만이기도 해서, 이슈 하나로 깔끔하게 분류가 안 되는 경우가 대부분이라고 했다.

### 하은의 재반박 — 그래도 구조가 필요하다

하은은 그렇다고 이슈 기반을 포기하면 자동화할 최소 단위 자체가 안 잡힌다고 재반박했다. 애매한 요청도 결국 어딘가엔 걸어둬야 자동으로 굴러가는데, 태스크 기반으로 가면 오히려 단위가 너무 잘게 쪼개져서 구현이 더 복잡해질 거라는 우려를 냈다.

### 정우 — 태스크 기반도 쉬운 길은 아니다

정우도 태스크 기반이 만능은 아니라는 건 인정했다. 잘게 쪼갤수록 그 사이 연결(하나의 상담이 여러 태스크에 걸쳐 있을 때 어떻게 묶을지)을 다시 설계해야 하는 문제가 있다고 스스로 지적했다.

### 결론 — 못 냄

세 사람 다 자기 쪽 우려는 있는데 상대 쪽 대안이 확실히 낫다고 확신하지도 못하는 채로 시간이 다 됐다. 이슈 기반으로 갈지 태스크 기반으로 갈지는 결론을 못 냈고, 다음에 실제 CS 로그 샘플을 같이 보면서 다시 얘기하기로 했다.

### 곁가지 — 가드레일 타이밍

토론 중간에 잠깐 나온 얘기로, DB 접근 관련 가드레일(안전장치)을 지금부터 넣을지 나중에 기능부터 다 붙이고 넣을지도 의견이 갈렸다. 정우는 나중에 사고 나면 늦는다고 우려했고, 하은은 지금 넣으면 개발 속도가 너무 느려진다고 봤다. 이것도 결론 없이 넘어갔다.
