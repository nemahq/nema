## [결정] CSV 업로드 대신 복사-붙여넣기 방식 우선 채택

- **상황**: 확장성을 고려하면서 리드 업로드 과정을 가볍게 만들어야 했다.
- **선택**: 리드 업로드는 CSV 업로드 대신 복사-붙여넣기 방식을 우선 채택하고, 필드 매핑과 기본 키 검증만 남긴다.
- **이유**: 테이블 형태 데이터는 붙여넣기만 해도 상당 부분 자동 인식할 수 있고, 기존 CSV 업로드 과정은 길고 무거워 실제로 잘 사용되지 않았다.
- **트레이드오프**: 
  - CSV 업로드에서 제공하던 유저/리드 분리와 옵션 설정 등은 유지하지 않는다.
- **대안**: 
  - 기존 CSV 업로드 방식 유지 — 유저/리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제 사용이 저조했다.

> **판단 이유**: 리드 업로드 방식이라는 하나의 선택지에서 복사-붙여넣기 방식을 채택했다. 기존 CSV 방식이 명시적으로 검토 후 배제되었으며, 그 이유와 남기기로 한 범위가 함께 제시됐다.

## [결정] 기존 CSV 업로드 방식 배제

- **상황**: 리드 업로드 경험을 단순화할 방식을 선택해야 했다.
- **선택**: 기존 CSV 업로드 방식은 리드 업로드의 우선 방식으로 사용하지 않기로 했다.
- **이유**: 유저/리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제로 잘 사용되지 않았다.
- **대안**: 
  - 복사-붙여넣기 방식

> **판단 이유**: 노트는 기존 CSV 방식을 단순히 대안으로 언급한 데 그치지 않고, 실제 사용 저조를 이유로 우선 방식에서 제외했다. 명시적으로 탈락한 후보이므로 채택 결정과 별도 판단으로 기록했다.

## [결정] 이벤트 트리거에 룰베이스 선필터링 후 LLM 적용

- **상황**: 월 1~2억 건 규모의 이벤트를 처리하면서 이벤트 트리거 방식을 정해야 했다.
- **선택**: 이벤트 트리거는 룰베이스로 먼저 필터링해 물량을 1% 수준(150만 건 이하)으로 줄인 뒤에만 LLM을 적용한다. 자연어 입력은 룰 생성의 보조 수단으로만 사용한다.
- **이유**: 모든 이벤트를 LLM으로 처리하면 서버 비용을 감당할 수 없기 때문이다.
- **트레이드오프**: 
  - 자연어 입력을 이벤트 전체에 직접 적용하지 않고, 룰을 만드는 보조 용도로 제한한다.
- **대안**: 
  - 모든 이벤트를 자연어로 필터링 — 월 1~2억 건을 모두 LLM에 처리하면 서버 비용을 감당할 수 없었다.

> **판단 이유**: 이벤트 처리 흐름과 LLM 적용 범위를 명시적으로 결정했다. 비용 문제와 물량 축소 목표가 이 선택의 이유 및 제약으로 제시됐다.

## [결정] 모든 이벤트의 자연어 필터링 배제

- **상황**: 월 1~2억 건 규모의 이벤트에 적용할 트리거 방식을 선택해야 했다.
- **선택**: 모든 이벤트를 자연어로 직접 필터링하는 방식은 사용하지 않기로 했다.
- **이유**: 전체 이벤트를 LLM에 처리할 경우 서버 비용을 감당할 수 없다는 점이 확인됐다.
- **대안**: 
  - 룰베이스 선필터링 후 LLM 적용

> **판단 이유**: 초기에 검토한 전체 자연어 필터링안이 비용을 이유로 명시적으로 배제됐다. 따라서 최종 처리 방식 선택과 별개의 탈락 판단으로 포함했다.

## [결정] 이번 스프린트에서 콘텐츠 파트 우선 개발

- **상황**: 이번 스프린트에서 어떤 B2B 리드젠 기능을 먼저 개발할지 정해야 했다.
- **선택**: 이번 스프린트에서는 B2B 리드젠에 필요한 콘텐츠 파트(캠페인 자료 구성)를 가장 먼저 개발하고, 정해진 시간에 자동 발송하는 기능은 나중으로 미룬다.
- **이유**: 콘텐츠 파트가 핵심이며, 시간 지정 기능은 천천히 만들어도 된다는 데 참석자들이 동의했다.
- **트레이드오프**: 
  - 정해진 시간에 자동으로 보내는 기능의 개발을 뒤로 미룬다.
- **대안**: 
  - 정해진 시간에 자동으로 보내는 기능을 먼저 개발 — 콘텐츠 파트가 핵심이고 시간 지정 기능은 나중에 만들어도 된다고 판단했다.

> **판단 이유**: 스프린트 우선순위와 자동 발송 기능의 연기 여부는 서로 연동된 하나의 우선순위 판단이다. 콘텐츠 파트를 먼저 개발하기로 한 이유와 미뤄지는 기능이 명시됐다.

## [결정] 대시보드에는 캠페인 성과 요약만 표시

- **상황**: 대시보드에 어느 수준까지 정보를 표시할지 정해야 했다.
- **선택**: 대시보드에는 캠페인 성과 요약만 보여주고, 세부 데이터는 별도 리포트 화면에서 확인하도록 한다.
- **이유**: 상세 지표까지 모두 넣으면 화면이 복잡해진다는 우려가 있었다.
- **트레이드오프**: 
  - 세부 데이터는 대시보드에서 즉시 확인할 수 없고 별도 리포트 화면에서 봐야 한다.
- **대안**: 
  - 대시보드에 상세 지표까지 모두 표시 — 화면이 복잡해질 수 있다는 우려가 있었다.

> **판단 이유**: 대시보드와 별도 리포트 화면 사이의 정보 배치를 결정했다. 상세 지표를 대시보드에 모두 넣자는 안이 명시적으로 제기되었다가 복잡성 우려로 채택되지 않았다.

## [결정] 대시보드 상세 지표 표시안 배제

- **상황**: 대시보드 정보량을 결정해야 했다.
- **선택**: 대시보드에 상세 지표까지 모두 넣는 방식은 채택하지 않기로 했다.
- **이유**: 화면이 복잡해질 수 있다는 우려가 있었다.
- **대안**: 
  - 대시보드에는 성과 요약만 표시하고 세부 데이터는 별도 리포트에서 제공

> **판단 이유**: 상세 지표를 모두 표시하자는 의견은 복잡성 우려 때문에 명시적으로 탈락했다. 최종 대시보드 구성 결정과 구별되는 탈락 판단으로 기록했다.

## [미결] 발신 채널의 설정 위치 결정

- **질문**: 전화·문자 등 발신 채널을 오디언스 설정, 발송 기준, 별도 운영 화면 중 어디에 둘 것인가?
- **배경**: 발신 채널을 배치할 위치를 두고 의견이 갈렸으며, 결론은 다음 회의로 넘어갔다.
- **선택지**: 
  - 오디언스 설정에 발신 채널을 넣기 — 연락처 입력을 자연스럽게 유도할 수 있지만, 오디언스 설정이 너무 무거워질 수 있다.
  - 발송 기준 쪽에 발신 채널을 넣기
  - 별도 운영 화면으로 발신 채널을 분리하기
- **확인 조건**: 다음 회의에서 결론을 낸다.

> **판단 이유**: 발신 채널을 둘 위치에 세 가지 후보가 제시되었지만 결론을 다음 회의로 미뤘다. 따라서 아직 해결되지 않은 선택 문제다.

## [미결] 캠페인 입력 스키마 생성 방식 결정

- **질문**: 캠페인 생성에 필요한 입력 스키마를 LLM이 자동 생성하게 할지, 정해진 함수 호출로 고정된 스키마를 사용할지?
- **배경**: 캠페인 생성 시 필요한 입력 스키마의 생성 방식을 아직 정하지 못했다.
- **선택지**: 
  - LLM이 입력 스키마를 자동 생성 — 유연하지만 안정성이 검증되지 않았다.
  - 정해진 함수 호출로 고정된 스키마 사용
- **확인 조건**: 성민과 도경이 이번 주 안에 어느 방식으로 갈지 결정한다.

> **판단 이유**: 두 가지 스키마 생성 방식이 비교되었으나 아직 선택되지 않았고, 이번 주 내 결정이라는 명시적 해결 조건이 있다.

- **근거**: CSV 업로드에는 유저/리드 분리, 필드 매핑, 옵션 설정 과정이 포함됐다.

> **판단 이유**: 노트는 기존 CSV 흐름의 사용 상태와 원인을 확인된 사실로 서술한다. 이는 업로드 방식 전환 결정의 근거이기도 하다.

## [학습] 전체 이벤트 LLM 처리 비용의 감당 불가 확인

- **발견**: 월 1~2억 건 규모의 이벤트를 모두 LLM으로 처리하면 서버 비용을 감당할 수 없다.
- **근거**: 월 이벤트 규모가 1~2억 건으로 나왔다.

> **판단 이유**: 전체 이벤트 자연어 필터링을 검토하는 과정에서 비용 문제를 확인했다고 명시했다. 수치화된 월 이벤트 규모가 이 발견의 근거로 제시됐다.
