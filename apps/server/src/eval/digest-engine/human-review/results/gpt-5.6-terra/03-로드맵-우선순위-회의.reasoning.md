## [결정] 리드 업로드를 복사-붙여넣기 방식으로 우선 전환

- **상황**: 리드 업로드 방식을 정해야 했다.
- **선택**: CSV 업로드 대신 테이블 데이터를 복사-붙여넣기하는 방식을 우선 채택하고, 매핑과 기본 키 검증만 남긴다.
- **이유**: 테이블 형태 데이터는 붙여넣기만으로도 상당 부분 자동 인식할 수 있었고, 확장성을 고려했다.
- **대안**: 
  - 기존 CSV 업로드 방식 유지 — 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제로 잘 사용되지 않았다.

> **판단 이유**: 기존 CSV 방식과 복사-붙여넣기 방식 중 후자를 채택한다고 명시했다. 선택 이유와 기존 방식이 배제된 이유도 함께 기록되어 있다.

## [결정] 이벤트 트리거에 룰베이스 선필터링 후 LLM 적용

- **상황**: 대규모 이벤트에 적용할 트리거 및 LLM 활용 방식을 정해야 했다.
- **선택**: 트리거는 룰베이스로 먼저 필터링해 물량을 1% 수준인 150만 건 이하로 줄인 뒤에만 LLM을 적용한다. 자연어 입력은 룰 생성 과정의 보조 수단으로만 사용한다.
- **이유**: 월 이벤트가 1~2억 건 규모여서 모든 이벤트를 LLM으로 처리하면 서버 비용을 감당할 수 없다.
- **대안**: 
  - 모든 이벤트를 자연어로 필터링 — 모든 이벤트를 LLM에 처리하면 서버 비용이 감당되지 않는다.

> **판단 이유**: 모든 이벤트에 자연어·LLM 필터링을 적용하는 방안을 검토한 뒤, 룰베이스 선필터링과 제한적 LLM 적용으로 결정했다.

## [결정] 이번 스프린트에서 캠페인 콘텐츠 파트를 최우선 개발

- **상황**: 이번 스프린트에서 콘텐츠 구성과 시간 지정 자동 발송 기능 중 우선순위를 정해야 했다.
- **선택**: B2B 리드젠에 필요한 캠페인 자료 구성 등 콘텐츠 파트를 가장 먼저 개발하고, 정해진 시간에 자동 발송하는 기능은 나중으로 미룬다.
- **이유**: 콘텐츠 파트가 핵심이며 시간 지정 기능은 천천히 만들어도 된다는 데 참석자들이 동의했다.
- **트레이드오프**: 
  - 정해진 시간에 자동으로 발송하는 기능의 개발을 뒤로 미룬다.
- **대안**: 
  - 정해진 시간에 자동 발송하는 기능을 먼저 개발 — 콘텐츠 파트가 핵심이고 시간 지정 기능은 나중에 만들어도 된다고 판단했다.

> **판단 이유**: 스프린트 우선순위로 콘텐츠 파트를 먼저 만들고 자동 발송 기능을 미루기로 합의했다.

## [결정] 대시보드에는 캠페인 성과 요약만 표시

- **상황**: 대시보드에 어느 수준까지 성과 정보를 표시할지 정해야 했다.
- **선택**: 대시보드에는 캠페인 성과 요약만 보여주고, 세부 데이터는 별도 리포트 화면에서 확인하게 한다.
- **대안**: 
  - 대시보드에 상세 지표까지 모두 표시 — 화면이 복잡해질 수 있다는 우려가 있었다.

> **판단 이유**: 대시보드에는 요약만 두고 세부 데이터는 별도 리포트로 분리하기로 정리했다.

## [결정] 대시보드의 상세 지표 표시안 배제

- **상황**: 대시보드 정보량을 결정하는 과정에서 상세 지표 표시안이 제안되었다.
- **선택**: 대시보드에 상세 지표를 모두 넣는 방안은 채택하지 않는다.
- **이유**: 화면이 복잡해질 수 있다는 우려가 제기되었다.

> **판단 이유**: 상세 지표를 모두 대시보드에 넣자는 제안이 있었으나 복잡성 우려로 채택되지 않았다고 명시되어 있어, 배제된 선택으로 별도 기록했다.

## [미결] 발신 채널의 설정 위치 결정

- **질문**: 전화·문자 등 발신 채널을 오디언스 설정에 둘지, 발송 기준에 둘지, 별도 운영 화면으로 분리할지 결정해야 한다.
- **배경**: 발신 채널을 어느 설정 영역에 배치할지를 두고 의견이 갈렸다.
- **선택지**: 
  - 오디언스 설정에 배치 — 연락처 입력을 자연스럽게 유도할 수 있지만, 오디언스 설정이 지나치게 무거워질 수 있다는 반론이 있다.
  - 발송 기준에 배치
  - 별도 운영 화면으로 분리
- **확인 조건**: 다음 회의에서 결론을 낸다.

> **판단 이유**: 발신 채널의 배치 후보가 여러 개로 남아 있고 결론을 다음 회의로 넘겼으므로 미결정 사안이다.

## [미결] 캠페인 입력 스키마 생성 방식 결정

- **질문**: 캠페인 생성에 필요한 입력 스키마를 LLM이 자동 생성하게 할지, 정해진 함수 호출로 고정된 스키마를 사용할지 결정해야 한다.
- **배경**: 캠페인 생성 시 필요한 입력 항목의 생성 방식을 아직 정하지 못했다.
- **선택지**: 
  - LLM이 입력 스키마를 자동 생성 — 유연하지만 안정성이 검증되지 않았다.
  - 정해진 함수 호출로 고정된 스키마 사용
- **확인 조건**: 성민과 도경이 이번 주 안에 어느 방식을 사용할지 결정한다.

> **판단 이유**: 두 생성 방식 중 어느 쪽을 택할지 아직 결정되지 않았으며, 담당자와 결정 시점이 명시되어 있다.

## [학습] 기존 CSV 리드 업로드 방식의 실제 사용성 저조

- **발견**: 기존 CSV 업로드는 실제로 잘 사용되지 않고 있었다.
- **근거**: 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거웠다.

> **판단 이유**: 기존 방식의 사용 현황이 사실로 서술되어 있고, 그 배경이 함께 제시되어 있다.

## [학습] 테이블 데이터의 붙여넣기 자동 인식 가능성 확인

- **발견**: 테이블 형태 데이터는 붙여넣기만 해도 상당 부분 자동 인식할 수 있다.

> **판단 이유**: 붙여넣기 방식의 자동 인식 가능성을 확인했다고 명시되어 있어 확인된 발견으로 분류했다.

## [학습] 전체 이벤트 LLM 처리의 비용 부담 확인

- **발견**: 월 1~2억 건 규모의 이벤트를 모두 LLM으로 처리하면 서버 비용을 감당하기 어렵다.
- **근거**: 월 이벤트 규모가 1~2억 건이다.

> **판단 이유**: 전체 이벤트를 LLM에 처리할 때의 비용 문제가 이번에 확인되었다고 명시되어 있으며, 월별 이벤트 규모가 근거로 제시되었다.
