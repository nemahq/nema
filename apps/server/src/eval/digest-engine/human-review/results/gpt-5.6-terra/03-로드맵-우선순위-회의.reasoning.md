## [결정] 리드 업로드를 복사-붙여넣기 방식으로 우선 전환

- **상황**: 리드 업로드 흐름의 복잡도와 사용성을 어떻게 개선할지 결정해야 했다.
- **선택**: CSV 업로드 대신 테이블 데이터를 복사-붙여넣기하는 방식을 우선 채택한다.
- **이유**: 기존 CSV 업로드는 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제 사용이 저조했고, 테이블 데이터는 붙여넣기만으로도 상당 부분 자동 인식할 수 있음이 확인됐다.
- **트레이드오프**: 
  - 매핑과 기본 키 검증만 남기고 나머지 설정 옵션은 축소한다.
- **대안**: 
  - 기존 CSV 업로드 방식을 유지한다.

> **판단 이유**: CSV 업로드와 복사-붙여넣기 중 후자를 채택한 명시적 결정이다. 기존 방식의 사용 저조와 자동 인식 확인이 이 선택의 이유로 제시됐다.

## [결정] 기존 CSV 업로드 방식을 우선안에서 제외

- **상황**: 리드 업로드 방식을 복사-붙여넣기와 기존 CSV 업로드 중에서 정해야 했다.
- **선택**: 기존 CSV 업로드 방식을 리드 업로드의 우선 방식으로 사용하지 않는다.
- **이유**: CSV 업로드는 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제로 잘 사용되지 않았다.
- **대안**: 
  - 테이블 데이터 복사-붙여넣기 방식을 우선 채택한다.

> **판단 이유**: 기존 CSV 방식은 검토 대상이었으나 명시적으로 다른 방식으로 대체됐다. 선택된 방식과 별도로, CSV 방식을 우선안에서 배제한 판단을 기록한다.

## [결정] 이벤트 전체에 LLM 자연어 필터를 적용하지 않음

- **상황**: 이벤트 트리거에 LLM을 어느 범위까지 적용할지 결정해야 했다.
- **선택**: 모든 이벤트를 자연어로 필터링하는 방식은 채택하지 않는다.
- **이유**: 월 이벤트가 1~2억 건 규모여서 전체 이벤트를 LLM에 처리하면 서버 비용을 감당할 수 없다는 점이 확인됐다.
- **대안**: 
  - 모든 이벤트를 자연어로 필터링한다.

> **판단 이유**: 전체 이벤트에 자연어 필터를 적용하는 안을 초기에 검토했지만, 비용 문제로 배제했다는 명시적 판단이다.

## [결정] 룰베이스 선별 후 LLM을 적용하는 이벤트 트리거 채택

- **상황**: 대량의 월간 이벤트를 처리하면서 LLM 기반 트리거를 운영할 방식을 정해야 했다.
- **선택**: 룰베이스로 이벤트를 먼저 1% 수준(150만 건 이하)까지 줄인 뒤에만 LLM을 적용한다.
- **이유**: 전체 이벤트를 LLM에 처리하는 서버 비용을 감당할 수 없기 때문이다.
- **트레이드오프**: 
  - 자연어 입력은 이벤트를 직접 필터링하는 수단이 아니라 룰 생성 과정의 보조 수단으로만 사용한다.
- **대안**: 
  - 모든 이벤트를 자연어로 필터링한다.

> **판단 이유**: 비용 제약에 대응해 룰베이스 선별과 후속 LLM 적용이라는 처리 순서를 명시적으로 결정했다.

## [결정] 이번 스프린트에서 캠페인 콘텐츠 파트를 최우선 개발

- **상황**: 이번 스프린트에서 콘텐츠 구성과 자동 발송 기능 중 무엇을 우선 개발할지 정해야 했다.
- **선택**: B2B 리드젠용 캠페인 자료 구성 등 콘텐츠 파트를 먼저 개발하고, 정해진 시간에 자동 발송하는 기능은 나중으로 미룬다.
- **이유**: 콘텐츠 파트가 핵심이며 시간 지정 기능은 천천히 만들어도 된다는 데 참석자들이 동의했다.
- **트레이드오프**: 
  - 정해진 시간에 자동 발송하는 기능의 개발을 뒤로 미룬다.
- **대안**: 
  - 정해진 시간에 자동 발송하는 기능을 먼저 개발한다.

> **판단 이유**: 스프린트 우선순위에 관한 결정이며, 콘텐츠의 핵심성 때문에 자동 발송보다 먼저 개발하기로 했다.

## [결정] 대시보드는 캠페인 성과 요약만 제공

- **상황**: 대시보드에 어느 수준까지 성과 정보를 표시할지 정해야 했다.
- **선택**: 대시보드에는 캠페인 성과 요약만 보여주고, 세부 데이터는 별도 리포트 화면에서 제공한다.
- **이유**: 상세 지표까지 넣으면 화면이 복잡해진다는 우려가 있었다.
- **트레이드오프**: 
  - 세부 데이터를 보려면 별도 리포트 화면으로 이동해야 한다.
- **대안**: 
  - 대시보드에 상세 지표까지 모두 표시한다.

> **판단 이유**: 대시보드의 정보량을 제한하고 세부 데이터를 별도 화면으로 분리하기로 한 명시적 결정이다.

## [결정] 대시보드에 상세 지표를 모두 넣는 안을 제외

- **상황**: 대시보드의 정보량을 캠페인 성과 요약 수준으로 제한할지, 상세 지표까지 포함할지 정해야 했다.
- **선택**: 대시보드에 상세 지표를 모두 표시하지 않는다.
- **이유**: 상세 지표를 모두 넣으면 화면이 복잡해진다는 우려가 더 크게 받아들여졌다.
- **대안**: 
  - 대시보드에는 성과 요약만 표시하고 세부 데이터는 별도 리포트 화면에서 제공한다.

> **판단 이유**: 상세 지표를 모두 넣자는 의견이 제시됐으나 화면 복잡성 우려로 채택되지 않았다는 별도의 배제 판단이다.

## [미결] 발신 채널의 설정 위치 결정

- **질문**: 전화·문자 등 발신 채널을 오디언스 설정, 발송 기준, 별도 운영 화면 중 어디에 배치할지 결정해야 한다.
- **배경**: 오디언스에 채널을 넣으면 연락처 입력을 자연스럽게 유도할 수 있지만, 오디언스 설정이 지나치게 무거워질 수 있다는 반론이 있다.
- **선택지**: 
  - 오디언스 설정에 발신 채널을 넣는다.
  - 발송 기준 쪽에 발신 채널을 넣는다.
  - 발신 채널을 별도 운영 화면으로 분리한다.
- **확인 조건**: 다음 회의에서 결론을 낸다.

> **판단 이유**: 발신 채널의 배치 후보와 장단점은 제시됐지만 결론을 다음 회의로 넘겼으므로 미결정 사안이다.

## [미결] 캠페인 입력 스키마 생성 방식 결정

- **질문**: 캠페인 생성에 필요한 입력 스키마를 LLM이 자동 생성하게 할지, 정해진 함수 호출을 통한 고정 스키마를 사용할지 결정해야 한다.
- **배경**: LLM 자동 생성은 유연하지만 안정성이 아직 검증되지 않았다.
- **선택지**: 
  - LLM이 입력 스키마를 자동 생성한다.
  - 정해진 함수 호출로 고정된 스키마를 사용한다.
- **확인 조건**: 성민과 도경이 이번 주 안에 어느 방식을 택할지 결정한다.

> **판단 이유**: 두 구현 방식 사이에서 아직 결정을 내리지 않았고, 담당자와 결정 시점만 정해진 미결정 사안이다.

## [학습] 기존 CSV 리드 업로드의 실제 사용이 저조함

- **발견**: 기존 CSV 업로드는 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제로 잘 사용되지 않고 있었다.

> **판단 이유**: 기존 업로드 방식의 사용 상태와 그 원인을 확인된 사실로 서술했으므로 학습으로 기록한다.

## [학습] 테이블 데이터는 붙여넣기만으로 상당 부분 자동 인식 가능

- **발견**: 테이블 형태의 데이터는 복사-붙여넣기만으로도 상당 부분 자동 인식이 가능하다.

> **판단 이유**: 테이블 데이터의 자동 인식 가능 여부를 확인했다고 명시했으므로 학습이다.

## [학습] 전체 이벤트 LLM 처리의 비용이 감당 불가

- **발견**: 월 1~2억 건 규모의 이벤트를 모두 LLM으로 처리하면 서버 비용을 감당할 수 없다.
- **근거**: 월간 이벤트 규모가 1~2억 건으로 확인됐다.

> **판단 이유**: 이벤트 규모와 전체 LLM 처리 비용의 관계가 이번에 확인된 사실로 제시됐다.

## [학습] LLM 자동 스키마 생성의 안정성은 아직 검증되지 않음

- **발견**: LLM이 캠페인 입력 스키마를 자동 생성하는 방식의 안정성은 아직 검증되지 않았다.

> **판단 이유**: LLM 자동 생성 방식의 안정성 검증이 완료되지 않았다는 상태가 명시돼 있으며, 이는 미결정 사안의 배경이 되는 확인 사항이다.
