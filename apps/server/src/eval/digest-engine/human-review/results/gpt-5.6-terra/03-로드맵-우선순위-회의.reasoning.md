## [결정] 리드 업로드의 우선 방식으로 복사-붙여넣기 채택

- **상황**: B2B 마케팅 자동화 제품에서 리드 데이터를 업로드하는 방식을 정해야 했다.
- **선택**: 리드 업로드는 CSV 업로드 대신 복사-붙여넣기 방식을 우선 채택하고, 필드 매핑과 기본 키 검증만 남기기로 했다.
- **이유**: 테이블 형태 데이터는 붙여넣기만으로도 상당 부분 자동 인식할 수 있었고, 확장성을 고려했다.
- **트레이드오프**: 
  - 상세 옵션 설정과 대부분의 추가 업로드 단계를 제공하지 않고 가볍게 간다.
- **대안**: 
  - 기존 CSV 업로드 방식 유지

> **판단 이유**: 리드 업로드 방식이라는 질문에 대해 복사-붙여넣기를 우선 방식으로 하기로 명시적으로 결정했다. 남길 기능과 줄일 범위도 같은 선택의 조건이다.

## [결정] 기존 CSV 업로드 방식을 우선 방식에서 제외

- **상황**: 리드 데이터를 업로드할 기본 방식을 검토했다.
- **선택**: 기존 CSV 업로드 방식은 리드 업로드의 우선 방식으로 채택하지 않기로 했다.
- **이유**: 유저와 리드를 분리하고 필드를 매핑하며 옵션을 설정하는 과정이 길고 무거워 실제 사용이 저조했다.
- **대안**: 
  - 복사-붙여넣기 방식

> **판단 이유**: CSV 방식을 채택하지 않은 것은 복사-붙여넣기 채택과 별도로 기록할 수 있는 명시적 기각 판단이다. 기각 이유도 구체적으로 제시됐다.

## [결정] 이벤트 트리거에 룰 기반 사전 필터 적용

- **상황**: 대규모 월간 이벤트 데이터를 어떤 방식으로 트리거링하고 LLM에 적용할지 정해야 했다.
- **선택**: 이벤트 트리거는 룰 기반으로 먼저 필터링해 처리량을 약 1%인 150만 건 이하로 줄인 뒤에만 LLM을 적용하기로 했다. 자연어 입력은 룰을 만드는 보조 수단으로만 사용한다.
- **이유**: 모든 이벤트를 LLM으로 처리하면 서버 비용을 감당할 수 없다고 확인됐다.
- **트레이드오프**: 
  - LLM은 사전 필터를 통과한 이벤트에만 적용한다.
  - 자연어 입력을 직접적인 전체 이벤트 필터가 아니라 룰 생성 보조 용도로 제한한다.
- **대안**: 
  - 모든 이벤트를 자연어로 필터링하고 LLM으로 처리하는 방식

> **판단 이유**: 처리 순서와 LLM 적용 범위를 정한 명시적 결정이다. 비용 제약과 자연어 입력의 제한은 이 선택에 직접 연결된다.

## [결정] 전체 이벤트의 자연어·LLM 필터링 방식 제외

- **상황**: 월간 대규모 이벤트에 적용할 트리거 방식을 검토했다.
- **선택**: 모든 이벤트를 자연어로 필터링하고 LLM으로 처리하는 방식은 채택하지 않기로 했다.
- **이유**: 월 이벤트가 1억~2억 건 규모여서 전량을 LLM에 태우면 서버 비용을 감당할 수 없었다.
- **대안**: 
  - 룰 기반으로 이벤트를 먼저 필터링한 후 LLM을 적용하는 방식

> **판단 이유**: 전체 이벤트 LLM 처리는 검토 후 비용 문제로 기각된 별도의 후보 경로다. 기각 이유가 분명히 기록돼 있다.

## [결정] 이번 스프린트에서 캠페인 콘텐츠 파트 우선 개발

- **상황**: 이번 스프린트에서 어떤 B2B 리드젠 기능을 먼저 개발할지 우선순위를 정해야 했다.
- **선택**: 이번 스프린트에서는 B2B 리드젠용 캠페인 콘텐츠 자료 구성 기능을 가장 먼저 개발하고, 정해진 시간에 자동 발송하는 기능은 이후로 미루기로 했다.
- **이유**: 콘텐츠 파트가 핵심이며, 시간 지정 기능은 천천히 만들어도 된다는 데 참석자들이 동의했다.
- **트레이드오프**: 
  - 정해진 시간에 자동 발송하는 기능의 개발을 뒤로 미룬다.
- **대안**: 
  - 정해진 시간에 자동 발송하는 기능을 이번 스프린트에서 먼저 개발

> **판단 이유**: 콘텐츠 구성과 시간 지정 발송 사이의 개발 우선순위를 명시적으로 정했다. 시간 지정 기능을 미루는 것은 같은 우선순위 판단의 비용이다.

## [결정] 대시보드에는 캠페인 성과 요약만 표시

- **상황**: 대시보드에 어느 수준까지 성과 데이터를 보여줄지 정해야 했다.
- **선택**: 대시보드에는 캠페인 성과 요약만 보여주고, 세부 데이터는 별도 리포트 화면에서 확인하도록 하기로 했다.
- **이유**: 상세 지표까지 모두 넣으면 화면이 복잡해질 수 있다는 우려가 있었다.
- **트레이드오프**: 
  - 세부 데이터는 대시보드에서 바로 확인하지 않고 별도 리포트 화면으로 이동해야 한다.
- **대안**: 
  - 대시보드에 상세 지표까지 모두 표시

> **판단 이유**: 대시보드의 정보 범위와 세부 데이터의 위치를 정한 결정이다. 화면 복잡성 우려가 이 선택의 이유로 제시됐다.

## [결정] 대시보드 상세 지표 전체 표시안 제외

- **상황**: 대시보드에 표시할 캠페인 성과 정보의 범위를 검토했다.
- **선택**: 대시보드에 상세 지표까지 모두 넣는 방안은 채택하지 않기로 했다.
- **이유**: 상세 지표를 모두 넣으면 화면이 복잡해질 수 있다는 우려가 더 컸다.
- **대안**: 
  - 대시보드에는 성과 요약만 표시하고 세부 데이터는 별도 리포트에서 제공

> **판단 이유**: 상세 지표 전체 표시안은 논의됐으나 복잡성 우려로 기각된 후보 경로다. 요약 중심 대시보드 결정과 별도로 기각 이유를 보존했다.

## [미결] 발신 채널의 설정 위치 결정

- **질문**: 전화·문자 등 발신 채널을 오디언스 설정, 발송 기준, 별도 운영 화면 중 어디에 배치할지 결정되지 않았다.
- **배경**: 오디언스 설정에 넣으면 연락처 입력을 자연스럽게 유도할 수 있지만, 오디언스 설정 자체가 지나치게 무거워질 수 있다는 반론이 있었다.
- **선택지**: 
  - 오디언스 설정에 발신 채널을 포함
  - 발송 기준에 발신 채널을 포함
  - 별도 운영 화면으로 분리
- **확인 조건**: 다음 회의에서 결론을 낸다.

> **판단 이유**: 세 가지 배치 방안이 제시됐지만 결론을 다음 회의로 넘겼으므로 미해결 질문이다.

## [미결] 캠페인 입력 스키마 생성 방식 결정

- **질문**: 캠페인 생성에 필요한 입력 스키마를 LLM이 자동 생성할지, 함수 호출로 고정된 스키마를 사용할지 결정되지 않았다.
- **배경**: LLM 자동 생성은 유연하지만 안정성이 아직 검증되지 않았다는 점이 걸림돌이다.
- **선택지**: 
  - LLM이 입력 스키마를 자동 생성
  - 함수 호출로 고정된 입력 스키마 사용
- **확인 조건**: 성민과 도경이 이번 주 안에 어느 방식으로 갈지 결정한다.

> **판단 이유**: 두 구현 방향이 제시됐으나 아직 선택되지 않았고, 담당자와 결정 시점이 명시돼 있어 pending으로 분류했다.

## [학습] 기존 CSV 업로드의 실제 사용 저조 확인

- **발견**: 기존 CSV 업로드는 실제로 잘 사용되지 않고 있었다.
- **근거**: 유저와 리드를 분리하고, 필드를 매핑하고, 옵션을 설정하는 과정이 길고 무거웠다.

> **판단 이유**: 기존 CSV 업로드의 사용 상태를 이미 확인된 사실로 서술했고, 그 배경이 되는 관찰도 함께 제시됐다.

## [학습] 테이블 데이터의 붙여넣기 자동 인식 가능성 확인

- **발견**: 테이블 형태 데이터는 복사-붙여넣기만으로도 상당 부분 자동 인식할 수 있었다.

> **판단 이유**: 테이블 데이터의 자동 인식 가능 여부를 '확인했다'고 명시했으므로 검증된 발견으로 분류했다.

## [학습] 전체 이벤트 LLM 처리 비용 문제 확인

- **발견**: 월간 전체 이벤트를 LLM으로 처리하면 서버 비용을 감당하기 어렵다.
- **근거**: 월 이벤트 규모가 1억~2억 건으로 추산됐다.

> **판단 이유**: 전체 이벤트 LLM 처리의 비용 문제를 이번에 확인했다고 명시했고, 이벤트 규모가 이를 뒷받침한다.

## 제외된 판단 (3개)

- "참석자 목록" — 회의 참여자 정보일 뿐, 왜 그렇게 했는지 다시 물을 수 있는 판단이 아니다.
- "콘텐츠 파트가 핵심이고 시간 지정 기능은 천천히 만들어도 된다는 참석자들의 동의" — 이번 스프린트 우선순위 결정의 이유와 트레이드오프에 포함했다.
- "성민과 도경이 이번 주 안에 결정하기로 함" — 캠페인 스키마 생성 방식 pending의 해결 조건에 포함했다.
