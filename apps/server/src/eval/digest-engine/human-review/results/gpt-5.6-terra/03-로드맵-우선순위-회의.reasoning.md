# 03-로드맵-우선순위-회의 (reasoning)

digest count: 13

## 원문 제목

B2B 마케팅 자동화 로드맵의 업로드·트리거·캠페인 UX 방향

> **판단 이유**: 노트 전체가 B2B 마케팅 자동화 제품의 여러 기능 영역에서 정한 방향과 남은 설계 쟁점을 다룬다. 특정 한 가지 결정이 아니라 업로드, 이벤트 처리, 우선순위, 대시보드, 캠페인 설정을 아우르는 제목이다.

## [결정] 리드 업로드에 복사-붙여넣기 방식을 우선 채택

- **상황**: B2B 리드를 제품에 업로드하는 방식을 정해야 했다.
- **선택**: CSV 업로드 대신 테이블 데이터를 복사-붙여넣기 하는 방식을 우선 채택하고, 필드 매핑과 기본 키 검증만 남긴다.
- **이유**: 기존 CSV 업로드는 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제로 잘 사용되지 않았으며, 테이블 데이터는 붙여넣기만으로도 상당 부분 자동 인식할 수 있음이 확인됐다.
- **트레이드오프**: 
  - 필드 매핑과 기본 키 검증 외의 설정 범위는 가볍게 제한한다.
- **대안**: 
  - CSV 업로드 방식 유지 — 설정 과정이 길고 무거워 실제 사용이 저조했다.

> **판단 이유**: 리드 업로드 방식이라는 하나의 설계 질문에 대해 복사-붙여넣기를 우선 채택한다고 명시적으로 결론 냈다. CSV 방식은 검토되었으나 선택되지 않은 대안으로 함께 기록했다.

## [결정] CSV 업로드 방식을 우선 채택하지 않음

- **상황**: 리드 업로드 방식을 복사-붙여넣기 방식과 CSV 업로드 방식 중에서 정해야 했다.
- **선택**: 기존 CSV 업로드 방식은 우선 채택하지 않는다.
- **이유**: 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제로 잘 사용되지 않았다.

> **판단 이유**: CSV 업로드는 단순히 언급된 기존 방식이 아니라, 복사-붙여넣기 방식과 비교한 뒤 명시적으로 지나간 후보이다. 후보별 거절을 별도 결정으로 남긴다.

## [결정] 이벤트 트리거를 룰베이스로 선별한 뒤 LLM 적용

- **상황**: 대량의 월간 이벤트에 LLM 기반 자연어 필터링을 어떻게 적용할지 정해야 했다.
- **선택**: 트리거는 룰베이스로 먼저 필터링해 월 이벤트 물량을 1% 수준인 150만 건 이하로 줄인 뒤에만 LLM을 적용한다. 자연어 입력은 룰 생성 과정의 보조 수단으로만 사용한다.
- **이유**: 월 이벤트가 1~2억 건 규모여서 모든 이벤트를 LLM에 처리하면 서버 비용을 감당할 수 없다는 점이 확인됐다.
- **대안**: 
  - 모든 이벤트를 자연어로 필터링 — 월 1~2억 건의 이벤트를 모두 LLM에 태우면 서버 비용이 감당되지 않는다.

> **판단 이유**: 이벤트 처리 순서와 LLM의 역할을 구체적으로 결정했다. 전체 자연어 필터링은 검토됐지만 비용 문제로 채택되지 않은 대안이다.

## [결정] 모든 이벤트의 자연어 필터링을 채택하지 않음

- **상황**: 월간 대량 이벤트를 LLM으로 직접 필터링할지 결정해야 했다.
- **선택**: 모든 이벤트를 자연어로 필터링하는 방식은 채택하지 않는다.
- **이유**: 월 이벤트가 1~2억 건 규모여서 전량을 LLM으로 처리하면 서버 비용을 감당할 수 없다.

> **판단 이유**: 전량 자연어 필터링은 룰베이스 선별 방식과 비교해 명시적으로 배제된 후보이므로 별도 결정으로 기록했다.

## [결정] 이번 스프린트에서 캠페인 콘텐츠 파트를 최우선 개발

- **상황**: 이번 스프린트에서 콘텐츠 파트와 정해진 시간에 자동 발송하는 기능의 개발 우선순위를 정해야 했다.
- **선택**: 이번 스프린트에서는 B2B 리드젠용 캠페인 자료 구성 등 콘텐츠 파트를 가장 먼저 개발한다.
- **이유**: 콘텐츠 파트가 핵심 기능이라는 데 참석자들이 동의했다.
- **대안**: 
  - 정해진 시간에 자동으로 보내는 기능을 먼저 개발 — 콘텐츠 파트가 핵심이며, 시간 지정 기능은 천천히 만들어도 된다고 판단했다.

> **판단 이유**: 두 기능의 개발 순서를 두고 콘텐츠 파트를 먼저 만들기로 합의했으므로 우선순위 결정이다.

## [결정] 정해진 시간 자동 발송 기능을 후순위로 연기

- **상황**: 이번 스프린트에서 콘텐츠 파트와 자동 발송 기능 중 무엇을 먼저 개발할지 정해야 했다.
- **선택**: 정해진 시간에 자동으로 보내는 기능은 나중으로 미룬다.
- **이유**: 콘텐츠 파트가 핵심이고, 시간 지정 기능은 천천히 만들어도 된다는 데 동의했다.
- **트레이드오프**: 
  - 이번 스프린트에는 정해진 시간 자동 발송 기능을 제공하지 않는다.

> **판단 이유**: 자동 발송 기능을 나중으로 미룬 것은 콘텐츠 파트를 먼저 개발하기로 한 결정과 별개로, 해당 기능의 일정에 관한 명시적 결정이다.

## [결정] 대시보드에는 캠페인 성과 요약만 표시

- **상황**: 캠페인 세부 지표를 대시보드에 포함할지와 세부 데이터를 어디에서 확인하게 할지 정해야 했다.
- **선택**: 대시보드에는 캠페인 성과 요약만 보여주고, 세부 데이터는 별도 리포트 화면에서 확인하게 한다.
- **이유**: 대시보드에 상세 지표까지 넣으면 화면이 복잡해진다는 우려가 있었다.
- **트레이드오프**: 
  - 대시보드에서 세부 데이터를 직접 확인할 수 없고 별도 리포트 화면으로 이동해야 한다.
- **대안**: 
  - 대시보드에 상세 지표까지 모두 표시 — 화면이 복잡해질 수 있다는 우려가 있었다.

> **판단 이유**: 대시보드와 리포트 화면 사이의 정보 배치를 구체적으로 정리한 결정이다. 상세 지표를 모두 넣는 안은 제기됐으나 채택되지 않았다.

## [결정] 대시보드에 상세 지표를 모두 넣지 않음

- **상황**: 캠페인 세부 지표를 대시보드에 표시할지 결정해야 했다.
- **선택**: 대시보드에 상세 지표를 모두 넣는 방식은 채택하지 않는다.
- **이유**: 상세 지표를 모두 넣으면 화면이 복잡해질 수 있다는 우려가 있었다.

> **판단 이유**: 상세 지표를 모두 넣자는 의견은 대시보드 요약 중심 방향을 정하는 과정에서 명시적으로 밀려난 후보이므로 별도 결정으로 남긴다.

## [미결] 발신 채널의 설정 위치 결정

- **질문**: 전화·문자 등 발신 채널을 오디언스 설정, 발송 기준, 별도 운영 화면 중 어디에 배치할지 결정해야 한다.
- **배경**: 발신 채널을 어느 설정 단계에 두어야 할지 의견이 갈렸고, 결론을 다음 회의로 넘겼다.
- **선택지**: 
  - 오디언스 설정에 발신 채널 배치 — 연락처 입력을 자연스럽게 유도할 수 있지만, 오디언스 설정이 너무 무거워질 수 있다.
  - 발송 기준 쪽에 발신 채널 배치
  - 별도 운영 화면으로 발신 채널 분리
- **확인 조건**: 다음 회의에서 결론을 낸다.

> **판단 이유**: 발신 채널 배치에 대해 세 가지 후보가 제시됐지만 노트는 결론을 다음 회의로 넘겼다고 명시한다. 따라서 아직 해소되지 않은 설계 쟁점이다.

## [미결] 캠페인 입력 스키마 생성 방식 결정

- **질문**: 캠페인 생성에 필요한 입력 스키마를 LLM이 자동 생성하게 할지, 정해진 함수 호출로 고정된 스키마를 사용할지 결정해야 한다.
- **배경**: LLM 자동 생성은 유연하지만 안정성이 아직 검증되지 않았다는 점이 걸림돌이다.
- **선택지**: 
  - LLM이 입력 스키마를 자동 생성 — 유연하지만 안정성이 검증되지 않았다.
  - 정해진 함수 호출로 고정된 스키마 사용
- **확인 조건**: 성민과 도경이 이번 주 안에 어느 방식으로 갈지 결정한다.

> **판단 이유**: 두 스키마 생성 방식 사이에서 아직 결정하지 못했다고 명시돼 있으며, 이번 주 안에 성민과 도경이 결론을 내기로 했다.

## [학습] 테이블 데이터는 붙여넣기만으로 상당 부분 자동 인식 가능

- **발견**: 테이블 형태 데이터는 복사-붙여넣기만 해도 상당 부분 자동 인식할 수 있다.

> **판단 이유**: 노트에서 테이블 데이터의 자동 인식 가능 여부를 ‘확인했다’고 표현하므로, 제안이 아니라 확인된 발견으로 분류했다.

## [학습] 기존 CSV 업로드의 실제 사용이 저조함

- **발견**: 기존 CSV 업로드는 설정 과정이 길고 무거워 실제로 잘 사용되지 않고 있었다.
- **근거**: CSV 업로드 과정에는 유저·리드 분리, 필드 매핑, 옵션 설정이 포함됐다.

> **판단 이유**: 기존 CSV 업로드의 사용 상태와 그 배경을 사실로 서술하고 있어, 업로드 방식 결정의 근거인 동시에 확인된 발견으로 기록했다.

## [학습] 전체 이벤트 LLM 처리 비용은 감당하기 어려움

- **발견**: 월간 이벤트 전체를 LLM으로 처리하면 서버 비용을 감당하기 어렵다.
- **근거**: 월 이벤트 규모가 1~2억 건으로 확인됐다.

> **판단 이유**: 전량 LLM 처리의 비용 문제를 이번에 확인했다고 명시했으므로, 이벤트 처리 전략의 근거가 된 발견이다.
