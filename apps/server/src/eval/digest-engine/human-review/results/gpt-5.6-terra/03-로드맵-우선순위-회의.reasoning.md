## [결정] 리드 업로드를 CSV 대신 복사-붙여넣기 방식으로 전환

- **상황**: 기존 CSV 업로드는 유저·리드 분리, 필드 매핑, 옵션 설정 과정이 길고 무거워 실제로 잘 사용되지 않고 있었다.
- **선택**: 확장성을 고려해 CSV 업로드 대신 복사-붙여넣기 방식을 우선 채택하고, 필드 매핑과 기본 키 검증만 남긴다.
- **이유**: 테이블 형태 데이터는 붙여넣기만 해도 상당 부분 자동 인식할 수 있음이 확인됐다.
- **트레이드오프**: 
  - CSV 업로드에서 제공하던 상세 설정 과정 대부분을 제거하고 매핑과 기본 키 검증만 유지한다.
- **대안**: 
  - 기존 CSV 업로드 방식 유지 — 업로드 과정이 길고 무거워 실제 사용이 저조했다.

> **판단 이유**: CSV 업로드와 복사-붙여넣기 중 어떤 리드 입력 방식을 채택할지에 대해 복사-붙여넣기를 우선하기로 명시적으로 결정했다.

## [결정] 이벤트 트리거에 룰베이스 선필터링 후 LLM 적용

- **상황**: 월 이벤트가 1~2억 건 규모여서 모든 이벤트를 자연어로 필터링하는 방안이 검토됐다.
- **선택**: 트리거는 룰베이스로 먼저 필터링해 이벤트 물량을 1% 수준인 150만 건 이하로 줄인 뒤에만 LLM을 적용한다. 자연어 입력은 룰 생성 과정의 보조 수단으로만 사용한다.
- **이유**: 모든 이벤트를 LLM에 적용하면 서버 비용을 감당할 수 없다는 점이 확인됐다.
- **트레이드오프**: 
  - 자연어 입력을 모든 이벤트에 직접 적용하지 않고 룰 생성 과정의 보조 기능으로 제한한다.
- **대안**: 
  - 모든 이벤트를 자연어로 필터링 — 월 1~2억 건의 이벤트를 전부 LLM에 태우면 서버 비용을 감당할 수 없다.

> **판단 이유**: 전체 이벤트에 LLM을 적용하는 방식 대신, 룰베이스 선필터링과 제한적 LLM 적용 방식을 결정했다.

## [결정] 이번 스프린트에서 콘텐츠 파트를 시간 지정 발송보다 우선 개발

- **상황**: 이번 스프린트에서 콘텐츠 파트와 정해진 시간의 자동 발송 기능 중 우선 개발 대상을 정해야 했다.
- **선택**: B2B 리드젠에 필요한 콘텐츠 파트인 캠페인 자료 구성을 가장 먼저 개발하고, 정해진 시간에 자동 발송하는 기능은 나중으로 미룬다.
- **이유**: 콘텐츠 파트가 핵심이며 시간 지정 기능은 천천히 만들어도 된다는 데 참석자들이 동의했다.
- **트레이드오프**: 
  - 정해진 시간에 자동으로 보내는 기능의 개발을 뒤로 미룬다.
- **대안**: 
  - 정해진 시간에 자동으로 보내는 기능을 먼저 개발 — 콘텐츠 파트가 핵심이고 시간 지정 기능은 나중에 만들어도 된다고 판단했다.

> **판단 이유**: 두 개발 영역의 우선순위가 명시되었으며, 콘텐츠 파트를 먼저 만들고 시간 지정 발송을 미루기로 했다.

## [결정] 대시보드는 성과 요약만 제공하고 상세 데이터는 리포트 화면으로 분리

- **상황**: 대시보드에 성과 요약만 표시할지 상세 지표까지 모두 표시할지 결정해야 했다.
- **선택**: 대시보드에는 캠페인 성과 요약만 보여주고, 세부 데이터는 별도 리포트 화면에서 확인하도록 한다.
- **이유**: 상세 지표까지 넣으면 화면이 복잡해질 수 있다는 우려가 있었다.
- **트레이드오프**: 
  - 대시보드에서 세부 데이터를 바로 확인할 수 없고 별도 리포트 화면으로 이동해야 한다.
- **대안**: 
  - 대시보드에 상세 지표까지 모두 표시 — 화면이 복잡해질 수 있다는 우려가 있었다.

> **판단 이유**: 대시보드 정보 범위에 대해 성과 요약만 두고 상세 데이터는 별도 화면으로 분리하기로 결정했다.

## [미결] 발신 채널 배치 위치 결정

- **질문**: 전화·문자 등 발신 채널을 오디언스 설정, 발송 기준, 별도 운영 화면 중 어디에 배치할지 결정해야 한다.
- **배경**: 발신 채널의 적절한 UI 배치에 대해 의견이 갈렸고 결론은 다음 회의로 넘겼다.
- **선택지**: 
  - 오디언스 설정에 발신 채널 배치 — 연락처 입력을 자연스럽게 유도할 수 있지만, 오디언스 설정이 너무 무거워질 수 있다.
  - 발송 기준 쪽에 발신 채널 배치
  - 별도 운영 화면으로 발신 채널 분리
- **확인 조건**: 다음 회의에서 결론을 내린다.

> **판단 이유**: 발신 채널의 배치 후보들이 제시됐지만 어느 방향으로 갈지 결론을 내리지 않고 다음 회의로 미뤘다.

## [미결] 캠페인 입력 스키마 생성 방식 결정

- **질문**: 캠페인 생성에 필요한 입력 스키마를 LLM이 자동 생성할지, 정해진 함수 호출로 고정된 스키마를 사용할지 결정해야 한다.
- **배경**: 캠페인 생성 시 필요한 입력 항목의 생성 방식을 아직 정하지 못했다.
- **선택지**: 
  - LLM이 입력 스키마를 자동 생성 — 유연하지만 안정성이 검증되지 않았다.
  - 정해진 함수 호출로 고정된 스키마 사용
- **확인 조건**: 성민과 도경이 이번 주 안에 어느 방식으로 갈지 결정한다.

> **판단 이유**: LLM 자동 생성과 고정 스키마라는 두 후보가 남아 있으며, 이번 주 안에 성민과 도경이 결론을 내리기로 했다.

## [학습] 복사-붙여넣기 데이터의 자동 인식 가능성 확인

- **발견**: 테이블 형태 데이터는 복사해 붙여넣기만 해도 상당 부분 자동 인식할 수 있다.

> **판단 이유**: 노트에서 자동 인식 가능성을 '확인했다'고 명시하므로, 확정된 발견으로 분류했다.

## [학습] 전체 이벤트 대상 LLM 필터링의 비용 문제 확인

- **발견**: 월 1~2억 건 규모의 이벤트를 모두 LLM에 적용하면 서버 비용을 감당하기 어렵다.
- **근거**: 월 이벤트가 1~2억 건 규모로 발생한다.

> **판단 이유**: 전체 이벤트를 LLM에 태우는 비용 문제를 이번에 '확인됐다'고 명시했으며, 이벤트 규모가 이를 뒷받침한다.
