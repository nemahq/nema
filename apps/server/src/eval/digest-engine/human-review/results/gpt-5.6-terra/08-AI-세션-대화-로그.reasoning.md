## [결정] 캐시 무효화에 30초 TTL을 우선 적용

- **상황**: 캐시 무효화를 TTL 방식으로 할지 이벤트 기반으로 할지 결정해야 했다.
- **선택**: 캐시 무효화 전략으로 30초 TTL을 먼저 적용한다.
- **이유**: 현재 리소스로는 이벤트 기반 무효화의 구현 복잡도를 감당하기 부담스럽다.
- **트레이드오프**: 
  - 최대 30초 동안 오래된 데이터를 보여줄 수 있다.
- **대안**: 
  - 이벤트 기반 무효화 — 구현이 더 복잡하고, 무효화 이벤트를 빠뜨리는 곳이 하나라도 있으면 버그로 이어질 수 있다.

> **판단 이유**: 정우가 절충안에 동의하며 "일단 그렇게 가자. TTL 30초로 시작할게"라고 최종 선택을 명시했다.

## [결정] 이벤트 기반 캐시 무효화는 지금 도입하지 않음

- **상황**: 현재 트래픽 패턴에는 이벤트 기반 무효화가 맞을 수 있지만, 현 시점에 도입할지 결정해야 했다.
- **선택**: 이벤트 기반 캐시 무효화는 지금 도입하지 않고, 나중에 여유가 생기면 추가한다.
- **이유**: 현재 리소스로는 구현 복잡도가 부담스럽다.
- **트레이드오프**: 
  - 데이터 변경 직후에도 캐시가 최대 30초 동안 최신 상태가 아닐 수 있다.
- **대안**: 
  - 지금 이벤트 기반 무효화를 도입 — 구현이 복잡하고 무효화 이벤트 누락 시 버그로 이어질 수 있으며, 현재 리소스로 감당하기 부담스럽다.

> **판단 이유**: 이벤트 기반 방식을 현재 적용하지 않고 추후 추가하기로 한 별도의 도입 시점 결정이다.

## [미결] 캐시 키에 사용자 ID를 지금 포함할지 결정

- **질문**: 향후 사용자별로 다른 데이터를 제공할 가능성에 대비해, 캐시 키에 사용자 ID를 지금부터 포함할지 결정해야 한다.
- **배경**: 현재 캐시 키는 리소스 ID만 사용한다. 사용자별 데이터 기능은 아직 확정되지 않았다.
- **선택지**: 
  - 지금 캐시 키에 사용자 ID를 포함 — 나중에 마이그레이션하는 것보다 비용이 적을 수 있다.
  - 기능 필요성이 확정될 때까지 사용자 ID를 포함하지 않음 — 기능이 사용되지 않으면 불필요하게 복잡도만 늘어날 수 있다.
- **확인 조건**: 사용자별 데이터 기능이 필요하다고 판단될 때 다시 결정한다.

> **판단 이유**: 정우가 사용자 ID 포함 여부에 대해 "좀 더 생각해볼게"라고 하며 결정을 미뤘다.
