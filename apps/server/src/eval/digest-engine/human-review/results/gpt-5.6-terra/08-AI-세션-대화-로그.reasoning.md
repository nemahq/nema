## [결정] 캐시 무효화를 TTL 30초 방식으로 시작

- **상황**: 캐시 무효화 전략으로 TTL 방식과 이벤트 기반 무효화 방식 중 어떤 접근을 먼저 도입할지 결정해야 했다.
- **선택**: 캐시 무효화는 우선 TTL 30초 방식으로 적용하고, 이벤트 기반 무효화는 리소스 여유가 생기면 나중에 추가한다.
- **이유**: 짧은 TTL을 사용하면 현재 시점에 큰 리스크 없이 시작할 수 있기 때문이다.
- **트레이드오프**: 
  - TTL이 만료되기 전 최대 30초 동안 오래된 데이터가 표시될 수 있다.
- **대안**: 
  - 이벤트 기반 무효화를 즉시 도입 — 현재 리소스로는 구현 복잡도를 감당하기 부담스럽다.

> **판단 이유**: 정우가 절충안에 동의하며 "일단 그렇게 가자. TTL 30초로 시작"이라고 확정했다. TTL 방식이 감수하는 데이터 최신성 비용과 즉시 이벤트 기반 방식을 택하지 않은 이유도 함께 제시됐다.

## [결정] 이벤트 기반 캐시 무효화의 즉시 도입 보류

- **상황**: 트래픽 패턴상 이벤트 기반 무효화가 적합해 보이지만, 현재 구현 가능 여부를 판단해야 했다.
- **선택**: 이벤트 기반 캐시 무효화는 지금 즉시 도입하지 않고, 리소스 여유가 생긴 뒤 추가 검토한다.
- **이유**: 현재 리소스로는 이벤트 기반 무효화의 구현 복잡도를 감당하기 부담스럽기 때문이다.
- **대안**: 
  - 지금 이벤트 기반 무효화를 도입 — 구현 복잡도가 부담스럽다.

> **판단 이유**: 이벤트 기반 방식은 후보로 검토됐으나 정우가 현재 리소스에서의 구현 복잡도를 부담으로 들었고, 최종적으로 TTL 방식부터 적용하기로 했다. 즉시 도입 여부라는 별도 후보 경로의 불채택 판단으로 기록했다.

## [미결] 캐시 키에 사용자 ID를 미리 포함할지 결정

- **질문**: 향후 사용자별 데이터 제공 기능에 대비해 지금 캐시 키에 사용자 ID를 포함할지, 필요해질 때까지 미룰지 결정해야 한다.
- **배경**: 현재 캐시 키는 리소스 ID만 사용한다. 향후 사용자별로 다른 데이터를 보여주는 기능이 추가되면 사용자 ID를 캐시 키에 포함해야 할 수 있다.
- **선택지**: 
  - 지금 캐시 키에 사용자 ID를 포함 — 나중에 마이그레이션하는 것보다 지금 미리 넣는 편이 비용이 적을 수 있다.
  - 사용자별 기능이 필요해질 때까지 포함을 미룸 — 해당 기능이 아직 확정되지 않았고, 미리 넣었다가 사용하지 않으면 복잡도만 늘어날 수 있다.
- **확인 조건**: 사용자별로 다른 데이터를 보여주는 기능이 필요하다고 판단될 때 다시 논의한다.

> **판단 이유**: 정우가 사용자 ID 포함 여부에 대해 "좀 더 생각해볼게"라고 하며 결론을 내리지 않았다. 두 방향과 각각의 근거, 재논의 조건이 모두 언급됐다.
