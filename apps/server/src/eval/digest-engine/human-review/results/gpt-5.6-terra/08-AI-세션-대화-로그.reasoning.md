## [결정] 캐시 무효화는 우선 30초 TTL로 시작

- **상황**: 캐시 무효화를 TTL 방식으로 할지 이벤트 기반으로 할지 정해야 했다.
- **선택**: 캐시 무효화는 우선 TTL 30초 방식으로 구현하고, 이벤트 기반 무효화는 리소스 여유가 생기면 나중에 추가한다.
- **이유**: 이벤트 기반 방식이 현재 트래픽 패턴에는 맞을 수 있지만, 지금 리소스로는 구현 복잡도를 감당하기 부담스럽기 때문이다.
- **트레이드오프**: 
  - 최대 30초 동안 오래된 데이터를 보여줄 수 있다.
- **대안**: 
  - 데이터가 변경되는 즉시 캐시를 지우는 이벤트 기반 무효화를 지금 바로 구현한다.

> **판단 이유**: 정우가 절충안에 동의하며 “일단 그렇게 가자. TTL 30초로 시작할게”라고 확정했다. 이벤트 기반 방식의 적합 가능성과 구현 부담, 그리고 나중에 추가한다는 계획은 이 하나의 무효화 전략 선택에 연결된다.

## [미결] 캐시 키에 사용자 ID를 지금 포함할지 여부

- **질문**: 향후 사용자별 데이터 제공 기능에 대비해 캐시 키에 사용자 ID를 지금부터 포함할지 결정해야 한다.
- **배경**: 현재 캐시 키는 리소스 ID만 사용하고 있으며, 사용자별로 다른 데이터를 보여주는 기능은 아직 확정되지 않았다.
- **선택지**: 
  - 지금 캐시 키에 사용자 ID를 포함한다.
  - 기능 필요성이 확정될 때까지 사용자 ID 포함을 미룬다.
- **확인 조건**: 사용자별 데이터 제공 기능이 필요하다고 판단될 때 다시 논의한다.

> **판단 이유**: 정우가 사용자 ID 포함 제안에 대해 “좀 더 생각해볼게”라고 하며 결론을 미뤘다. 기능의 확정 여부와 불필요한 복잡도 가능성이 판단 배경으로 제시됐다.

## [가정] 현재 트래픽 패턴에는 이벤트 기반 무효화가 적합할 수 있음

- **가설**: 현재 서비스의 트래픽 패턴을 보면 이벤트 기반 캐시 무효화가 더 적합할 것 같다.
- **근거**: 정우가 현재 트래픽 패턴을 근거로 들었지만, 구체적인 트래픽 데이터나 검증 결과는 제시되지 않았다.
- **영향**: 이 가정이 맞더라도 현재는 구현 복잡도 때문에 TTL 방식으로 시작하고, 이후 이벤트 기반 무효화 추가를 검토하게 된다.

> **판단 이유**: 정우가 “맞을 것 같긴 한데”라고 헤지하여, 이벤트 기반 방식의 적합성을 확정된 사실이 아닌 미검증 믿음으로 표현했다. 이는 무엇을 할지에 대한 제안이 아니라 현재 상황에 대한 판단이다.
