# 08-AI-세션-대화-로그 (reasoning)

digest count: 3

## 원문 제목

캐시 무효화 방식과 캐시 키 확장 검토

> **판단 이유**: 노트 전체는 캐시 무효화 전략을 정하고, 향후 사용자별 데이터 지원에 대비한 캐시 키 설계를 보류하는 내용이다. 하나의 결정만이 아니라 두 캐시 설계 주제를 함께 다룬 제목으로 정했다.

## [결정] 캐시 무효화를 우선 30초 TTL로 시작

- **상황**: 트래픽 패턴에 맞는 캐시 무효화 전략으로 TTL 방식과 이벤트 기반 무효화 중 어떤 방식을 택할지 결정해야 했다.
- **선택**: 캐시 무효화는 우선 TTL 30초 방식으로 구현하고, 이벤트 기반 무효화는 나중에 여유가 생기면 추가한다.
- **이유**: 이벤트 기반 방식이 트래픽 패턴에는 맞을 수 있지만, 현재 리소스로는 구현 복잡도를 감당하기 부담스럽기 때문이다.
- **트레이드오프**: 
  - 최대 30초 동안 오래된 데이터를 보여줄 수 있다.
- **대안**: 
  - 이벤트 기반 무효화 — 구현이 더 복잡하고, 무효화 이벤트를 빠뜨리는 곳이 하나라도 있으면 버그로 이어질 수 있으며 현재 리소스로 감당하기 부담스럽다.

> **판단 이유**: 정우가 절충안에 동의하며 “일단 그렇게 가자. TTL 30초로 시작할게”라고 명시해 확정된 결정으로 분류했다. 이벤트 기반 방식은 검토됐으나 현재의 구현 부담 때문에 선택되지 않은 대안이다.

## [미결] 캐시 키에 사용자 ID를 미리 포함할지 검토

- **질문**: 향후 사용자별로 다른 데이터를 보여주는 기능에 대비해, 지금 캐시 키에 사용자 ID를 포함할지 결정해야 한다.
- **배경**: 현재 캐시 키는 리소스 ID만 사용하며, 사용자별 데이터 기능이 추가되면 사용자 ID를 포함해야 할 수 있다.
- **선택지**: 
  - 지금부터 캐시 키에 사용자 ID를 포함 — 나중에 마이그레이션하는 것보다 비용이 적을 수 있다.
  - 사용자별 데이터 기능이 필요하다고 판단될 때 추가 — 현재 기능이 확정되지 않았고, 미리 넣었다가 사용하지 않으면 불필요한 복잡도만 늘어날 수 있다.
- **확인 조건**: 사용자별 데이터 기능이 필요하다고 판단될 때 다시 논의한다.

> **판단 이유**: 정우가 “좀 더 생각해볼게”라고 하며 캐시 키 설계를 확정하지 않았다. 사용자 ID를 지금 포함하는 방향과 필요 시 추가하는 방향이 모두 노트에 제시되어 있어 미결 질문으로 남아 있다.

## [가정] 현재 트래픽 패턴에는 이벤트 기반 무효화가 더 맞을 수 있음

- **가설**: 현재 트래픽 패턴을 보면 이벤트 기반 무효화가 더 적합할 것 같다.

> **판단 이유**: 정우가 이벤트 기반 방식이 트래픽 패턴에 맞을 것 같다고 추정했지만, 이를 뒷받침하는 구체적 근거나 검증은 노트에 없다. 행동 제안이 아니라 현재 상황에 대한 미검증 판단이므로 가정으로 분류했다.
