# 06-포스트모템-회고 (reasoning)

digest count: 8

## [결정] LLM 응답 랜덤성 검증을 위한 반복 실행 규칙 수립

- **상황**: PPA 테스트를 한 번 통과한 뒤에도 같은 프롬프트를 반복 실행했을 때 결과가 매번 달랐다.
- **선택**: LLM 응답의 랜덤성을 확인할 때는 최소 반복 실행을 수행한다.
- **이유**: 한 번의 성공만으로는 LLM 응답의 안정성을 확인할 수 없었기 때문이다.
- **대안**: 
  - 한 번의 PPA 테스트 통과만으로 검증을 끝내는 방식

> **판단 이유**: 같은 프롬프트의 반복 결과가 달랐다는 경험을 바탕으로, 최소 반복 실행을 하기로 하는 테스트 정책을 명시적으로 세웠다.

## [결정] 동작 복잡도별 성공률 기준 확정

- **상황**: 대화 삭제 처리처럼 단순해 보이는 동작의 edge case 테스트 성공률이 60~80%에 그쳤다.
- **선택**: 단순한 동작은 100% 통과를 목표로 하고, 복잡한 동작은 10회 중 1회 실패까지 허용한다.

> **판단 이유**: 이번 회고에서 동작의 복잡도에 따라 허용 가능한 성공률 기준을 구체적으로 확정했다.

## [결정] 프롬프트 수정 후 전체 회귀 테스트를 배포 조건으로 설정

- **상황**: 이번 이슈 이전에는 프롬프트 변경 후 회귀 테스트 단계가 느슨했다.
- **선택**: 프롬프트를 수정한 뒤에는 기존 회귀 테스트를 모두 통과해야만 배포한다.

> **판단 이유**: 배포 전 회귀 테스트 전부 통과를 명시적인 조건으로 확정한 운영 결정이다.

## [결정] 프롬프트 문제 분석 방식을 리플레이 기능으로 전환

- **상황**: 기존에는 시스템 프롬프트를 한 줄씩 손으로 읽으며 문제점을 찾아 수정했다.
- **선택**: 시스템 프롬프트를 한 줄씩 수동으로 검토하는 대신, 실패 대화 히스토리를 재생하는 리플레이 기능을 사용한다.
- **이유**: 기존 수동 검토 방식은 너무 번거로웠고, 리플레이 기능으로 전환한 뒤 이 과정이 크게 줄었기 때문이다.
- **대안**: 
  - 시스템 프롬프트를 한 줄씩 수동으로 읽으며 문제점을 찾아 수정하는 방식

> **판단 이유**: 노트는 기존 방식의 번거로움과 리플레이 전환 후의 과정 축소를 대비해, 분석·검증 방식을 바꾼 판단을 설명한다.

## [미결] 서브 에이전트와 루트 에이전트의 역할 분리 여부

- **질문**: 서브 에이전트와 루트 에이전트로 역할을 분리할지, 하나의 에이전트가 모든 처리를 맡게 둘지 결정해야 한다.
- **배경**: 역할 분리가 의미 있으려면 루트 에이전트가 서브 에이전트의 지식을 모두 알고 있어야 하지만, 현재 구조에서는 이것이 가능하지 않다.
- **선택지**: 
  - 서브 에이전트와 루트 에이전트로 역할을 분리한다.
  - 하나의 에이전트가 모든 처리를 맡게 둔다.

> **판단 이유**: 두 운영 구조가 후보로 제시되었지만 이번 회고에서 결론을 내리지 못했고, 이후 다시 검토하기로 했다.

## [학습] 단순한 동작도 낮은 성공률을 보일 수 있음

- **발견**: 동작의 로직이 단순해 보여도 성공률이 높다고 보장할 수 없으며, 복잡도와 성공률은 항상 비례하지 않는다.
- **근거**: ‘삭제 호출 여부 판단’처럼 단순한 동작의 edge case 테스트 성공률이 프롬프트만으로 60~80%에 그쳤다.

> **판단 이유**: 노트가 실제 테스트 결과를 근거로 복잡도와 성공률의 비례 관계가 성립하지 않는다는 점을 확인된 배움으로 서술한다.

## [학습] 동일 프롬프트의 반복 실행 결과는 달라질 수 있음

- **발견**: 같은 프롬프트라도 반복 실행하면 결과가 매번 달라질 수 있다.
- **근거**: PPA 테스트를 한 번 통과한 뒤 같은 프롬프트를 5회, 10회 반복 실행했을 때 결과가 달랐다.

> **판단 이유**: 반복 실행에서 관찰된 결과 차이를 LLM 응답의 랜덤성에 관한 확인된 사실로 기록했다.

## [학습] 자동 프롬프트 개선안은 사람의 검토 없이 적용하면 안 됨

- **발견**: 자동화 도구의 프롬프트 수정 제안은 참고용으로만 사용하고, 적용 전 사람이 검토해야 한다.
- **근거**: 자동화 도구의 제안대로 적용했을 때 다른 케이스가 깨진 사례가 있었다.

> **판단 이유**: 자동 개선안을 적용한 결과 다른 케이스가 깨진 경험을 근거로, 사람 검토의 필요성을 다시 확인한 배움이다.
