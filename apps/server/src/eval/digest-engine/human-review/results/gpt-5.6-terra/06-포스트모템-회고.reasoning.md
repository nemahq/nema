# 06-포스트모템-회고 (reasoning)

digest count: 11

## [결정] 삭제 처리 검증을 리플레이 방식으로 전환

- **상황**: 상담 봇의 대화 삭제 처리 기능을 검증할 방법이 필요했다.
- **선택**: 실패했던 대화 히스토리를 그대로 재생하는 리플레이 방식으로 삭제 처리 기능을 검증하기로 했다.
- **이유**: 시스템 프롬프트를 한 줄씩 손으로 읽으며 문제를 찾고 고치는 기존 방식은 너무 번거로웠고, 리플레이 기능 전환 후 이 과정이 크게 줄었다.
- **대안**: 
  - 시스템 프롬프트를 한 줄씩 손으로 읽으며 문제점을 찾아 고치는 방식 — 과정이 너무 번거로웠다.

> **판단 이유**: 기존 수동 검토 방식 대신 리플레이 기능으로 전환했다고 명시되어 있어, 검증 방식을 선택한 결정으로 분류했다.

## [결정] 수동 프롬프트 줄별 검토 방식을 중단

- **상황**: 삭제 처리 테스트와 프롬프트 문제 수정 과정의 효율을 개선해야 했다.
- **선택**: 시스템 프롬프트를 한 줄씩 손으로 읽으며 문제를 찾아 고치는 방식은 사용하지 않기로 했다.
- **이유**: 이 방식은 너무 번거로웠다.
- **대안**: 
  - 실패한 대화 히스토리를 재생하는 리플레이 방식

> **판단 이유**: 기존 방식을 번거롭다고 평가하고 리플레이 방식으로 바꾼 것은, 수동 방식을 명시적으로 포기한 별도 판단이기도 하다.

## [결정] LLM 응답 검증에 반복 실행을 적용

- **상황**: 같은 프롬프트라도 반복 실행할 때마다 결과가 달랐다.
- **선택**: LLM 응답의 랜덤성을 확인하기 위해 최소 반복 실행을 수행하는 것을 규칙으로 세웠다.
- **이유**: 한 번의 PPA 테스트 통과만으로는 결과의 안정성을 확인할 수 없었다.

> **판단 이유**: 반복 실행이 필요하다는 인식을 넘어 이를 '규칙으로 세웠다'고 했으므로, 테스트 절차에 관한 결정으로 분류했다.

## [결정] 동작 복잡도별 성공률 기준 확정

- **상황**: 삭제 호출 여부 판단처럼 단순해 보이는 동작도 프롬프트만으로는 60~80% 성공률에 그쳤다.
- **선택**: 단순한 동작은 100% 통과를 목표로 하고, 복잡한 동작은 10번 중 1번 실패까지 허용하기로 했다.

> **판단 이유**: 단순·복잡한 동작에 각각 적용할 허용 성공률 기준을 명시적으로 확정했으므로 결정으로 분류했다.

## [결정] 배포 전 전체 회귀 테스트 통과를 필수화

- **상황**: 이번 이슈 이전에는 프롬프트 수정 후 회귀 테스트 단계가 느슨했다.
- **선택**: 프롬프트를 수정한 뒤에는 기존 회귀 테스트를 모두 통과해야만 배포하기로 했다.

> **판단 이유**: 배포 조건으로 전체 기존 회귀 테스트 통과를 명시했으므로, 배포 절차에 대한 결정이다.

## [미결] 에이전트 역할 분리 여부

- **질문**: 서브 에이전트와 루트 에이전트로 역할을 나눌지, 하나의 에이전트가 모든 작업을 처리하게 유지할지 결정해야 한다.
- **배경**: 이번 논의에서도 결론을 내리지 못했다.
- **선택지**: 
  - 서브 에이전트와 루트 에이전트로 역할을 분리 — 루트 에이전트가 서브 에이전트의 지식을 전부 알고 있어야 역할 분리가 의미 있는데, 현재 구조에서는 그것이 불가능하다.
  - 하나의 에이전트가 모든 작업을 처리하도록 유지
- **확인 조건**: 다음에 시간을 따로 잡아 다시 검토한다.

> **판단 이유**: 두 가지 구조적 방향을 제시했지만 어느 쪽도 선택하지 않았고, 추후 재논의하기로 했으므로 미결 사항이다.

## [학습] 단순한 동작도 낮은 성공률을 보일 수 있음

- **발견**: 로직이 단순해 보이는 동작이라도 LLM 프롬프트 기반 처리에서는 성공률이 낮게 나올 수 있으며, 복잡도와 성공률이 항상 비례하지는 않는다.
- **근거**: 삭제 호출 여부 판단은 단순한 동작이었지만 edge case 테스트 성공률이 60%, 80%로 나왔다.

> **판단 이유**: 테스트 결과를 통해 복잡도와 성공률의 관계에 대해 확인한 사실로 서술되어 있어 학습으로 분류했다.

## [학습] 한 번의 PPA 통과로는 안정성을 보장할 수 없음

- **발견**: 같은 프롬프트라도 반복 실행 결과가 달라질 수 있으므로, 한 번의 PPA 테스트 통과만으로는 충분하지 않다.
- **근거**: 같은 프롬프트를 다섯 번, 열 번 반복 실행했을 때 결과가 매번 달랐다.

> **판단 이유**: 반복 실행에서 관찰된 결과를 바탕으로 한 번의 성공이 충분하지 않다고 확인했으므로 학습이다.

## [학습] 자동 개선 제안은 사람의 검토가 필요함

- **발견**: 자동화 도구의 프롬프트 수정 제안은 그대로 적용하지 말고 사람이 검토하는 단계를 거쳐야 한다.
- **근거**: 제안대로 적용한 뒤 다른 케이스가 깨진 사례가 몇 번 있었다.

> **판단 이유**: 자동 개선 제안을 적용했을 때 발생한 문제를 근거로 사람 검토의 필요성을 다시 확인한 내용이므로 학습으로 분류했다.

## [가정] 역할 분리의 전제는 루트 에이전트의 지식 보유

- **가설**: 루트 에이전트가 서브 에이전트의 지식을 전부 알고 있어야 역할 분리가 의미 있다.
- **영향**: 이 전제가 충족되지 않으면 서브 에이전트와 루트 에이전트의 역할 분리가 의미 없을 수 있다.

> **판단 이유**: 역할 분리 논의의 전제로 제시된 구조적 조건이지만, 이를 뒷받침하는 검증 근거는 노트에 없다.

## [가정] 현재 구조는 루트 에이전트의 전체 지식 보유를 지원하지 않음

- **가설**: 현재 구조에서는 루트 에이전트가 서브 에이전트의 지식을 전부 알 수 없다.
- **영향**: 현재 구조에서는 역할 분리의 의미가 없을 수 있다.

> **판단 이유**: 현재 구조의 상태를 역할 분리 미결의 근거로 단정해 제시했지만, 확인 근거는 노트에 없다.

## 제외된 판단 (4개)

- "대화 삭제 처리 기능의 edge case 테스트 성공률이 60%, 80%였고 예상보다 낮았다." — 단순한 동작도 낮은 성공률을 보일 수 있다는 학습의 증거로 포함했다.
- "한 번 PPA 테스트를 통과한 뒤 안심했던 경험" — 한 번의 통과로는 안정성을 보장할 수 없다는 학습의 배경과 증거로 포함했다.
- "자동화 도구 제안대로 수정했다가 다른 케이스가 깨진 사례" — 자동 개선 제안에 사람 검토가 필요하다는 학습의 증거로 포함했다.
- "다음에 시간을 잡아 에이전트 역할 분리 문제를 다시 보기로 함" — 향후 일정에 관한 작업 약속이며, 역할 분리 여부 자체는 미결 사항으로 별도 정리했다.
