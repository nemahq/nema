# 06-포스트모템-회고 (reasoning)

digest count: 10

## [결정] 리플레이 기반 검증으로 전환

- **상황**: 상담 봇의 대화 삭제 처리 기능을 테스트해야 했다.
- **선택**: 실패했던 대화 히스토리를 그대로 재생하는 방식으로 삭제 처리 기능을 검증했다.
- **이유**: 시스템 프롬프트를 한 줄씩 수동으로 읽으며 문제를 찾고 고치는 기존 방식이 번거로웠다.

> **판단 이유**: 기존 수동 점검 방식에서 리플레이 기능으로 ‘전환’했다고 명시되어 있어, 테스트 방식에 대한 결정으로 분류했다.

## [결정] LLM 검증에 최소 반복 실행 적용

- **상황**: 한 번의 PPA 테스트 통과만으로 프롬프트 결과를 신뢰할 수 있는지 판단해야 했다.
- **선택**: LLM 응답의 랜덤성을 확인하기 위해 최소 반복 실행을 하기로 했다.
- **이유**: 같은 프롬프트를 다섯 번, 열 번 반복했을 때 결과가 매번 달랐다.

> **판단 이유**: ‘최소 반복 실행이 필요하다’는 내용을 이번에 규칙으로 세웠다고 했으므로, 향후 검증 절차에 대한 결정이다.

## [결정] 자동 개선안은 사람 검토 후 적용

- **상황**: 자동 개선 제안을 프롬프트에 반영하는 방식을 정해야 했다.
- **선택**: 자동화 도구의 프롬프트 수정 제안은 참고만 하고, 사람이 검토하는 단계를 거쳐 적용하기로 했다.
- **이유**: 제안대로 적용했을 때 다른 케이스가 깨진 사례가 있었다.

> **판단 이유**: 자동 제안을 그대로 받아들이지 않고 사람 검토를 반드시 거치겠다고 명시했으므로 결정으로 분류했다.

## [결정] 동작 복잡도별 성공률 기준 확정

- **상황**: 기능 동작의 성공률 허용 기준을 정해야 했다.
- **선택**: 단순한 동작은 100% 통과를 목표로 하고, 복잡한 동작은 10번 중 1번 실패까지 허용한다.

> **판단 이유**: ‘이번에 확정한 것’ 아래에 성공률 기준이 구체적으로 제시되어 있어 명시적인 결정이다.

## [결정] 회귀 테스트 전체 통과 후 배포

- **상황**: 프롬프트 수정 후 배포 조건을 정해야 했다.
- **선택**: 프롬프트를 수정한 뒤 기존 회귀 테스트를 모두 통과해야만 배포한다.
- **이유**: 이번 이슈 이전에는 이 단계가 느슨했다.

> **판단 이유**: 배포의 필수 조건을 정한 명시적 결정이며, 이전에는 회귀 테스트 단계가 느슨했다는 설명이 근거로 제시되었다.

## [미결] 서브·루트 에이전트 역할 분리 여부

- **질문**: 서브 에이전트와 루트 에이전트로 역할을 분리할지, 하나의 에이전트가 모두 처리하게 둘지 결정해야 한다.
- **배경**: 역할 분리가 의미 있으려면 루트 에이전트가 서브 에이전트의 지식을 모두 알고 있어야 하지만, 현재 구조에서는 가능하지 않다.
- **선택지**: 
  - 서브 에이전트와 루트 에이전트로 역할을 분리한다.
  - 하나의 에이전트가 모든 처리를 담당하게 둔다.
- **확인 조건**: 다음에 시간을 잡아 다시 검토한다.

> **판단 이유**: 두 구조 사이에서 이번에도 결론을 내리지 못했다고 했으므로, 아직 해결되지 않은 의사결정 문제다.

## [학습] 단순한 동작도 낮은 성공률을 보일 수 있음

- **발견**: 로직상 단순해 보이는 동작이라도 프롬프트 기반 실행에서는 성공률이 낮을 수 있으며, 복잡도와 성공률이 항상 비례하지는 않는다.
- **근거**: 삭제 호출 여부 판단은 단순한 동작이었지만 edge case 테스트 성공률이 60%와 80%로 나왔다.

> **판단 이유**: 테스트 결과를 통해 복잡도와 성공률의 관계에 대해 확인한 사실로 서술되어 있어 학습으로 분류했다.

## [학습] 동일 프롬프트의 반복 실행 결과가 달라짐

- **발견**: 같은 프롬프트라도 반복 실행 시 결과가 매번 달라질 수 있다.
- **근거**: 같은 프롬프트를 다섯 번, 열 번 반복 실행했을 때 결과가 매번 달랐다.

> **판단 이유**: 반복 실행에서 관찰한 LLM 응답의 랜덤성이라는 확인된 사실이므로 학습이다.

## [학습] 리플레이 전환으로 수동 점검 부담 감소

- **발견**: 리플레이 기능으로 전환한 뒤 시스템 프롬프트를 수동으로 읽으며 문제를 찾고 고치던 과정이 크게 줄었다.
- **근거**: 기존 방식은 너무 번거로웠고, 리플레이 기능으로 전환한 뒤에야 해당 과정이 크게 줄었다고 기록되어 있다.

> **판단 이유**: 기존 방식과 전환 후 과정의 변화를 경험적으로 확인한 내용이므로 학습으로 분류했다.

## [학습] 자동 개선안 적용이 다른 케이스를 깨뜨릴 수 있음

- **발견**: 자동화 도구의 프롬프트 수정 제안을 그대로 적용하면 다른 케이스가 깨질 수 있다.
- **근거**: 이번에 제안대로 적용했다가 다른 케이스가 깨진 사례가 몇 번 있었다.

> **판단 이유**: 자동 제안 적용의 부작용을 실제 사례로 확인한 내용이므로 학습이다.

## 제외된 판단 (3개)

- "‘다들 이 정도로 낮을 줄은 예상 못 했다.’" — 예상과 달랐다는 반응은 성공률이 낮았다는 학습의 맥락이며, 별도의 결정·학습·미해결 판단으로 분리하지 않았다.
- "PPA 테스트를 한 번 통과시켜 놓고 안심했던 적이 있다." — 과거의 검증 관행에 대한 서술로, 반복 실행 규칙을 세운 결정과 결과 변동성 학습의 배경에 포함했다.
- "‘진작 바꿨어야 했다’는 이야기가 나왔다." — 리플레이 전환에 대한 평가적 소감이며, 전환 후 수동 점검 부담이 줄었다는 학습에 이미 반영되었다.
