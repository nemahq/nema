# 06-포스트모템-회고 (reasoning)

digest count: 10

## 원문 제목

대화 삭제 처리 테스트 성공률 이슈 회고와 테스트 운영 기준

> **판단 이유**: 노트 전체는 상담 봇의 대화 삭제 처리 기능에서 낮은 테스트 성공률을 겪은 뒤, 테스트 방식·품질 기준·에이전트 구조를 되짚은 회고다. 특정 결정 하나가 아니라 이슈에서 얻은 운영 원칙과 미해결 구조 논의를 함께 포괄한다.

## [결정] LLM 응답 검증에 반복 실행 적용

- **상황**: PPA 테스트를 한 번 통과한 뒤에도 같은 프롬프트를 다섯 번, 열 번 반복 실행하면 결과가 매번 달랐다.
- **선택**: LLM 응답의 랜덤성을 확인하기 위해 최소 반복 실행을 수행하는 규칙을 세웠다.
- **이유**: 한 번의 성공만으로는 LLM 응답의 안정성을 확인할 수 없었기 때문이다.

> **판단 이유**: 반복 실행을 필요로 하는 운영 규칙을 명시적으로 세웠으므로 결정으로 분류했다. 결과가 반복마다 달랐다는 관찰이 이 선택의 이유로 제시됐다.

## [결정] 리플레이 기반 프롬프트 검증으로 전환

- **상황**: 기존에는 시스템 프롬프트를 한 줄씩 손으로 읽으며 문제점을 찾아 수정했다.
- **선택**: 시스템 프롬프트를 한 줄씩 수동으로 검토하는 대신, 실패한 대화 히스토리를 재생하는 리플레이 기능으로 검증 방식을 전환했다.
- **이유**: 기존 수동 검토 방식이 너무 번거로웠고, 리플레이 기능으로 전환한 뒤 그 과정이 크게 줄었기 때문이다.
- **대안**: 
  - 시스템 프롬프트를 한 줄씩 손으로 읽으며 문제점을 찾아 고치기 — 과정이 너무 번거로웠다.

> **판단 이유**: 기존 수동 방식에서 리플레이 기능으로 '전환'했다는 선택이 명시돼 있다. 수동 방식의 번거로움과 전환 후 과정 감소가 선택 근거로 함께 언급됐다.

## [결정] 자동 프롬프트 개선안에 사람 검토 필수화

- **상황**: 자동화 도구가 프롬프트 수정안을 출력하지만 이를 그대로 적용하는 방식을 어떻게 다룰지 판단해야 했다.
- **선택**: 자동화 도구의 프롬프트 수정안은 참고만 하고, 적용 전에 사람이 반드시 검토하기로 했다.
- **이유**: 제안대로 적용했을 때 다른 케이스가 깨진 경우가 있었기 때문이다.
- **대안**: 
  - 자동 개선 제안을 그대로 적용하기 — 제안대로 적용했다가 다른 케이스가 깨진 적이 있었다.

> **판단 이유**: 자동 제안을 그대로 수용하지 않고 사람 검토 단계를 두겠다는 명시적 운영 방침이므로 결정이다. 다른 케이스가 깨진 경험이 해당 방침의 근거다.

## [결정] 동작 복잡도별 성공률 기준 확정

- **상황**: 대화 삭제 처리처럼 단순해 보이는 동작도 edge case 테스트에서 60~80% 성공률을 보여, 허용 가능한 성공률 기준을 정할 필요가 있었다.
- **선택**: 단순한 동작은 100% 통과를 목표로 하고, 복잡한 동작은 10번 중 1번 실패까지 허용한다.

> **판단 이유**: 노트의 '이번에 확정한 것'에서 동작 복잡도별 성공률 목표와 허용 실패 범위를 명시했으므로 결정으로 분류했다.

## [결정] 배포 전 전체 회귀 테스트 통과 의무화

- **상황**: 이번 이슈 이전에는 프롬프트 수정 후 회귀 테스트 단계가 느슨했다.
- **선택**: 프롬프트를 수정한 뒤 기존 회귀 테스트를 모두 통과해야만 배포하기로 했다.

> **판단 이유**: 배포 조건을 명시적으로 확정한 운영 결정이다. 이전에 해당 단계가 느슨했다는 점이 이 기준이 마련된 배경으로 적혀 있다.

## [미결] 서브 에이전트와 루트 에이전트의 역할 분리 여부

- **질문**: 서브 에이전트와 루트 에이전트로 역할을 분리할지, 하나의 에이전트가 모든 일을 처리하도록 유지할지 결정해야 한다.
- **배경**: 역할 분리가 의미 있으려면 루트 에이전트가 서브 에이전트의 지식을 모두 알고 있어야 한다고 보지만, 현재 구조에서는 그것이 가능하지 않다.
- **선택지**: 
  - 서브 에이전트와 루트 에이전트로 역할을 분리하기 — 루트 에이전트가 서브 에이전트의 지식을 전부 알고 있어야 역할 분리가 의미 있는데, 현재 구조에서는 그 조건을 충족하지 못한다.
  - 하나의 에이전트가 모든 일을 처리하도록 유지하기
- **확인 조건**: 다음에 시간을 잡아 다시 검토하기로 했다.

> **판단 이유**: 역할 분리 여부에 대해 두 선택지를 제시했지만 '결론을 못 냈다'고 명시했으므로 미해결 사항이다. 다음 논의가 예정됐다는 점도 남아 있다.

## [학습] 단순한 동작도 낮은 성공률을 보일 수 있음

- **발견**: 로직상 단순해 보이는 동작이라도 프롬프트 기반 실행에서는 성공률이 낮을 수 있으며, 동작 복잡도와 성공률은 항상 비례하지 않는다.
- **근거**: 대화 삭제 처리의 '삭제 호출 여부 판단'은 단순한 동작이었지만 edge case 테스트 성공률이 60~80%에 그쳤다.

> **판단 이유**: 노트가 이번 사례를 통해 체감한 일반화된 사실로 명시했으며, 실제 테스트 성공률이 이를 뒷받침하는 근거로 제시됐다.

## [학습] 단일 PPA 통과로 안정성을 판단할 수 없음

- **발견**: 한 번의 PPA 테스트 통과만으로 프롬프트의 안정성을 판단할 수 없다.
- **근거**: 같은 프롬프트를 다섯 번, 열 번 반복 실행했을 때 결과가 매번 달랐다.

> **판단 이유**: 반복 실행에서 결과가 달랐다는 관찰을 바탕으로 얻은 확인된 교훈이므로 학습으로 분류했다.

## [학습] 자동 프롬프트 개선안은 다른 케이스를 깨뜨릴 수 있음

- **발견**: 자동화 도구가 제안한 프롬프트 수정안을 그대로 적용하면 다른 케이스가 깨질 수 있다.
- **근거**: 이번에 몇 차례 자동화 도구의 제안대로 적용했다가 다른 케이스가 깨졌다.

> **판단 이유**: 자동 제안 적용의 결과로 실제 회귀 문제가 발생했다는 경험적 확인이므로 학습으로 기록했다.

## [가정] 의미 있는 역할 분리의 전제

- **가설**: 서브 에이전트와 루트 에이전트의 역할 분리가 의미 있으려면 루트 에이전트가 서브 에이전트의 지식을 모두 알고 있어야 한다.
- **영향**: 현재 구조에서 그 조건을 충족하지 못하면 역할 분리의 의미가 없다고 본다.

> **판단 이유**: 역할 분리 논의의 전제로 제시된 구조적 믿음이지만, 이를 검증한 근거는 노트에 없다. 제안 자체가 아니라 역할 분리가 성립하는 조건에 관한 주장이라 가정으로 분류했다.
