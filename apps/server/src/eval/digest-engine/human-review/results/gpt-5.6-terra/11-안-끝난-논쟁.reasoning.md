## [미결] 이슈 기반과 태스크 기반 중 워크플로우 단위 선택

- **질문**: 고객사 요청을 이슈 단위로 큐잉·자동 처리할지, 더 세분화한 태스크 단위로 처리할지 결정해야 한다.
- **배경**: 이슈 기반 워크플로우는 담당자가 개별 상담을 직접 처리하는 대신 요청을 이슈 단위로 큐에 쌓아 자동화하기 쉽게 하려는 제안에서 출발했다.
- **선택지**: 
  - 이슈 기반 워크플로우 — 자동화하려면 애매한 요청이라도 걸어둘 최소 단위의 구조가 필요하며, 태스크 기반은 단위가 너무 잘게 쪼개져 구현이 더 복잡해질 수 있다.
  - 태스크 기반 워크플로우 — 고객사 요청은 처음부터 이슈로 명확히 구분되지 않는 경우가 많아 더 잘게 쪼개는 편이 자연스러울 수 있다. 다만 하나의 상담이 여러 태스크에 걸칠 때 그 연결을 다시 설계해야 한다.
- **확인 조건**: 실제 CS 로그 샘플을 함께 검토한 뒤 다시 논의한다.

> **판단 이유**: 이슈 기반과 태스크 기반 중 어느 쪽을 택할지 명시적으로 결론을 내리지 못했고, 다음 논의에서 로그를 보고 판단하기로 했다. 두 방향의 근거와 우려는 모두 이 하나의 미결 선택에 대한 논거다.

## [미결] DB 접근 가드레일 도입 시점 결정

- **질문**: DB 접근 관련 안전장치를 지금 도입할지, 기능을 모두 붙인 뒤 도입할지 결정해야 한다.
- **배경**: 토론 중 DB 접근 가드레일의 적용 시점이 별도 쟁점으로 제기되었다.
- **선택지**: 
  - 지금부터 가드레일 도입 — 나중에 사고가 나면 늦을 수 있다.
  - 기능을 모두 붙인 뒤 가드레일 도입 — 지금 도입하면 개발 속도가 너무 느려질 수 있다.

> **판단 이유**: 가드레일의 필요성 자체가 아니라 도입 시점에 대해 의견이 갈렸으며, 결론 없이 넘어갔다. 따라서 독립된 미결 판단이다.

## [학습] CS 요청은 단일 이슈로 분류하기 어려운 경우가 많음

- **발견**: 실제 CS 로그에서는 하나의 이슈로 명확히 구분되는 문의보다 여러 범주에 걸친 애매한 요청이 더 많다.
- **근거**: CS 로그에서 “이거 왜 안 돼요” 같은 문의 하나가 버그 신고, 사용법 질문, 요금제 불만에 동시에 걸리는 사례가 대부분이라고 언급되었다.

> **판단 이유**: 소이가 실제 CS 로그를 근거로 요청 분류의 양상을 확인된 사실처럼 제시했다. 이는 단순한 제안이 아니라 로그에서 얻은 관찰이므로 학습으로 분류했다.

## 제외된 판단 (5개)

- "고객사 문제를 이슈로 등록하면 이후 처리가 자동으로 돌아가도록 하자는 제안" — 이슈 기반 워크플로우를 후보로 둔 미결 선택에 병합했다.
- "고객사에게 ‘이슈’ 개념은 낯설고 모호하며, 요청은 처음부터 이슈 형태로 들어오지 않는다는 지적" — 태스크 기반 후보를 지지하는 논거로 워크플로우 단위 선택 미결 항목에 병합했다.
- "이슈 기반을 포기하면 자동화를 위한 최소 단위가 잡히지 않는다는 반박" — 이슈 기반 후보를 지지하는 논거로 워크플로우 단위 선택 미결 항목에 병합했다.
- "태스크를 잘게 쪼개면 하나의 상담이 여러 태스크에 걸칠 때 연결 방식을 다시 설계해야 한다는 지적" — 태스크 기반 후보의 단점으로 워크플로우 단위 선택 미결 항목에 병합했다.
- "세 사람이 상대 대안이 확실히 낫다고 확신하지 못했다는 결론 상태" — 워크플로우 단위 선택이 미결이라는 내용에 이미 반영되어 있어 별도 판단으로 만들지 않았다.
