# 11-안-끝난-논쟁 (reasoning)

digest count: 3

## [미결] 자동화 워크플로우의 기본 단위를 이슈로 할지 태스크로 할지 결정

- **질문**: 고객사 요청을 이슈 단위로 큐잉·처리하는 이슈 기반 워크플로우로 갈지, 더 잘게 나눈 태스크 기반 워크플로우로 갈지
- **배경**: 현재 담당자가 상담을 개별적으로 붙잡고 처리하는 방식 대신 자동화 가능한 처리 구조가 필요하다. 다만 실제 고객 문의는 하나의 명확한 이슈로 분류되지 않고 버그 신고·사용법 질문·요금제 불만 등에 걸쳐 있는 경우가 많다고 제기되었다.
- **선택지**: 
  - 이슈 기반 워크플로우 — 자동화하려면 요청을 걸어둘 최소 단위가 필요하며, 태스크 기반은 단위가 지나치게 잘게 쪼개져 구현이 더 복잡해질 수 있다.
  - 태스크 기반 워크플로우 — 고객사에는 ‘이슈’라는 개념이 낯설고 모호할 수 있으며, 실제 상담은 처음부터 명확한 이슈 형태로 들어오지 않는다. 다만 하나의 상담이 여러 태스크에 걸칠 때 이를 묶는 연결 구조를 다시 설계해야 한다.
- **확인 조건**: 다음 논의에서 실제 CS 로그 샘플을 함께 검토한다.

> **판단 이유**: 이슈 기반과 태스크 기반 중 어느 방식을 택할지 명시적으로 결론을 내리지 못했다. 각 방향의 근거와 우려가 제시되었고, 실제 CS 로그 검토가 후속 판단의 기준으로 남았다.

## [미결] DB 접근 가드레일을 지금 도입할지 기능 완성 후 도입할지 결정

- **질문**: DB 접근 관련 안전장치를 지금부터 구축할지, 기능을 먼저 모두 붙인 뒤 도입할지
- **배경**: 토론 중 DB 접근 안전장치의 도입 시점을 두고 의견이 갈렸다.
- **선택지**: 
  - 지금부터 가드레일 도입 — 나중에 사고가 발생하면 늦을 수 있다.
  - 기능을 먼저 붙인 뒤 가드레일 도입 — 지금 가드레일을 넣으면 개발 속도가 너무 느려질 수 있다.

> **판단 이유**: 가드레일 도입 시점에 대해 상반된 방향이 제시되었지만 결론 없이 넘어갔다. 따라서 아직 해결해야 할 미결정 사항이다.

## [학습] 실제 CS 문의는 단일 이슈로 명확히 분류되지 않는 경우가 많음

- **발견**: 실제 CS 로그에서는 하나의 이슈로 딱 떨어지는 문의보다 여러 범주에 애매하게 걸쳐 있는 요청이 더 많다.
- **근거**: ‘이거 왜 안 돼요’ 같은 문의 하나가 버그 신고, 사용법 질문, 요금제 불만을 동시에 포함할 수 있다는 CS 로그 관찰이 제시되었다.

> **판단 이유**: 소이가 실제 CS 로그를 근거로 문의 분류의 애매함을 확인된 현황으로 제시했다. 이는 단순 제안이나 추측이 아니라 로그 관찰에 기반한 발견이다.

## 제외된 판단 (3개)

- "하은의 이슈 기반 워크플로우 제안" — 이슈 기반과 태스크 기반의 선택은 하나의 미결정 질문을 구성하므로, 별도 아이디어가 아니라 워크플로우 기본 단위 결정이라는 pending의 분기와 근거로 통합했다.
- "정우의 태스크 기반 워크플로우 대안" — 이슈 기반 대안과 같은 선택 질문에 대한 경쟁 경로이므로, 별도 아이디어가 아니라 동일 pending의 분기와 근거로 통합했다.
- "다음에 실제 CS 로그 샘플을 같이 보기로 함" — 후속 논의 일정·행동이며, 워크플로우 단위 선택을 위한 resolutionCondition으로 반영했다. 그 자체로는 독립적인 판단이 아니다.
