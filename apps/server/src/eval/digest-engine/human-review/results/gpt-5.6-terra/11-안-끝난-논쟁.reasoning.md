# 11-안-끝난-논쟁 (reasoning)

## [미결] 워크플로우의 기본 단위를 이슈와 태스크 중 무엇으로 할지

- **질문**: 고객 요청 처리 워크플로우를 이슈 기반으로 설계할지, 태스크 기반으로 설계할지 결정해야 한다.
- **배경**: 이슈 기반은 요청을 큐에 쌓아 자동화하기 쉬운 최소 단위를 제공할 수 있지만, 실제 고객 문의는 버그·사용법·요금제 불만 등에 걸쳐 있어 하나의 이슈로 분류하기 어려운 경우가 많다는 의견이 나왔다. 태스크 기반은 고객 문의 형태에는 더 자연스러울 수 있으나, 상담이 여러 태스크에 걸칠 때 이를 연결하는 구조를 별도로 설계해야 하고 구현이 복잡해질 수 있다는 우려도 제기됐다.
- **선택지**: 
  - 고객 요청을 이슈 단위로 등록하고 처리하는 이슈 기반 워크플로우
  - 고객 요청을 더 잘게 나눈 태스크 단위로 처리하는 태스크 기반 워크플로우
- **확인 조건**: 실제 CS 로그 샘플을 함께 검토한 뒤 다시 논의한다.

> **판단 이유**: 회의에서 이슈 기반과 태스크 기반 중 어느 방식을 택할지 명시적으로 결론을 내리지 못했다. 다음 논의를 위해 실제 CS 로그를 보기로 했으므로 미결정 사안으로 분류했다.

## [미결] DB 접근 가드레일을 지금 도입할지 나중에 도입할지

- **질문**: DB 접근 관련 안전장치를 현재 기능 개발과 함께 넣을지, 기능을 먼저 완성한 뒤 도입할지 결정해야 한다.
- **배경**: 정우는 가드레일 도입을 늦추면 사고가 난 뒤에는 늦을 수 있다고 우려했고, 하은은 지금 도입하면 개발 속도가 지나치게 느려질 것으로 봤다.
- **선택지**: 
  - 기능 개발 초기부터 DB 접근 가드레일을 도입한다.
  - 기능을 먼저 구현한 뒤 DB 접근 가드레일을 도입한다.

> **판단 이유**: 가드레일 도입 시점을 두고 상반된 방향이 제시됐지만 결론 없이 넘어갔다. 따라서 아직 결정해야 할 독립적인 미결정 사안이다.

## [학습] CS 문의는 단일 이슈로 명확히 분류되지 않는 경우가 많음

- **발견**: 실제 CS 로그에서는 하나의 이슈로 명확히 구분되는 문의보다 여러 성격에 걸쳐 있는 애매한 요청이 더 많다.
- **근거**: "이거 왜 안 돼요" 같은 문의는 버그 신고, 사용법 질문, 요금제 불만이 동시에 될 수 있어 하나의 이슈로 깔끔하게 분류되지 않는 경우가 대부분이라는 CS 로그 관찰이 제시됐다.

> **판단 이유**: 소이가 실제 CS 로그를 근거로 고객 문의의 분류 어려움을 확인된 관찰로 제시했다. 이는 이슈 기반과 태스크 기반 선택에 영향을 주는 별도의 사실 발견이다.

## 제외된 판단 (4개)

- "하은의 이슈 기반 워크플로우 제안과 자동화 용이성 주장" — 이슈 기반이라는 후보 방향과 그 장단점은 워크플로우 기본 단위에 관한 미결정 사안의 branches 및 background에 통합했다.
- "정우의 태스크 기반 대안과 고객에게 더 자연스러울 수 있다는 주장" — 태스크 기반이라는 후보 방향과 그 장단점은 워크플로우 기본 단위에 관한 미결정 사안의 branches 및 background에 통합했다.
- "태스크를 세분화하면 여러 태스크에 걸친 상담의 연결 구조를 다시 설계해야 한다는 지적" — 태스크 기반 선택의 우려로서 동일한 워크플로우 기본 단위 미결정 사안의 background에 통합했다.
- "가드레일을 늦추면 사고 뒤에는 늦을 수 있고, 지금 넣으면 개발 속도가 느려질 수 있다는 주장" — 각 주장은 DB 접근 가드레일 도입 시점이라는 하나의 미결정 사안의 background에 통합했다.
