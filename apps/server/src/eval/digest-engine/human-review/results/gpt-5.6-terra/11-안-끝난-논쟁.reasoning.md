# 11-안-끝난-논쟁 (reasoning)

digest count: 6

## 원문 제목

이슈·태스크 기반 CS 워크플로우와 DB 가드레일 도입 시점 논의

> **판단 이유**: 노트는 CS 처리 구조를 이슈 기반과 태스크 기반 중 무엇으로 설계할지 논의한 내용이 중심이며, DB 접근 가드레일의 도입 시점이라는 별도 미결 사안도 함께 다룬다. 어느 한 판단만이 아니라 두 주제를 함께 포괄하는 제목이다.

## [미결] CS 워크플로우를 이슈 기반과 태스크 기반 중 무엇으로 설계할지

- **질문**: 고객사 요청을 이슈 단위로 큐잉·자동 처리할지, 더 잘게 나눈 태스크 단위로 처리할지 결정해야 한다.
- **배경**: 이슈 기반 구조는 자동화를 위한 처리 단위를 만들기 쉽다는 제안에서 시작됐지만, 실제 고객 요청은 하나의 이슈로 명확히 분류되지 않는 경우가 많다는 반론이 나왔다.
- **선택지**: 
  - 이슈 기반 워크플로우 — 애매한 요청도 어딘가에 연결해야 자동 처리가 가능하며, 이슈 기반을 포기하면 자동화를 위한 최소 단위가 잡히지 않는다는 의견이 있었다.
  - 태스크 기반 워크플로우 — 고객 요청은 처음부터 명확한 이슈 형태가 아니고 여러 성격에 걸치는 경우가 많아 더 잘게 나눈 태스크가 자연스러울 수 있다는 의견이 있었다. 다만 태스크를 세분화하면 하나의 상담에 걸친 여러 태스크의 연결 방식을 다시 설계해야 한다.
- **확인 조건**: 다음 논의에서 실제 CS 로그 샘플을 함께 검토한다.

> **판단 이유**: 이슈 기반과 태스크 기반 중 어느 구조를 택할지 논의했지만 결론을 내리지 못했고, 실제 CS 로그 검토를 통해 다시 판단하기로 했다. 따라서 해결해야 할 선택지가 있는 미결 사안이다.

## [미결] DB 접근 가드레일의 도입 시점

- **질문**: DB 접근 관련 안전장치를 지금부터 구현할지, 기능을 먼저 완성한 뒤 도입할지 결정해야 한다.
- **배경**: 토론 중 DB 접근 가드레일의 선제 적용 여부를 두고 개발 안전성과 개발 속도 사이의 의견 차이가 있었다.
- **선택지**: 
  - 지금부터 가드레일 도입 — 나중에 사고가 발생한 뒤에는 늦을 수 있다는 우려가 제기됐다.
  - 기능을 먼저 붙인 뒤 가드레일 도입 — 지금 가드레일을 넣으면 개발 속도가 너무 느려질 수 있다는 의견이 있었다.

> **판단 이유**: 가드레일을 언제 도입할지에 대해 서로 다른 방향과 근거가 제시됐지만, 노트는 결론 없이 넘어갔다고 명시한다.

## [학습] 실제 CS 요청은 단일 이슈로 분류되지 않는 경우가 많음

- **발견**: 실제 CS 로그에서는 하나의 이슈로 명확히 구분되는 문의보다 여러 성격에 걸쳐 있는 애매한 요청이 더 많다.
- **근거**: "이거 왜 안 돼요" 같은 문의 하나가 버그 신고, 사용법 질문, 요금제 불만에 동시에 해당할 수 있다는 CS 로그 관찰이 제시됐다.

> **판단 이유**: 소이가 실제 CS 로그를 근거로 요청 유형의 분류 어려움을 사실로 보고했다. 단순한 제안이나 추측이 아니라 로그 관찰에 기반한 확인 내용으로 제시됐다.

## [가정] 고객사에 이슈 개념이 낯설고 모호할 수 있음

- **가설**: 고객사 관점에서 '이슈'라는 개념은 낯설고 모호하며, 실제 상담 요청도 처음부터 이슈 형태로 들어오지 않는다.
- **영향**: 이슈 기반 워크플로우를 고객 요청의 기본 단위로 삼는 선택의 적합성이 낮아질 수 있다.

> **판단 이유**: 정우가 이슈 기반 설계에 반대하는 근거로 고객사의 인식과 요청 형태를 단정적으로 제시했지만, 이 주장 자체를 직접 검증한 자료는 노트에 없다. 고객 행동과 상태에 관한 미검증 믿음이므로 가정으로 분류했다.

## [가정] 태스크 기반은 구현 복잡도를 높일 수 있음

- **가설**: 태스크 기반으로 처리 단위를 지나치게 세분화하면 구현이 더 복잡해질 수 있다.
- **영향**: 태스크 기반 워크플로우를 선택할 때 자동화 구현 비용과 설계 난이도를 재검토해야 한다.

> **판단 이유**: 하은이 태스크 기반의 세분화가 구현 복잡도를 높일 것이라는 우려를 제시했으나, 이를 뒷받침하는 검증 결과는 제시되지 않았다. 미래의 구현 난이도에 대한 미검증 예측으로 분류했다.

## [가정] 세분화된 태스크에는 상담 연결 방식의 재설계가 필요함

- **가설**: 하나의 상담이 여러 태스크에 걸칠 경우, 태스크 간 연결·묶음 방식을 새로 설계해야 한다.
- **영향**: 태스크 기반 접근을 채택하면 태스크 분할뿐 아니라 상담 맥락을 연결하는 설계 작업이 추가된다.

> **판단 이유**: 정우가 태스크 기반의 한계로 여러 태스크에 걸친 상담을 묶는 설계 문제를 지적했지만, 현재 시스템에서의 검증이나 해결 방식은 제시되지 않았다. 설계상 발생할 것으로 보는 미검증 상태 판단이다.
