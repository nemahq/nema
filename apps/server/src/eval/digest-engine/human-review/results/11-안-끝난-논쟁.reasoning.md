# 11-안-끝난-논쟁 (reasoning)

digest count: 3

## [미결] 워크플로우 관리 단위 결정

- **질문**: 고객 요청 처리를 위한 워크플로우 단위를 '이슈 기반'으로 할지 '태스크 기반'으로 할지 결정해야 함.
- **배경**: 하은은 자동화 용이성을 위해 이슈 기반을 제안했으나, 정우와 소이는 고객의 애매한 요청 유형을 고려할 때 이슈 기반이 부적절하고 태스크 기반이 더 자연스러울 수 있다고 주장함.
- **선택지**: 
  - 이슈 기반 워크플로우
  - 태스크 기반 워크플로우
- **확인 조건**: 다음 회의에서 실제 CS 로그 샘플을 검토한 후 재논의하여 결정.

> **판단 이유**: 토론 끝에 결론을 내리지 못하고 향후 샘플 분석을 통해 결정하기로 하였으므로 펜딩으로 분류함.

## [미결] DB 가드레일 도입 시점

- **질문**: DB 접근 가드레일(안전장치)을 현재 개발 초기 단계에 도입할지, 기능 구현 완료 후 도입할지 결정해야 함.
- **배경**: 정우는 사고 방지를 위해 즉시 도입을 주장하고, 하은은 개발 속도 저하를 우려하여 추후 도입을 주장함.
- **선택지**: 
  - 지금 즉시 도입
  - 기능 구현 완료 후 도입
- **확인 조건**: 추후 추가 논의를 통해 합의.

> **판단 이유**: 논의 도중 의견이 갈렸으나 결론 없이 넘어갔으므로 펜딩으로 분류함.

## [학습] CS 요청의 복합적 성격

- **발견**: 고객 요청은 단일 '이슈'로 분류되기 어려운, 여러 성격이 혼재된 애매한 사례가 다수임.
- **근거**: 소이가 확인한 CS 로그 데이터에서 버그, 사용법 문의, 요금 불만 등이 복합적으로 나타나는 사례가 많음.

> **판단 이유**: 소이가 CS 로그 데이터를 근거로 제시한 사실적 발견이므로 러닝으로 분류함.

## 제외된 판단 (3개)

- "이슈 단위로 큐에 쌓이고 처리되는 편이 자동화하기 쉽다." — 결정이 아닌 하은의 제안 근거임.
- "태스크 기반으로 가면 단위가 너무 잘게 쪼개져 구현이 복잡해질 것이다." — 결정이 아닌 하은의 우려사항임.
- "태스크 기반은 잘게 쪼갤수록 연결 설계 문제가 생긴다." — 결정이 아닌 정우의 인지사항임.
