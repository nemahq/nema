# digest-engine eval

원문 → 다이제스트(정리) 단계의 프롬프트 품질을 확인하는 자리. 몫은 정리까지다 — 진술
추출·관계 판정·연결("잇기")은 각자 다른 단계라(`organizing.md` vs `linking.md`가 별개
챕터인 것과 같은 이유) 여기 몫이 아니고, 나중에 `statement-engine/`·`relation-engine/`이
생기면 그쪽 몫이다.

## 원문 성격 4축

포맷(Slack·회의노트·Linear 댓글 …)과는 다른 축 — "어디서 캡처됐나"가 아니라 "왜/어떻게
판단이 생겼나"다.

1. **목적/부산물**: 결정하려고 소집된 대화인가, 다른 목적으로 모였다가 판단이 곁가지로
   남았나. 둘 다 필요하다(부산물형은 캡처 값어치, 목적형은 Nema를 정리 자리로 쓰는 값어치).
2. **불확실성의 형태**: 확정(decision) / 탐색(pending·idea) / 암묵(assumption).
3. **참여자 구도**: 혼자 / 1:1 / 소그룹 / 외부개입.
4. **트리거**: 계획된 논의 / 외부 자극 반응 / 회고·재평가.

## 통과선

목표는 **좋은 다이제스트가 아니라 다음 단계(진술 추출)를 안 망치는 다이제스트**다. 정리
자체는 차별점이 아니고, 다이제스트를 쓰는 쪽(진술·관계)이 아직 없어 "좋다"의 기준을
지금은 못 세운다.

케이스마다 셋을 본다. 셋 다 참이면 통과.

| 통과선 | 볼 것 | 다음 단계로 번지는 이유 |
|---|---|---|
| 빠짐 | 원문의 판단이 다이제스트에 없나 | 없는 판단은 진술도 안 나온다 |
| 지어냄 | 원문에 없는 게 들어갔나 | 그대로 진술이 되어 없던 관계를 만든다 |
| 유형 오분류 | 유형이 틀렸나(결정/가정, 미결/아이디어) | 진술이 나오는 칸을 유형이 정한다 |

관찰 도구 — 위 통과선을 재는 항목:

- 다섯 유형 비율, 특히 assumption이 잡히는지 → 빠짐·유형오분류
- pending vs idea가 갈리는지 → 유형오분류
- 칸 공백률(원문에 없는 것만 비어야 함) → 빠짐·지어냄
- "재확인만 한 문장"과 "새 판단" 구분 → 빠짐·지어냄

**안 본다**: 문장 매끄러움, 요약 굵기, 제목. 다음 단계로 안 번지고, 연결이 서면 기준이
달라져 지금 깎아도 다시 깎게 된다. **워크로드별 최적 배치(거르기·판정·임베딩)도 아직 안
다룬다** — 그 동작들이 서고 난 뒤 다룬다.

모델은 `task-routing.ts`가 정하므로 이 자리에서 고르지 않는다. 결과는 실행 시점의 모델
id별로 `human-review/results/<model-id>/`에 쌓여, 모델을 바꿔 돌려도 직전 결과가 남는다.

## 멈추는 규칙

같은 증상에 프롬프트 수정은 2라운드까지. 안 고쳐지면 프롬프트가 아니라 구조 문제로 보고
멈춘다 — 흐름이 안 굳은 채 깎은 프롬프트는 흐름이 바뀌면 통째로 버려진다.

## 원문 재료

가상 데이터가 아니라 실제 기록에서 채운다(`samples/`). 4축·11종은 커버리지
체크리스트일 뿐, 채우는 재료가 실물이어야 잣대가 완성 기준(갈아타기 판정)과 같아진다.

## 평가 환경

staging. 로컬 Supabase는 워크트리 공유 스택이라 `db reset`마다 데이터가 날아간다.
도그푸딩 계정(`claude@getnema.app`)이 이 용도로 격리돼 있다. 지금은 사람이 눈으로 본다
(`human-review/`) — LLM 자동 채점(`llm-eval/`)은 통과선이 실전에서 안정된 뒤에 만든다.

## 다시 여는 조건

연결 단계가 서면 재개한다. 그때는 다이제스트 결함이 링크 실패로 드러나 눈에 보인다.
