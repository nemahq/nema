# digest-engine eval

원문 → 다이제스트(정리) 단계의 프롬프트 품질을 실제 원문으로 확인하는 자리. 몫은 정리까지다.
진술 추출·관계 판정·연결("잇기")은 각자 다른 파이프라인 단계라(`organizing.md` vs `linking.md`가
별개 챕터인 것과 같은 이유) 여기 몫이 아니고, 나중에 `statement-engine/`·`relation-engine/`이
생기면 그쪽 몫이다.

## 원문 성격을 보는 4축

포맷(Slack·회의노트·Linear 댓글·AI 세션 로그 …)과는 다른 축이다. 포맷은 "어디서 캡처됐나"고,
아래 넷은 "왜/어떻게 판단이 생겼나"다. 같은 포맷도 이 축에 따라 완전히 다른 신호를 낸다.

1. **목적/부산물**: 이 대화 자체가 결정하려고 소집됐나(목적형), 다른 목적으로 모였다가 판단이
   곁가지로 남았나(부산물형). Nema의 값어치는 부산물형에서 더 크다. 목적형은 사람이 어차피
   의식적으로 정리하는 경향이 있다.
2. **불확실성의 형태**: 확정(decision) / 탐색(pending·idea) / 암묵(assumption, 누구도 확인
   안 했지만 다들 그렇다고 가정하며 진행).
3. **참여자 구도**: 혼자 / 1:1 / 소그룹 / 외부개입(고객·투자자·파트너).
4. **트리거**: 계획된 논의 / 외부 자극 반응(고객 이탈·장애·경쟁사 움직임) / 회고·재평가.

## 테스트 케이스 8종

원문은 첫 대상(1~20인 스타트업 창업자·PM, AI를 업무에 깊게 쓰고 하루에도 여러 번 판단을
내리는 사람)이 실제로 만들 법한 원문에 가깝게, 민감정보를 뺐거나 실제 패턴을 본뜬 가상
데이터로 채운다(`samples/`).

## 평가 방식

지금은 **사람이 눈으로 본다**(`human-review/`). 아직 "무엇이 좋은 다이제스트인가"의 기준이
안 잡혀서, LLM 자동 채점(`llm-eval/`)을 먼저 만들면 검증 안 된 가정을 채점 기준에 미리
박아넣게 된다. 사람 리뷰를 몇 바퀴 돌려 기준이 잡히면 그때 `llm-eval/`을 채운다.

볼 것은 4가지다. 초기 논의에서 짚은 3가지, 실데이터에서만 보이는 것 1가지:

1. 다섯 유형 비율, 특히 assumption이 잡히는지
2. pending vs idea가 실제로 갈리는지
3. 칸이 얼마나 비는지(원문에 없는 것만 비어야 함)
4. "이미 정해진 걸 재확인만 한 문장"과 "이번에 새로 나온 판단"을 구분하는지
