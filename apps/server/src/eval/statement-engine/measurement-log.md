## 측정 #7 — 2026-06-19 · 측정 모델 교체 베이스라인 — Vertex `gemini-3.5-flash` (gpt-5 아님)

| 골든 F1 (P / R) | 0.842 (0.889 / **0.80**) | 0.93~0.958 (~0.95 / 0.917~0.944) | P≥0.8, R≥0.85 |
| 일관성 (쌍대 F1) | **0.906** | 0.855~0.877 | ≥0.85 ✅ |

**③ 짧은 글 무영향 회귀** — 통제 실험 포함:

| 조건 | F1 | meeting-memo |
|---|---|---|
| 옛 프롬프트 · #4 (전일) | 0.958 | 정상 |

**④ 상한 실주행**: 합성 입력 10,050토큰 → 7청크 병렬, 벽시계 138초, 진술 356개, 오류 0. verify-e2e 5단계 전부 ✅ — 장문 다청크가 **한 changeset으로 원자 적용**되고 `locator.index`가 원문 순서로 연속임을 실배관(RPC·RLS·Qdrant)에서 확인.

**결론**: 분할이 4층 검증을 전부 통과 — 일관성·원자성 개선, 경계 누락 없음, 짧은 글 무영향, 배관 원자성 유지. **머지 가능.** 남은 것: 일관성 절대값 보정(후속), mini 티어 적합성 실험(별도 이슈).

## 측정 #5 — 2026-06-12 · 길이별 곡선 — 초장문 분할의 관문 + 제공자 변동 발견

**발견**:

- **분할 필요 확정** (가설 → 사실): 빠른 시간대 기준으로도 ~2,700토큰부터 60초선이 깨지고, 일관성(진술 수 분산)은 ~1,278토큰 ±3~13% → 2,712토큰+ ±16~18%로 길이에 따라 무너진다. 지연은 입력 길이가 아니라 **출력량(진술 수)과 비례** — 분할의 본질은 한 콜의 출력량 묶기.
- **제공자 속도는 통제 변수가 아니다**: 같은 입력·같은 설정·재시도 0인데 두 스냅샷의 지연이 1.5~2.3배 차이. 진술 수는 비슷하므로 모델 출력이 아니라 제공자 처리 속도의 시간대 변동이다. 최소 급간(676토큰)도 느린 시간대엔 60초를 스쳤다 — **분할로는 타임아웃 안쪽을 보장할 수 없다.**
- #4의 "타임아웃 0건"도 빠른 시간대 스냅샷이었다는 뜻 — 단발 측정으로 타임아웃을 보정하면 안 된다.

**결정** (상세 근거는 [`long-input-chunking.md`](../../../../../docs/flows/save-engine-v2/long-input-chunking.md)):

- **역할 분담**: 분할(임계선 1,500토큰)은 출력량 — 평균 지연·일관성 — 을 묶고, **타임아웃은 제공자 출렁임을 흡수**한다.
- **추출 타임아웃 60→120초** + lease 90→150초(`extraction_lease_covers_slow_provider`): 60초는 느린 시간대의 정상 호출(1,278토큰 74~89초)을 죽은 호출로 오판해 끊는다. 비동기 파이프에서 타임아웃을 높게 잡는 오차(복구 몇 분 지연)는 낮게 잡는 오차(정상 작업 폐기)보다 싸다.
- 구현 후 이 곡선 러너의 분할 비교 모드로 재측정 예정 — 일관성 회복이 임계선 1,500의 합격 조건.
