# 진술 엔진 측정 일지

> 평가 러너의 라운드별 기록 — 무엇을 바꿨고, 숫자가 어떻게 움직였고, 무엇을 발견했나.

## 측정 #14 — 2026-06-24 · 검색 뭉치기 민감도 — 과소분할이 검색을 깨나 (NEM-168 태스크 8)

**바꾼 것**: 엔진·골든 불변, 새 측정 도구(`run-retrieval-degraded.ts` + 열화 모듈 `degrade.ts`). 합격선을 "현재 값"으로 잡으면 앵커링이라, 거꾸로 추출을 깎아 하류가 어디서 깨지나로 도출한다(§3 "아직 빈 것"). 깎기 = 골든을 문서 내 인접 진술로 뭉쳐(과소분할 모사 = #13의 쪼개기 경계 불안정) rate별 코퍼스를 다시 깔고 recall@5를 잰다. 합친 진술은 원본 여럿을 덮으므로(커버리지), 질의 기대 원본 id가 top-k 안 어느 합성 진술에 덮이면 recall 적중.

| rate | 진술 수 | recall@5 | precision@5 | MRR |
|---|---|---|---|---|
| 0 (불변) | 39 | 1.0 | 0.338 | 1.0 |
| 0.25 | 31 | 1.0 | 0.308 | 1.0 |
| 0.5 | 21 | 1.0 | 0.323 | 0.96 |
| 0.75 | 14 | 1.0 | 0.277 | 1.0 |
| 1.0 | 6 | 1.0 | 0.215 | 1.0 |

**발견**:

- **검색 recall은 뭉치기에 둔감하다 — 전 구간 1.0.** 문서 전체를 1진술로 합쳐도(39→6) recall이 안 떨어진다. 작은/좁혀진 코퍼스에선 top-5가 거의 전체라 recall이 포화된 것(§3가 경고한 "작은 시험지" 한계). rate=0 precision 0.338이 측정 #12(#309)의 sparse precision@5와 일치 — 채점 검증.
- **target 함의(역설적으로 유용): 검색은 추출 합격선을 빡빡하게 강제하지 않는다.** 과소분할의 진짜 해는 검색이 아니라 관계에서 온다(관계 일지 #7: effectiveRecall이 rate 0.5부터 무너짐). 관계가 binding constraint, 검색은 느슨한 바닥.
- **한계**: 작은 코퍼스라 recall 포화 — 진짜 recall cliff는 dense 코퍼스(distractor 수천, #9)에서만 보인다. 후속 정밀화 거리.

**다음**: 관계 일지 #7과 함께 입력측 target 1차. 검색 recall의 실측 cliff는 dense 위에서.

## 측정 #13 — 2026-06-24 · 추출 일관성, 실데이터·고품질 맥락 (NEM-168 태스크 7)

**바꾼 것**: 엔진 불변, 새 측정 도구(`run-extraction-consistency.ts` + 공유 코어 `extraction-core.ts`로 #1~#10 추출 러너의 매칭·일관성 로직 재사용). tiro 실데이터 전사(`transcript.txt`)를 제품 경로 `generateDraft`(드래프팅 프롬프트, v1 폴리시)로 정제해 **고품질 맥락**(태스크 6 결정: "고품질 맥락 = generateDraft 출력")을 만들고, 그 위에서 추출 5회의 쌍대 F1(일관성)을 잰다. 골든 없음 — 일관성은 자기참조라 정답지 불요. **합성 골든 시험지(#10)가 일관성을 부풀리는지, 태스크 1이 짚은 모델 약점(쪼개기 경계 불안정)이 실데이터·고품질 맥락에서도 재현되는지** 본다.

| 노트(타입) | 일관성 | 진술 수(5 run) | 분산 |
|---|---|---|---|
| 회의(상담 통계 설계) | 0.867 | 18/17/16/17/18 | 0.12 |
| 인터뷰(사용성) | 0.854 | 23/26/26/24/27 | 0.16 |
| 아이데이션(리포트 알리기) | 0.867 | 20/21/21/19/17 | 0.20 |
| **평균(3)** | **0.863** | — | **0.16** |

(비교: 골든 일관성 #10 0.906 / 합격선 0.85. 측정 모델 gemini-3.5-flash, 판정 Claude sonnet-4-6. transcript 10~14k자 → draft 1.1~1.9k자.)

**발견**:

- **실데이터 일관성이 골든보다 낮다 (0.863 < 0.906).** 합성 골든 시험지가 일관성을 ~0.04 부풀린다 — §3가 검색에서 본 "작은 시험지가 부풀린 점수"가 추출 쪽에서도 확인된다. 단 0.85 합격선은 넘는다(빠듯).
- **불안정이 체계적이다.** 세 노트 타입(회의·인터뷰·아이데이션)에서 0.854~0.867로 타이트하게 수렴 — 특정 노트 특이성이 아니라 추출의 구조적 성질. 진술 수가 같은 입력 5회에서 ±12~20% 흔들린다. 골든 글은 짧아 진술 ~5~9개로 쪼개기 경계가 적은데, 실 노트는 16~27개라 경계가 많고 그만큼 흔들림 표면이 크다. **태스크 1이 짚은 "쪼개기 경계 불안정"이 실데이터·고품질 맥락에서 직접 재현된다.**
- **v1 폴리시 기준.** 고품질 맥락 = generateDraft 출력(태스크 6, 코드=v1). draft도 측정 모델(flash)로 생성. 드래프팅 프롬프트·모델이 재검증되면 재측정.
- **표본 한계 + 측정 도구 보강.** 5개 추출했으나 3개 평가 — 2개(싱크·인터뷰)는 일시 인프라 실패(긴 전사 draft 타임아웃·네트워크 fetch failed)로 빠졌다. 데이터 결함 아니며, 두 실패를 도구 보강으로 막았다: ① generateDraft 타임아웃 180초+재시도, ② judge의 fetch 전송 오류를 재시도 대상에 포함(기존엔 HTTP 상태 오류만 재시도), ③ judge 동시성 8→16(벽시계 병목 — 실호출 8,680건이 단일 세마포어를 통과하던 것). 다음 무거운 run(태스크 8)이 이 위에서 돈다.

**다음**: 이 0.863은 태스크 8(민감도 target)의 입력이다 — 일관성·경계를 일부러 떨어뜨리면 하류(검색 recall·관계 F1)가 어디서 깨지나로 합격선을 도출한다. 실데이터 일관성이 골든보다 낮다는 건, 추출 target도 골든 절대값이 아니라 난도 올린 실데이터 위에서 확정해야 함을 뒷받침한다.

## 측정 #12 — 2026-06-24 · 측정 도구 보강 — Precision@k · macro-F1 · promptHash (NEM-168 태스크 11 a·b·c)

**바꾼 것**: 엔진·골든 불변, 자(러너)만 보강. (a) `run-retrieval`·`run-retrieval-dense`에 **Precision@k** 추가 — recall만으론 "건진 것 중 잡음"이 안 보인다. 분모는 top-k 실건수(threshold 무관한 순위 품질, 측정 #9의 흔들리는 0.2 임계에 안 묶이게). (b) `run-extraction` 분류 채점에 **클래스별 P/R/F1 + macro-F1** — accuracy가 다수 클래스(claim)에 눌려 소수 클래스(question·todo) 실패를 가린다. 순수 함수로 `metrics.ts`에 빼 단위테스트로 수식 고정. (c) `run-extraction` 결과에 **promptHash**(run-judgment와 동형) — 결과가 어느 추출 프롬프트로 잰 것인지 자기증명.

| 러너 | 코퍼스 | recall@5 | **precision@5** |
|---|---|---|---|
| sparse (run-retrieval) | 골든 39 | 1.0 | **0.338** |

**발견**:

- **sparse precision@5(0.338)은 잡음이 아니라 구조적 상한**이다. 정답이 1~2개뿐인 질의가 많아 P@5 ≤ |expected|/5에 묶인다(proper-noun 축 0.2 = 정답 1개, negation 0.4 = 정답 2개). distractor가 없는 sparse라 당연 — **precision의 잡음 신호는 dense(distractor 수천)에서 의미가 산다.** 같은 코드 경로라 dense 러너가 곧 그 값을 낸다.
- **macro-F1·promptHash는 코드/단위테스트로 검증**(`metrics.test.ts`: accuracy 0.83인데 소수 클래스 전멸 시 macro 0.455로 떨어지는 케이스 고정). 실측 round는 추출 러너가 judge(Anthropic) 키를 요구해 이 세션에선 미실행 — 다음 추출 측정 때 macro-F1이 결과지에 함께 찍힌다.

## 측정 #9 — 2026-06-23 · 검색 난도 ↑ — tiro 실데이터 distractor 주입 (NEM-168 ⑤ 첫 실측)

**바꾼 것**: 엔진 그대로. 새 러너 `run-retrieval-dense.ts` — tiro 실데이터(`.local/tiro-samples`)의 요약(`summary.md`)을 추출해 진술 distractor를 만들고, 골든 40개 코퍼스에 부어 빽빽한 검색을 시험한다. 기존 검색 eval(골든 40개만)은 경쟁자가 적어 recall 0.978이 "쉬운 시험"이었다 — 실density에서 버티나 본다. 요약을 쓰는 건 원본 전사가 아니라 이미 깎인 맥락이라 엔진 설계 입력에 가깝고, distractor 용도라 라벨도 불필요(recall은 골든으로만 채점).

| 지표 | sparse (40) | dense (1,076 · 10글) | dense (6,521 · 60글) |
|---|---|---|---|
| recall@5 | 0.978 | 0.90 | **0.722** |
| MRR | 1.0 | 0.9 | 0.828 |
| paraphrase | 1.0 | 0.944 | 0.833 |
| negation | 1.0 | 1.0 | **0.5** |
| proper-noun-variant | 1.0 | 1.0 | 1.0 |
| temporal | 0.834 | 0.5 | 0.167 |
| 무정답 q16 / q17 top | 0.24 / 0.16 | 0.31 / 0.20 | 0.34 / 0.25 (둘 다 distractor) |

**발견**:

- **0.978은 작은 코퍼스가 부풀린 값**. 코퍼스가 40→6,521로 자라며 recall이 0.978→0.72로 내려간다. 곡선이 결과지 단일 숫자가 아니다.
- **단 0.72를 그대로 믿으면 안 된다**: 검색은 space/줄기로 한정되므로(`statement-search.ts`의 spaceIds) 6,521 전부가 한 질의와 경쟁하는 건 전체-계정 최악 가정이다. 실 operating recall은 scope 코퍼스 크기에 달려 0.72~0.90 사이. **scope별 코퍼스 크기 측정이 다음 정밀화 거리.**
- **temporal은 의미검색 소관이 아니다**(0.834→0.167). "다음주·이번 주"는 의미 유사도가 아니라 날짜다. 생성 시각(createdAt·changeset)이나 내용 속 기한을 구조화해 거를 일 — **의미검색 eval에서 빼고 구조화 시간 경로로 재배치.**
- **negation이 density에서 무너진다**(1.0→0.5). q4 "직접 연동을 선택하지 않은 이유" → 0. 부정 질의의 진짜 약점이 빽빽함에서 드러남.
- **proper-noun은 1.0 유지** — 고유명사 토큰 겹침은 density에 강하고, 순수 의미 매칭(paraphrase·negation)이 약하다.
- **무정답 누설 악화** — q16·q17 top이 둘 다 distractor로 0.2를 넘는다. threshold 0.2가 실코퍼스엔 낮다(단 정답 하단 0.21도 가까워 시소).

**분류 (NEM-168)**: recall-at-scale 하락 = 진짜 튜닝/아키텍처(재랭킹·scope 조이기) — 측정 잡음 아님. temporal = 재배치(구조화 시간). negation = 새 약점 주시. threshold = 실코퍼스 기준 재검토. **distractor 1글당 ~100개라 밀도가 높다 — 요약이 상세하거나 추출이 잘게 쪼갠 것, distractor 용도엔 무방.**
