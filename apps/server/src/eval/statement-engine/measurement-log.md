## 측정 #20 — 2026-06-25 · eval B 1차 — scope vs 전역 recall, 빽빽한 코퍼스 (NEM-168 ④ 성과)

**바꾼 것**: 신규 러너 `run-retrieval-scoped.ts` + `retrieval-scoped-seed.ts`(질의 6). auto-scoping의 제품 주장("코퍼스가 커지면 전역 top-k가 깨지고 scope가 지킨다")을 처음 끝단으로 잰다([auto-scoping-design](../../../../../docs/flows/save-engine-v2/auto-scoping-design.md) §6 B). 코퍼스 = tiro threaded 81글(18주제 라벨) + standalone 80글(무태그) = **15,462 진술**. 같은 질의를 (가) 전역 전체 검색, (나) coarse가 고른 주제 + 무태그로 좁힌 검색으로 돌려 top-5 안 정답-주제 비율(density)·hit를 비교한다. 모델 gemini-3.5-flash, voyage 임베딩.

| 질의 | 정답 주제(진술수) | coarse | 전역 d@5 / hit | scope d@5 / hit |
|---|---|---|---|---|
| s1 suggest | suggest(517) | ✓ | 0.8 / ✓ | 1.0 / ✓ |
| s2 module_fed | module_fed(254) | ✓ | **0 / ✗** | **0.4 / ✓** |
| s3 phone_monitor | (259) | ✓(+2 과선택) | 0.4 / ✓ | 0.4 / ✓ |
| s4 connect | (188) | ✓ | 0.8 / ✓ | 0.8 / ✓ |
| s5 ai_mkt_engine | (1495) | ✓(+3) | 0.4 / ✓ | 0.6 / ✓ |
| s6 post_eval | (1682) | ✓(+1) | 0.6 / ✓ | 0.6 / ✓ |
| 평균 | | 1.0 | hit 0.833 · d 0.50 | **hit 1.0 · d 0.633** |

**발견**:

- **scope가 전역을 한 번도 안 깬다 — 6/6에서 ≥.** density 0.50→0.63, hit 0.83→1.0. 좁혀서 손해 본 질의가 없다.
- **핵심 증거 s2**: 15,462 진술 빽빽함에서 **전역 top-5가 module_fed를 0개 잡았다(miss)** — 254개 정답 진술이 다른 17주제·무태그에 전부 밀렸다. 주제로 좁히니 top-5에 2개(0.4, hit). 빽빽함에서 전역이 통째로 놓친 정답 주제를 scope가 구한다 — eval B의 핵심 주장 1건이 끝단으로 입증됐다.
- **coarse 라우팅 6/6 정확**(측정 #17이 dense 코퍼스·실검색 배선에서도 재확인). 단 s3·s5·s6은 과선택(여러 주제) — recall 무벌점 설계대로지만 scope를 넓혀 이득을 희석한다.
- **이득이 압도적이진 않다(0.5→0.63)**: ① 무태그 80글이 scope에도 항상 포함돼(설계 §4) 희석, ② 일부 질의는 전역도 충분(s4 0.8). 무태그 비율이 이득의 큰 노브임을 시사.

**부수 발견**: COARSE_QUERIES(측정 #17)를 eval B에 못 썼다 — buried 질의의 디테일(230만원·iframe 등)이 실제 gold 주제 노트에 실재하는지 #17이 검증한 적 없어, 절반이 gold 주제 밖이거나 summary에 없었다(coarse는 노트를 안 보고 질의만 본다). 그래서 노트를 직접 읽어 답이 실재하는 질의를 신작했다. → 측정 #17 buried recall은 "라우팅"의 신호지 "그 사실이 그 주제에 산다"의 신호가 아니다.

**한계**: 표본 6 잠정. 근사 채점(정답=주제 단위, 진술 정밀도 없음). 무태그 80/161 비율이 이득에 민감. 단발·flash.

**다음**: 6→18주제로 질의 확장(통계 강화). 무태그 비율 민감도(scope 이득이 무태그 양에 얼마나 눌리나)는 그 다음.

## 측정 #19 — 2026-06-25 · coarse를 구조화에 합칠까 분리할까 — 라우팅 퇴행 (NEM-168 ④ 배선)

**바꾼 것**: 엔진 불변, 측정만. auto-scoping 배선(#324)에서 coarse(주제 라우팅)를 질의 구조화(시간·의미) 콜에 **합칠지 분리할지**를 가른다. 설계 §3.2는 비용 절약으로 "한 콜"이었는데, 합친 프롬프트로 #17 시험지(tiro 18주제·28질문)를 다시 잰다. 모델 gemini-3.5-flash.

| coarse 라우팅 (이름만) | 전체 | 묻힌 사실 |
|---|---|---|
| 분리 (독립 프롬프트, #17) | 0.929 | 0.8 |
| **합침** (구조화에 끼움) | **0.786** | **0.40** |

시간 토큰 정확도는 두 방식 다 2/2(무손상).

**발견**:

- **합치면 주제 라우팅이 깎인다 — 묻힌 사실 0.8→0.40 반토막.** 시간은 멀쩡한데 주제만 무너진다. 한 콜에서 시간+의미+주제를 같이 시키니 주제 주의가 희석된 것(시간 지시·예시가 프롬프트를 지배). 테마형·인접·강등은 1.0 유지, 어려운 칸만.
- **분리하면 회복.** coarse를 독립 프롬프트로 떼어 `structureQuery`와 병렬 호출하면 이름만 0.893/묻힌 0.7(#17의 0.929/0.8과 같은 급, 0.89 vs 0.93은 단발 변동), 이름+설명 1.0. 합침의 0.786/0.40 퇴행이 사라진다.
- **비용은 거의 같다.** 분리해도 주제 목록을 어차피 보내니 토큰 ~5%·API 왕복 1번뿐, 병렬이라 지연 무변. "한 콜" 절약이 실은 작은데 품질 손해는 컸다.

**결론**: 설계 §3.2의 "한 콜"을 측정이 기각 — coarse를 분리(병렬)로. 가드레일이 합침의 퇴행을 잡았다(안 돌렸으면 주제 반토막인 채 머지될 뻔). 한계: 단발·flash·시험지 28문항 잠정.

| 0.75 | 14 | 1.0 | 0.277 | 1.0 |
| 1.0 | 6 | 1.0 | 0.215 | 1.0 |

|---|---|---|---|
| sparse (run-retrieval) | 골든 39 | 1.0 | **0.338** |

- **무정답 누설 악화** — q16·q17 top이 둘 다 distractor로 0.2를 넘는다. threshold 0.2가 실코퍼스엔 낮다(단 정답 하단 0.21도 가까워 시소).
