# statement-engine eval

다이제스트 → 진술(Statement) 단계의 프롬프트 품질을 확인하는 자리. 몫은 진술 만들기까지다
— 후보 검색·거르기·판정·관계 저장은 각자 다른 단계라 여기 몫이 아니고, 나중에
`relation-engine/`이 생기면 그쪽 몫이다.

## 원문 재료

`digest-engine/samples/`를 그대로 쓴다. 새 코퍼스를 안 만드는 이유: `source.ingest` 한
콜이 다이제스트와 진술을 함께 낸다(source-service.ts). 같은 원문을 다시 넣으면 다이제스트와
진술이 한 응답에 같이 나오므로, 케이스를 복제해서 관리 부담을 늘릴 이유가 없다. 다이제스트
품질은 `digest-engine`이 재고, 여기는 그 다이제스트에서 나온 `statement` 칸만 본다.

## 통과선

목표는 **혼자 읽히는 진술**이다. 킥오프 문서("무엇을 확인하려는가")가 정한 셋을 그대로
쓴다. 케이스마다 셋을 본다. 셋 다 참이면 통과.

| 통과선 | 볼 것 | 왜 |
|---|---|---|
| 완전성 | 다이제스트만 보고 진술을 쓸 수 있었나(진술 없이 남은 다이제스트가 있나) | 못 쓴 게 있다면 그건 다이제스트가 부실한 것 — 이 단계가 정리 단계의 채점표 노릇을 한다 |
| 자기완결성 | 진술 문장만 따로 떼어 읽어도 무슨 말인지 알 수 있나(대명사·암묵 지시어가 안 풀렸나) | 진술은 다이제스트 없이 혼자 검색·비교되는 단위라(linking.md 2.3), 여기서 안 풀리면 뒤 단계 전부가 흔들린다 |
| 새어듦 | 주된 칸이 아닌 다른 칸(이유·트레이드오프·근거)의 내용이 진술에 섞여 들어왔나 | 섞이면 "같은 선택인가"를 물어야 할 자리에서 이유까지 비교하게 돼 판정이 어긋난다(linking.md 2.2) |

관찰 도구:

- 진술 없는 다이제스트 비율(전체 다이제스트 대비) → 완전성
- `digestField`별로 주된 칸 값과 진술 문장을 나란히 놓고 대조 → 자기완결성·새어듦

**안 본다**: 문장의 유려함, 길이. 다음 단계(후보 검색·판정)로 안 번진다.

## 멈추는 규칙

`digest-engine`과 같다 — 같은 증상에 프롬프트 수정은 2라운드까지. 안 고쳐지면 구조 문제로
보고 멈춘다.

## 평가 환경

**1차 리뷰는 로컬**로 한다. `digest-engine`은 staging을 쓰지만(도그푸딩 계정, `db reset`에도
안 날아가는 영속성), 이 슬라이스가 만든 `statements` 테이블은 아직 `staging` 브랜치에
머지되기 전이라 staging DB에 없다 — 지금 staging에 대고 돌리면 진술 생성 자체는 되지만
저장이 매번 실패해서 결과에 진술이 하나도 안 보인다. `human-review/run.ts`가 로컬
Supabase(`supabase start`)에 로컬 서버(`APP_ENV=local`)로 붙는다. **이 스택이 `staging`에
머지된 뒤에는 `digest-engine`과 같은 방식(staging + 도그푸딩 계정)으로 옮긴다** — 결과가
worktree `db reset`에 안 날아가고, 실사용에 더 가까운 환경에서 재보게 된다.

## 다시 여는 조건

`digest-engine`과 같은 원문으로 재보는 구조라, 다이제스트 프롬프트가 바뀌면 여기도 다시
돈다. 후보 검색·거르기·판정 단계가 서면 관찰 도구에 그쪽 지표를 더한다.
